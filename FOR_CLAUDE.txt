PeerCraft — handoff notes for a fresh Claude session
=====================================================
Written: 2026-08-18. HEAD commit: 1c1d1ab "UDP hole punching first realization"
(prior: 51fbb2a "multiplayer on localhost is done").

WHAT THIS PROJECT IS
---------------------
A Fabric Minecraft mod (early-stage alternative to Essential/LabyMod-style P2P
multiplayer) that lets two players connect directly to each other's world without
either running a real dedicated server or opening router ports on their own
machines. It works by tunneling the raw Minecraft TCP protocol over a custom
framed UDP relay between two mod instances, with real internet peers found via a
small rendezvous server + UDP hole punching.

CURRENT STATUS: WORKING, INCLUDING REAL CROSS-INTERNET P2P.
The user just confirmed a successful UDP hole-punch connection with a friend on a
genuinely different network — the full pipeline (rendezvous → punch → relay →
Minecraft join) has been validated end-to-end outside of loopback/LAN testing.
This is the first time that's been confirmed; prior sessions only had local
(same-machine) testing fully validated, plus one earlier failed real-world attempt
that led to two real bugs being found and fixed (see "Bugs found and fixed" below).

REPO LAYOUT — TWO INDEPENDENT GRADLE PROJECTS, SAME REPO
----------------------------------------------------------
/home/ikuku/desktop/PeerCraft/
  fabric-example-mod/   — the actual Fabric mod (Minecraft 1.21.1, Java 21, Loom).
                           Its own gradlew; `./gradlew build` here only.
  rendezvous-server/    — standalone plain-Java UDP server, NO Minecraft/Fabric
                           dependency at all. Its own gradlew; `./gradlew jar`
                           produces one runnable jar meant to be copied to a
                           separate always-on machine (currently: user's old
                           laptop, port-forwarded, same way they'd forwarded a
                           port for a vanilla MC server before).

These are deliberately NOT a multi-module build (no root settings.gradle) — kept
independent so the mod's Loom toolchain and the server's plain-Java build never
interfere. Downside: RendezvousProtocol.java (the wire codec) is hand-duplicated
between the two projects — both copies have a `fixedEncodingMatchesModCopy`/
`fixedEncodingMatchesServerCopy` unit test pinning exact wire bytes so drift is
caught immediately if either copy is edited without the other.

ARCHITECTURE — TWO LAYERS
---------------------------

1) THE RELAY (fully working, extensively validated, do not casually rewrite):
   MC client (TCP) -> LocalProxy (TCP, 127.0.0.1:25566) -> P2PBridge -> UDP ->
   [network] -> UDP -> P2PBridge -> TCP -> IntegratedServer (host's real world)

   Key files (fabric-example-mod/src/main/java/net/peercraft/network/p2p/):
   - FramedPacket.java   — wire format: [version=2][type][flags][sessionId:8][seq:8]
                            + payload. type 0=DATA, 1=NACK. flags bit0=FIN.
   - ReorderBuffer.java  — per-direction reassembly. Returns a Result{deliverable,
                            requestSeq}: on a gap it signals which seq to NACK
                            (debounced ~200ms) instead of just timing out. A
                            3s-since-last-progress SessionBrokenException is the
                            last-resort "give up and close cleanly" path.
   - P2PBridge.java      — the orchestrator singleton (P2PBridge.INSTANCE). Owns
                            HostConnection/ClientSession nested classes (sessionId,
                            seq counter, ReorderBuffer, a bounded 256-entry
                            retransmit ring buffer keyed by seq for honoring
                            NACKs). MAX_CHUNK_SIZE=8000 — large TCP reads get split
                            into multiple ≤8000-byte UDP datagrams before sending,
                            because this dev machine's firewall was empirically
                            found to hard-drop UDP datagrams >~16.3KB on the
                            relay's specific ports (not a general internet limit,
                            but capping chunk size sidesteps needing to know the
                            local threshold, and is good practice for real
                            internet MTU/NAT robustness anyway).
   - P2PSender.java / P2PReceiver.java — thin DatagramSocket wrappers. IMPORTANT:
                            they now share ONE socket (P2PReceiver binds it,
                            P2PSender takes it via constructor + getSocket()) —
                            this was a real bug fix: sending from a *different*
                            ephemeral port than the one whose NAT mapping got
                            punched would silently break real internet P2P (was
                            invisible on loopback). P2PReceiver decouples the
                            socket-read loop from packet processing via a
                            bounded queue + worker thread so a slow downstream
                            write can never stall socket draining.
   - RawPacketListener.java — tiny interface P2PBridge dispatches non-FramedPacket
                            (rendezvous/punch, magic byte 0xE1) datagrams to.

   fabric-example-mod/src/main/java/net/peercraft/network/proxy/LocalProxy.java —
   the local TCP proxy the *joining* MC client actually connects to
   (127.0.0.1:25566, not the LAN port).

2) INTERNET P2P — rendezvous + hole punching (new this session, now confirmed working):
   fabric-example-mod/src/main/java/net/peercraft/network/rendezvous/:
   - RendezvousProtocol.java — wire codec for [magic=0xE1][type]+payload control
     messages: REGISTER, ROOM_CREATED, JOIN, JOIN_FAIL, PEER_FOUND (server-facing)
     and PUNCH/PUNCH_ACK (peer-to-peer, server never sees these).
   - RendezvousClient.java — talks to the rendezvous server. Host calls
     registerRoom(...), gets a 6-char room code back (alphabet excludes
     0/O/1/I/L). Joiner calls joinRoom(code, ...). Retries REGISTER/JOIN every
     500ms but ONLY while still on that specific step (bug fix history below);
     once the host has its code (WAITING_FOR_PEER), a separate 15s keepalive
     (resending REGISTER, idempotent) keeps its NAT mapping to the rendezvous
     server open indefinitely while waiting for a friend to join — no client-side
     timeout for that wait, only the server's own 10-minute unclaimed-room TTL.
   - PunchCoordinator.java — once PEER_FOUND gives a peer address+token, sends
     PUNCH{token} every 300ms for up to 10s, watching for PUNCH/PUNCH_ACK back
     from exactly that address+token. On success calls
     P2PBridge.setTargetPeer(ip, port) — the EXACT SAME method the old static-
     config path used, so everything in layer (1) above runs completely
     unchanged after a successful punch. No TURN/relay fallback on failure —
     deliberate v1 scope decision (a home-hosted rendezvous server's uplink
     can't sustain relaying full game traffic for multiple pairs); failure is
     just a clean log message.

   rendezvous-server/src/main/java/net/peercraft/rendezvous/:
   - RendezvousServer.java — single-threaded UDP receive/dispatch loop + a
     30s-interval sweep thread for expiring old rooms. All log lines now
     timestamped (HH:mm:ss.SSS) and fairly verbose (every REGISTER logged
     including idempotent/keepalive resends; on INVALID_CODE it dumps every
     room it currently knows about) — this was added mid-session while
     debugging a real "room code went invalid" incident, see below.
   - RoomRegistry.java — in-memory only, no persistence (rooms are pairing
     handshakes, not accounts). 6-char codes, unclaimed TTL 10 min, claimed TTL
     60s (grace window for a joiner's own UDP-retried JOIN to get the same
     idempotent answer), per-IP REGISTER rate limit (5/60s), global unclaimed-
     room cap (1000) — all as SERVER_BUSY-style rejection, not silent drops.
   - Room.java — mutable per-code state, package-private, only touched while
     `synchronized` on the Room instance itself (see RoomRegistry.join()).

   Integration points on the client:
   - P2PBridge.startHostViaRendezvous(mcPort) / startClientViaRendezvous() — new
     entry points, parallel to the old startHost()/startClient(). Wire up
     RendezvousClient -> (on match) PunchCoordinator -> (on punch success)
     setTargetPeer(...). The rendezvousListener field is swapped between the
     RendezvousClient and PunchCoordinator instances as the flow progresses;
     handleIncomingPacket demuxes on the first byte (0xE1) before ever reaching
     FramedPacket.decode.
   - OpenToLanMixin.java / PeerCraftClient.java — branch on
     PeerCraftConfig.internetPlay(): call the ViaRendezvous variants instead of
     the static ones. mode (host/client/auto/disabled) is UNCHANGED and still
     required — internetPlay is an orthogonal opt-in layered on top, not a
     replacement.

CONFIG (PeerCraftConfig.java) — all via -Dpeercraft.<key> or PEERCRAFT_<KEY> env,
same convention throughout, see its own doc comments and fabric-example-mod/README.md:
  mode, proxyPort, clientUdpPort, hostUdpPort, peerHost, peerPort   (original, local path)
  internetPlay (bool, default false), rendezvousHost, rendezvousPort, roomCode  (new)

NO IN-GAME UI YET for any of this — room codes are only ever visible in the log
file / console (`Комната создана! Код для второго игрока: XXXXXX`), and the
joiner must be given the code out-of-band (chat, Discord, etc.) and pass it via
-Dpeercraft.roomCode at launch. This is a known, deliberate v1 gap.

BUGS FOUND AND FIXED THIS SESSION (useful history, don't reintroduce)
------------------------------------------------------------------------
1. P2PSender/P2PReceiver used two different sockets — fatal for hole punching
   (see above). Fixed by sharing one socket.
2. RendezvousClient's retry loop kept resending REGISTER every 500ms for the
   full 10s window even after ROOM_CREATED had already arrived (checked "not
   done yet" instead of "still on this specific step") — flooded the server for
   no reason AND would have spuriously timed out a healthy WAITING_FOR_PEER room
   if a friend took >10s to join. Fixed: retry loop is now scoped to the exact
   state it started in.
3. Discovered via a real failed cross-network attempt: after fix #2 removed the
   spam, the host sent NOTHING while waiting for a joiner — and a home router's
   UDP NAT mapping to the rendezvous server closes after a period of inactivity
   (commonly 30-60s), so a PEER_FOUND reply arriving after that silently gets
   dropped by the host's own NAT/firewall. Fixed with a 15s keepalive (chosen
   specifically for safety margin) — resends REGISTER (idempotent) while in
   WAITING_FOR_PEER, stops once matched/failed.
4. One real cross-network test hit "неверный код комнаты" (INVALID_CODE) for a
   room that should still have been valid (well within the 10-min TTL, server
   not restarted) — root cause NOT fully confirmed yet. Leading theory: the
   host's NAT re-mapped its external port between the original REGISTER and a
   later keepalive, so RoomRegistry's idempotency check (keyed on the full
   (ip,port) pair) missed and silently created a second, orphaned room the host
   never learned about (RendezvousClient stops listening for ROOM_CREATED after
   the first one). Added diagnostic logging (see RendezvousServer changes above)
   to catch this with hard evidence next time it happens, rather than guessing
   further. NOT YET CONFIRMED OR DISPROVEN — worth watching for.
   NOTE: the very next test after this (the one that just succeeded with the
   user's friend) apparently worked fine, so this may have been a one-off or
   specific to that network path — but the diagnostic logging is still in place
   and worth checking if it recurs.

TESTING
-------
- fabric-example-mod: `./gradlew test` — includes FramedPacketTest,
  ReorderBufferTest (local relay), RendezvousProtocolTest (wire round-trip +
  fixed-byte pin), RendezvousClientTest (regression test for bug #2 above),
  RendezvousEndToEndTest (spins up the REAL rendezvous-server jar as a
  subprocess and drives real RendezvousClient/PunchCoordinator through a full
  register->join->punch flow on loopback — self-skips if the server jar hasn't
  been built yet; build it first with `cd rendezvous-server && ./gradlew jar`).
- rendezvous-server: `./gradlew test` — RendezvousProtocolTest, RoomRegistryTest
  (uses a package-private LongSupplier-clock constructor seam for deterministic
  TTL/grace-window tests without sleeping), RendezvousServerIntegrationTest
  (real server subprocess-free, in-JVM, driven by raw DatagramSockets).
- Local two-instance MC testing: see fabric-example-mod/README.md — separate
  `run-host/`/`run-client/` working directories (IDE run configs "Minecraft
  Client (host)" / "Minecraft Client (join)" already set up this way) so their
  logs/latest.log files don't interleave. Also documents the reconnect
  regression test and the full internet-play test procedure.
- IMPORTANT environment note: this dev machine's `java-21-openjdk` package was
  originally JRE-only (no javac) — full JDK had to be installed
  (`jdk21-openjdk`) for `./gradlew build`/`test` to work at all. If a fresh
  session hits "does not provide the required capabilities: [JAVA_COMPILER]",
  that's the same issue (stale Gradle daemon started before the JDK was
  installed) — `./gradlew --stop` then retry usually fixes it.

WHAT'S DELIBERATELY OUT OF SCOPE FOR NOW (don't build unless asked)
------------------------------------------------------------------
- TURN/relay fallback when hole punching fails.
- Symmetric-NAT/CGNAT port prediction (punch only tries the exact server-
  observed address, no guessing).
- Accounts, persistent lobbies/friend lists, server browser — user has said
  they want these eventually but explicitly wanted a simple v1 first.
- Rendezvous protocol auth/encryption — plaintext UDP, fine for a self-hosted
  low-value-target server for now, flagged as a real gap if ever exposed wider.
- In-game UI for room codes (currently log-only).
- IPv6 (address encoding allows it, untested).
