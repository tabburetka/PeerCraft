WHAT THIS PROJECT IS
---------------------
A Fabric Minecraft mod (early-stage alternative to Essential/LabyMod-style P2P
multiplayer) that lets several players connect directly to one host's world
without anyone running a real dedicated server or opening router ports. It
works by tunneling the raw Minecraft TCP protocol over a custom framed UDP
relay between mod instances, with real internet peers found via a small
rendezvous server + UDP hole punching. The host chooses a max-player count
when opening their world to the network; multiple joiners can be connected
to the same room concurrently, and a slot freed up by a leaving player
becomes available again within ~15 seconds (see ARCHITECTURE below).

ARCHITECTURE — TWO LAYERS
---------------------------

1) THE RELAY (now multi-peer on the host side — see this session's changes):
   MC client (TCP) -> LocalProxy (TCP, 127.0.0.1:25566) -> P2PBridge -> UDP ->
   [network] -> UDP -> P2PBridge -> TCP -> IntegratedServer (host's real world)

   Key files (fabric-example-mod/src/main/java/net/peercraft/network/p2p/):
   - FramedPacket.java   — wire format: [version=2][type][flags][sessionId:8][seq:8]
                            + payload. Unchanged this session.
   - ReorderBuffer.java  — per-direction, per-session reassembly. Unchanged
                            this session; the host now owns ONE instance PER
                            JOINER instead of one for the whole bridge (see
                            HostConnection below), but the class itself is
                            the same.
   - PeerAddress.java    — NEW this session. record PeerAddress(InetAddress
                            host, int port) — routing key used throughout
                            P2PBridge to tell joiners apart.
   - P2PBridge.java      — the orchestrator singleton (P2PBridge.INSTANCE).
                            REWORKED this session for multiple concurrent
                            host-side peers:
                              * hostConnectionsBySessionId / hostConnectionsByAddress
                                (both ConcurrentHashMap) replace the old single
                                `currentHostConnection` field — one HostConnection
                                object per joiner, keyed both ways (sessionId
                                is still the trust anchor; address is for fast
                                admission + live player-count).
                              * authorizedPeers (Set<PeerAddress>) — NEW
                                admission gate: a HostConnection can only be
                                opened for an address that actually completed
                                a hole punch. This also closes a latent gap
                                that existed before this session: previously
                                ANY UDP sender who guessed the host's relay
                                port and crafted a seq==0 frame could open a
                                live TCP session to the host's local MC
                                server without ever punching or knowing the
                                room code.
                              * activePunches (Map<PeerAddress, PunchCoordinator>)
                                — replaces the old single rendezvousListener
                                slot ON THE HOST ONLY; several punches to
                                different joiners now run concurrently
                                without cancelling each other. The JOINER
                                role still uses a single rendezvousListener
                                slot (unchanged, correct — a joiner only ever
                                talks to one host).
                              * clientTargetPeer (PeerAddress) replaces the
                                old targetIp/targetPort pair — joiner-role
                                only now (the host never had a single target
                                peer conceptually, that was always the actual
                                bug being fixed).
                              * currentPlayerCount() = hostConnectionsByAddress.size()
                                — fed into RendezvousClient.registerRoom(...)
                                as an IntSupplier, re-read on every 15s
                                keepalive. THIS is the entire mechanism behind
                                "a slot freed up by a leaving player becomes
                                available again" — no dedicated "player left"
                                wire message was added; the host just keeps
                                self-reporting its live count.
                              * sendEncoded/sendFramed/sendChunked/etc. now
                                all take an explicit PeerAddress destination
                                parameter instead of reading a bridge-wide
                                field — host call sites pass
                                conn.peerAddress, joiner call sites pass
                                clientTargetPeer.
   - P2PSender.java / P2PReceiver.java — thin DatagramSocket wrappers, UNCHANGED
                            this session. Still share ONE socket (critical for
                            NAT punch to remain valid — see prior notes).
   - RawPacketListener.java — UNCHANGED.

   fabric-example-mod/src/main/java/net/peercraft/network/proxy/LocalProxy.java —
   UNCHANGED this session. Runs only on the joiner; one instance for the
   whole client lifetime, correctly reusable across sequential Join attempts
   to DIFFERENT rooms (verified by tracing, not by a new automated test —
   see a Q&A about this in the conversation history if this file is stale).

2) RENDEZVOUS + HOLE PUNCHING (protocol extended this session for room capacity):
   fabric-example-mod/src/main/java/net/peercraft/network/rendezvous/:
   - RendezvousProtocol.java — wire codec. REGISTER changed this session:
     was `[magic=0xE1][type]` (2 bytes, no payload); now
     `[magic=0xE1][type][maxPlayers:1][currentPlayerCount:1]` (4 bytes).
     This is a HARD wire-format break — both mod and rendezvous-server must
     be rebuilt and redeployed together (deliberate call, project isn't
     released widely, no version negotiation was added). New
     Register(int maxPlayers, int currentPlayerCount) record +
     decodeRegister(...). No new REASON_* wire constant was added — "room
     full" reuses the previously-dead REASON_ALREADY_CLAIMED(=2), whose
     existing Russian client-facing string ("комната уже занята") already
     reads correctly for this case.
   - RendezvousClient.java — REWORKED this session:
       * registerRoom(...) now takes (int maxPlayers, IntSupplier
         currentPlayerCountSupplier, RoomCallback, MatchCallback) instead of
         just (RoomCallback, MatchCallback). The keepalive loop re-encodes
         REGISTER fresh on every 15s tick using the supplier's CURRENT value
         — this is what makes the live player count actually live.
       * REAL BUG FOUND AND FIXED: host-mode match dedup used to be a single
         `Long lastMatchedToken` field — with only one joiner this was fine,
         but with two+ concurrent joiners, matching joiner B would overwrite
         the field, and a late retransmitted PEER_FOUND for joiner A would
         then incorrectly look "new" (fail to dedupe) and spawn a redundant
         punch attempt. Fixed: `Map<Address, Long> lastMatchedTokenByPeer`.
         A regression test for this now exists
         (RendezvousClientTest.matchesForDifferentPeersDoNotCrossDedupe).
   - PunchCoordinator.java — UNCHANGED this session (confirmed by design
     review that it was already safe to run several instances concurrently
     sharing one P2PSender — the ONLY thing making concurrent punches unsafe
     before was P2PBridge's single-slot bookkeeping, fixed above).

   rendezvous-server/src/main/java/net/peercraft/rendezvous/:
   - RendezvousServer.java — handleRegister now decodes the new payload and
     passes maxPlayers/currentPlayerCount into RoomRegistry.register(...).
     handleJoin is structurally UNCHANGED (a JOIN was already handled one
     joiner at a time; the single-joiner-per-room assumption lived entirely
     in RoomRegistry/Room, not here).
   - RoomRegistry.java — register(...) now takes maxPlayers/currentPlayerCount,
     clamps maxPlayers server-side to [1,32] independent of what the client
     sends (server never trusts the mod's own clamp). join(...) REWORKED:
     capacity is checked (room.currentPlayerCount >= room.maxPlayers) ONLY
     for a genuinely new joiner address — an address the room has seen
     before (reconnecting after the debounce window) is always let back in
     regardless of the reported count, since it isn't a new admission.
   - Room.java — REWORKED: the old single joinerAddress/token/claimed/
     lastMatchedAt fields are gone, replaced by
     `Map<Address, JoinerSlot> joiners` (one slot per distinct joiner) plus
     new `int maxPlayers` / `int currentPlayerCount` fields (self-reported
     by the host, see above — RoomRegistry is NOT the authority on who's
     actually connected, P2PBridge on the host is; RoomRegistry's check is
     advisory/first-line, saving a wasted punch attempt in the common case).

   Integration points on the client (fabric-example-mod):
   - P2PBridge.startHostViaRendezvous(mcPort, maxPlayers, HostListener) — the
     maxPlayers parameter is NEW this session (was previously implicit/absent
     — the method used to only take mcPort + listener).
   - ShareToLanScreenMixin.java / PeerCraftHostOptions.java / OpenToLanMixin.java
     — a CycleButton "Макс. игроков" (values 1..8) was added next to the
     existing "PeerCraft: через интернет" checkbox; its value is stored in
     PeerCraftHostOptions.maxPlayers (volatile int, mirrors the existing
     internetPlayRequested field's pattern) and threaded through to
     startHostViaRendezvous(...) in OpenToLanMixin.

BUGS FOUND AND FIXED (cumulative history, don't reintroduce)
------------------------------------------------------------------------
From earlier sessions (still relevant, unchanged code paths):
1. P2PSender/P2PReceiver used two different sockets — fatal for hole
   punching. Fixed by sharing one socket. (STILL the design — do not split
   them again.)
2. RendezvousClient's retry loop used to keep resending REGISTER for the
   full timeout window even after the relevant reply had arrived. Fixed:
   retry loop scoped to the exact state it started in. (This session's
   startRetryLoop rework — payload became a Supplier<byte[]> instead of a
   fixed byte[] — preserved this fix; re-verify if you touch it again.)
3. Host NAT mapping to the rendezvous server can close from inactivity while
   WAITING_FOR_PEER — fixed with a 15s keepalive. This session REUSED that
   exact keepalive tick to also carry the live player count (see above) —
   if you ever remove/slow down the keepalive, you'd also break the
   live-slot-freeing mechanism, not just the original NAT-mapping fix.
4. One real cross-network test hit a spurious INVALID_CODE — root cause
   NOT confirmed (see RendezvousServer's diagnostic describeAllRooms() log
   dump on that error path). Never recurred since. Still unconfirmed either
   way — watch for it if it happens again.

From THIS session (multi-player rooms):
5. The core pre-existing limitation this whole session addressed: P2PBridge
   had exactly one target-peer field, one HostConnection, one
   rendezvousListener slot for the ENTIRE bridge — a second real joiner
   would silently evict the first (new HostConnection replacing the old one
   under startNewHostConnection, second PunchCoordinator cancelling the
   first's punch). Comprehensively fixed — see ARCHITECTURE above.
6. RendezvousClient's host-mode match dedup (single lastMatchedToken field)
   was subtly wrong once two+ concurrent joiners were possible — fixed, see
   ARCHITECTURE above (item under RendezvousClient.java).
7. Latent (not previously flagged) admission gap: before this session's
   authorizedPeers gate, any UDP sender who guessed the host's relay port
   and sent a well-formed seq==0 frame could open a live TCP session to the
   host's own local Minecraft server, with no proof they'd ever punched or
   knew a room code. Closed as a side effect of adding multi-peer admission
   control, not the original goal, but worth knowing it's now closed.

KNOWN GAP, NOT YET FIXED (came up mid-session, low priority, flagged for
awareness): if a UDP port (hostUdpPort/clientUdpPort/proxyPort) is already
occupied when the mod tries to bind it, the mod does NOT crash — but it
fails SILENTLY at the socket layer (P2PReceiver.start() logs an ERROR and
returns false, but P2PBridge.restartReceiver(...) never checks that return
value, so P2PSender ends up wrapping a null socket and every subsequent
send is a silent no-op). The user only sees a generic, MISLEADING failure
10 seconds later ("сервер знакомств не ответил") that doesn't point at the
real (local, not remote) cause — the real cause is only in the log file.
Also: the two local IDE run configs for testing multiple joiners on ONE
machine (run-client/run-client2, see below) both default to the SAME
clientUdpPort (50002) unless one is given an explicit
-Dpeercraft.clientUdpPort override in its VM_PARAMETERS — this WILL collide
if you try to run both simultaneously without fixing that. Neither of these
was fixed this session (out of scope, flagged for the user, not yet
actioned as of this writing) — worth doing if a future session has time and
the user wants clearer diagnostics / an easier local 3-instance test setup.

WHAT'S DELIBERATELY OUT OF SCOPE (don't build unless asked)
------------------------------------------------------------------
- Mesh P2P between joiners — architecture stays a star: every joiner only
  ever talks to the host, never to each other. Explicitly confirmed still
  out of scope when this session's plan was designed.
- TURN/relay fallback when hole punching fails (unchanged from before —
  a home-hosted rendezvous server's uplink can't sustain relaying full game
  traffic for multiple pairs).
- Symmetric-NAT/CGNAT port prediction (unchanged).
- Accounts, persistent lobbies/friend lists, server browser (unchanged).
- Rendezvous protocol auth/encryption — still plaintext UDP.
- IPv6 (still untested, though the address encoding allows it).
- Extending the STATIC/local-test path (startHost()/startClient(),
  peerHost/peerPort config) to multiple peers — deliberately left
  single-peer, it's a dev-only loopback testing path, not the real feature.
  If someone ever wants multi-instance LOCAL (no rendezvous server) testing
  with more than 2 mod instances, that's a small separate follow-up, not
  done here.
- Wire-format backward compatibility for the REGISTER change above — no
  version negotiation was added; old and new REGISTER encodings are NOT
  interoperable. Deliberate, not an oversight (project isn't released
  widely yet, user controls both deploy targets).
