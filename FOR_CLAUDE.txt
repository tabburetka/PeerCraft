WHAT THIS PROJECT IS
---------------------
A Fabric Minecraft mod (early-stage alternative to Essential/LabyMod-style P2P
multiplayer) that lets several players connect directly to one host's world
without anyone running a real dedicated server or opening router ports. It
works by tunneling the raw Minecraft TCP protocol over a custom framed UDP
relay between mod instances, with real internet peers found via a small
rendezvous server + UDP hole punching. The host chooses a max-player count
when opening their world to the network; multiple joiners can be connected
to the same room concurrently, and a slot freed up by a leaving player
becomes available again within ~15 seconds.

On top of that P2P core, the rendezvous server now ALSO runs a full accounts
+ friends system (built this session — see "ACCOUNTS + FRIENDS SYSTEM"
below): players log in (via real Mojang licensing OR a plain nickname+
password "pirate" account), add each other as friends, and a friend who's
currently hosting shows up in your friends list with a "Подключиться"
button that joins their room directly — no room code ever typed or shared
out of band. This is the reason the rendezvous server, previously fully
stateless, now persists data to disk (accounts.json).

CURRENT STATUS: WORKING END TO END. The user tested the whole flow in a
real game today (register, friend code, presence, one-click connect) and
confirmed it works, modulo a few GUI layout bugs that are now fixed (see

DEPENDENCIES (rendezvous-server) — CHANGED THIS SESSION
------------------------------------------------------------------------
The server was 100% dependency-free before this session (stdlib only, plus
JUnit for tests). It now depends on Gson (accounts.json persistence). This
means the plain `jar` task alone would ship without its runtime dependency —
build.gradle's `jar` task was rewritten to bundle the runtime classpath by

it's incompatible with this Gradle version's `application` plugin (tries to
read a `mainClassName` property that no longer exists). Don't reintroduce it
without checking that's been fixed upstream first.

ACCOUNTS + FRIENDS SYSTEM (built this session, Фазы 0–6 of the plan)
------------------------------------------------------------------------
Full design rationale, alternatives considered, and phase-by-phase plan are
preserved at /home/ikuku/.claude/plans/vectorized-finding-ocean.md if you
need the "why", not just the "what" below. Short version of the identity
model: a player is EITHER a "licensed" account (real Mojang UUID, verified
via the same joinServer/hasJoined trick Essential uses — no full AES/RSA
login handshake needed, just a matching serverId string) OR an "unlicensed"
("pirate") account (nickname + password, server-generated UUID). Nicknames
are NOT unique — a 6-character "friend code" (same alphabet/generator as
room codes) is the real identifier, used both to add a friend directly and
to log in a pirate account from a new device (password login always goes
through the friend code, never a possibly-ambiguous nickname).

Protocol (AccountProtocol.java) — type-byte ranges:
  0x20-0x2B  Auth: licensed begin/serverId/confirm, register, password
             login begin/challenge/response, remembered (silent) relogin,
             AUTH_OK/AUTH_FAIL, rename/rename-ack.
  0x30-0x3B  Friends: code lookup, send/accept/decline/remove request,
             list incoming requests, list friends (carries live
             online/hosting status + room code), search/browse accounts.
  0x40-0x41  Presence: heartbeat, stop (fire-and-forget, no reply).
Passwords never cross the network in the clear: registration sends
client-computed salt+PBKDF2-hash (never the raw password); login is a
challenge-response (server sends a random challenge + the account's salt,
client answers HMAC-SHA256(rederived-hash, challenge)). PBKDF2/HMAC use only
javax.crypto (JDK-native) — duplicated as PasswordHasher.java (server,
package-private) and PasswordCrypto.java (mod, public); a pinned test
vector in both projects' test suites (PasswordHasherTest /
PasswordCryptoTest, "pinnedTestVectorMatchesModCopy"/"...ServerCopy") makes
sure the two copies can never silently drift out of parameter sync.

REGISTER (0x01, RendezvousProtocol) and JOIN (0x03) were BOTH extended with
optional account trailers, backward-compatible with their old anonymous
forms (decodeRegister/decodeJoin branch on payload length — old pin tests
for the short forms still pass unchanged):
  - A logged-in host's REGISTER carries accountId+sessionToken so the room
    shows up as "hosting" in friends' presence. The server independently
    re-derives the accountId from the sessionToken and only trusts it if it
    matches what was claimed — a REGISTER can never claim to be hosting as
    someone else's account.
  - A logged-in joiner's JOIN carries just their sessionToken (no claimed
    accountId at all — nothing to spoof); the server resolves it and
    forwards the joiner's real accountId to the HOST's copy of PEER_FOUND
    only (encodePeerFoundWithAccount) — the joiner's own copy of PEER_FOUND
    never gets this field, it doesn't need to know its own accountId.

Server-side (rendezvous-server/src/main/java/net/peercraft/rendezvous/):
  - account/Account.java — mutable record: id, displayName, licensed flag,
    friendCode, password salt/hash (null if licensed), rememberToken
    (rotated on every silent-relogin use), and mutual friends/
    outgoing/incoming-request sets. NOTE: these Set fields are NOT `final`
    — Gson deserializes via Unsafe field injection (no no-arg constructor),
    which bypasses `= ConcurrentHashMap.newKeySet()` field initializers
    entirely and hands back a non-concurrent Set. Account has
    normalizeCollectionsAfterDeserialization() (called from
    AccountStore.load()) specifically to fix this back — there's a
    regression test for it (AccountStoreTest.
    friendsSetSurvivesReloadAsAConcurrencySafeCollection) that verifies via
    concurrent mutation+iteration. If you add MORE mutable collection
    fields to Account, remember to add them to that normalize method too.
  - account/AccountStore.java — JSON persistence (Gson), atomic write
    (temp file + move), dirty-flag + periodic flush (see
    AccountService.maintenance(), called from the same 30s sweeper the
    original room-TTL sweep already used). save() catches RuntimeException
    too, not just IOException — this runs on a ScheduledExecutorService
    tick, which silently stops rescheduling FOREVER if a task ever throws
    uncaught, so a Gson hiccup must not permanently kill all future saves.
  - account/SessionRegistry.java, PendingAuthRegistry.java,
    PresenceRegistry.java — all TTL-based, in-memory only (not persisted —
    a server restart just makes every client silently relogin/reheartbeat).
    PresenceRegistry deliberately tracks TWO separate staleness clocks
    (lastSeenAt from the generic heartbeat, lastHostRegisterAt from the
    room-REGISTER keepalive specifically) — a single shared clock would let
    "hosting" status linger forever once a host closes their world but
    keeps playing (their generic heartbeat would keep refreshing it). See
    PresenceRegistryTest.hostingDecaysToOnlineAfterHostTtlEvenIfGeneric
    HeartbeatKeepsComing for the regression test.
  - account/MojangVerifier.java (interface) + HttpMojangVerifier.java (real,
    calls sessionserver.mojang.com) + FakeMojangVerifier.java (deterministic,
    for tests — enabled server-wide via -Dpeercraft.rendezvous.fakeMojang=true).
  - account/AccountService.java — the ONLY class RendezvousServer talks to
    in this package; wire-protocol concerns stay in RendezvousServer itself.
    Public entry point: `new AccountService(dataFile, fakeMojang, clock)`.
    Search results are sorted licensed-first (per spec) via two temp lists
    concatenated, capped at 20 total.
  - RendezvousServer.java — new -D flags read in main():
    peercraft.rendezvous.dataDir (default ./data),
    peercraft.rendezvous.fakeMojang (default false). New packet cases for
    every 0x20-0x41 type, all delegating straight to AccountService.

Client-side (fabric-example-mod):
  - network/account/AccountClient.java (src/main) — its OWN UDP socket and
    receive loop, deliberately independent of P2PBridge/P2PReceiver (needs
    to work from the title screen, and stay alive for the whole game
    session for the presence heartbeat, regardless of whether any P2P
    hosting/joining is active). Singleton `AccountClient.INSTANCE` for
    production, but the class itself is NOT a hard singleton — tests
    construct isolated `new AccountClient()` instances. One "pending
    request" slot with a generic retry-until-matching-reply-or-timeout
    mechanism (PendingRequest/ReplyHandler, private inner classes) used by
    every single request type. Presence heartbeat: fires once immediately
    on login success (works for every login path — they all funnel through
    one shared authOkOrFailHandler), then every 20s; stopped via
    ClientLifecycleEvents.CLIENT_STOPPING (PeerCraftClient.java) sending a
    best-effort TYPE_PRESENCE_STOP.
  - client/account/AccountStorage.java (src/client) — the mod's FIRST-EVER
    client-side disk persistence (config dir /peercraft/account.json, Gson,
    atomic write). Has a package-visible Path-explicit overload
    (load(Path)/save(Path,...)/clear(Path)) specifically so tests don't
    need a bootstrapped FabricLoader just to exercise the read/write logic
    — see AccountStorageTest. NOTE: build.gradle had to be told
    `sourceSets { test { compileClasspath/runtimeClasspath +=
    sourceSets.client.output } }` — Loom's splitEnvironmentSourceSets()
    doesn't wire that up by default, and without it tests can't even see
    client-package classes to compile against them.
  - client/account/AccountState.java, AccountSessionHolder.java — thin
    persistence-layer records/wrapper around AccountClient's session.
  - GUI (client/gui/): PeerCraftAccountScreen (hub — login/register/login-
    by-code when logged out; identity+logout+rename+"Друзья" when logged
    in), PeerCraftRegisterScreen, PeerCraftLoginByCodeScreen,
    PeerCraftRenameScreen, PeerCraftFriendsScreen (polls listFriends every
    ~5s via Screen.tick() while open; "Подключиться" reuses the EXISTING
    P2PBridge.startClientViaRendezvous(...) — the join side needed zero
    changes, only the friends screen needed to supply the room code instead
    of a human typing it), PeerCraftFriendRequestsScreen,
    PeerCraftSearchScreen. All of these are a plain stacked list of buttons,
    capped at 8 rows shown, NO scrolling — deliberately skipped
    ObjectSelectionList's more involved API since a hobby project's
    friend/request/search lists realistically fit. TitleScreenMixin gained
    a second "PeerCraft: Аккаунт" button (shown in every non-disabled mode,
    including host mode — unlike "PeerCraft: Join").
  - P2PBridge.java / RendezvousClient.java integration: registerRoom(...)
    and joinRoom(...) both gained an account-aware overload alongside the
    original anonymous one; P2PBridge reads AccountClient.INSTANCE.
    getCurrentSession() itself (callers' public method signatures didn't
    need to change).

Фаза 5 — save-data isolation (host-side identity injection):
The underlying bug this closes: the host's IntegratedServer runs with
setUsesAuthentication(false) whenever "разрешить нелицензионных игроков" is
on (see Фаза 6 below), and VANILLA in that mode assigns every joiner a UUID
derived PURELY from their nickname (UUIDUtil.createOfflineProfile — see
ServerLoginPacketListenerImpl.handleHello, confirmed by decompiling the
real Minecraft source via `./gradlew genCommonSources`, NOT guessed). Two
joiners sharing a nickname would silently collide into the exact same
playerdata file. Mechanism (all Фаза 5, this session):
  - network/p2p/PlayerIdentityRegistry.java — maps a HostConnection's local
    TCP port to the joiner's accountId. Works because on loopback, a
    socket's own local port IS the remote port the OTHER end (the
    IntegratedServer accepting the connection) sees — P2PBridge.
    startNewHostConnection() populates this right after opening the
    per-joiner Socket, using P2PBridge.joinerAccountIdByAddress (populated
    in beginHostPunch from RendezvousClient.accountIdForPeer(peer), itself
    populated from the account-carrying PEER_FOUND — see the JOIN/
    PEER_FOUND extension above).
  - client/mixin/ServerLoginPacketListenerImplMixin.java — @Redirect on the
    UUIDUtil.createOfflineProfile(username) call inside handleHello. Looks
    up PlayerIdentityRegistry by the connection's remote port; if found,
    returns `new GameProfile(accountId, username)` instead. Deliberately
    does NOT need its own "is authentication off" check — that call site in
    vanilla is ALREADY only reached when authentication is off in the first
    place, so the redirect is naturally a no-op whenever a host requires
    licensed players (see Фаза 6). NOT YET VERIFIED IN A REAL GAME — see
    "CURRENT STATUS" above; compiles, packages into the jar, and the
    surrounding wire mechanism is fully unit/integration-tested, but the
    Mixin itself needs an actual two-joiners-same-nickname session to
    confirm it fires correctly.

Фаза 6 — "разрешить нелицензионных игроков" host toggle:
PeerCraftHostOptions.allowUnlicensedPlayers (default true, preserves old
behavior). OpenToLanMixin now calls setUsesAuthentication(false) only when
true; when false, it explicitly calls setUsesAuthentication(true) (though
this was confirmed via decompiled source to already be vanilla's own
default at world-start time — IntegratedServer.initServer() calls
setUsesAuthentication(true) unconditionally, publishServer() never touches
it, so PeerCraft's mixin used to be the ONLY thing turning it off). When
off, the real Mojang encrypted handshake runs end-to-end through
P2PBridge's UDP relay completely untouched by PeerCraft code — the relay is
byte-transparent, it doesn't care whether the payload is encrypted.
ShareToLanScreenMixin's new checkbox for this is hidden (not just
disabled) whenever "PeerCraft: через интернет" is off — see BUGS FOUND AND
FIXED #13 for the layout history here.

CONFIG — all via -Dpeercraft.<key> or PEERCRAFT_<KEY> env (mod) or plain
-D flags (server, see above), same convention throughout:
  mode, proxyPort, clientUdpPort, hostUdpPort, peerHost, peerPort   (original, local path)

BUGS FOUND AND FIXED (cumulative history, don't reintroduce)
------------------------------------------------------------------------
From earlier sessions (still relevant, unchanged code paths):
1. P2PSender/P2PReceiver used two different sockets — fatal for hole
   punching. Fixed by sharing one socket. (STILL the design.)
2. RendezvousClient's retry loop used to keep resending REGISTER for the
   full timeout window even after the relevant reply had arrived. Fixed:
   retry loop scoped to the exact state it started in.
3. Host NAT mapping to the rendezvous server can close from inactivity while
   WAITING_FOR_PEER — fixed with a 15s keepalive, which also carries the
   live player count (see below) and, THIS session, the account trailer.
4. One real cross-network test hit a spurious INVALID_CODE — root cause
   still unconfirmed. Never recurred since.
5-7. Multi-player-rooms session (see git history if you need the details):
   P2PBridge single-slot bookkeeping generalized to per-joiner maps,
   host-mode match dedup fixed to be per-peer, and a latent
   guess-the-port admission gap closed via authorizedPeers.

From THIS session (accounts + friends):
8. LOGIN_CHALLENGE originally didn't include the account's salt — without
   it a client logging in from a NEW device (the whole point of
   friend-code login) couldn't rederive the password hash to answer the
   challenge at all. Caught and fixed during protocol design, before any
   client code was written against the broken version.
9. Account's mutable friend/request Set fields silently lost their
   ConcurrentHashMap-backed thread safety after a Gson reload (Unsafe field
   injection bypasses field initializers) — see the detailed note under
   "account/Account.java" above. Would have caused a
   ConcurrentModificationException in the background save-sweeper thread
   the first time a friend list was mutated concurrently with a save, which
   (per bug philosophy below) would have PERMANENTLY silently killed all
   future account persistence for that server run.
10. rendezvous-server's `jar` task shipped without its new Gson runtime
    dependency until build.gradle was fixed to bundle the runtime classpath
    by hand (see "DEPENDENCIES" above) — would have crashed with
    NoClassDefFoundError the moment any account code path actually ran
    on a freshly deployed server.
11. The `com.gradleup.shadow` plugin (tried as the "normal" way to build a
    fat jar) is incompatible with this project's Gradle version's
    `application` plugin — reverted in favor of a hand-written `from {
    ...zipTree... }` block in the `jar` task itself. Don't re-add it
    without confirming upstream compatibility first.
12. (Found by the user testing in-game, fixed same session) PeerCraft
    RegisterScreen's "Продолжить" button was positioned directly on top of
    the freshly-created friend code text — moved below all the success-view
    text lines.
13. (Found by the user testing in-game, fixed same session)
    ShareToLanScreenMixin's new "Разрешить нелицензионных игроков" checkbox
    overlapped vanilla's own "Start LAN World"/"Cancel" button row (which
    sits at height-28 — confirmed via decompiling the real
    ShareToLanScreen.java, not guessed). Whole PeerCraft settings block on
    that screen was moved higher and switched from a 1-row side-by-side
    layout to a 3-row vertical stack; "Макс. игроков" and "Разрешить
    нелицензионных игроков" are now also hidden entirely (via each
    widget's public `.visible` field, toggled live from the "через
    интернет" checkbox's callback) whenever "PeerCraft: через интернет" is
    off, since neither setting means anything without it.

KNOWN GAPS, NOT YET FIXED
------------------------------------------------------------------------
- If a UDP port (hostUdpPort/clientUdpPort/proxyPort) is already occupied,
  the mod fails silently at the socket layer with a misleading downstream
  error message. Unchanged, low priority, flagged multiple sessions running.
- run-client/run-client2 IDE configs still default to the same
  clientUdpPort unless manually overridden. Unchanged.
- Session-token/remember-token replay risk over plaintext UDP: mitigated by
  rotating rememberToken on every silent-relogin use, but a passive local-
  network sniffer could still replay a session token until it naturally
  expires (30 min TTL). No transport encryption was added this session
  (would need an ECDH+AES layer just for the account channel — scoped out,
  see the plan doc's risk list if you want to pick this up).
- Фаза 5's Mixin is unverified in a real game (see "CURRENT STATUS").
- No moderation/ban system, no nickname content filtering.
- Accounts.json makes the rendezvous server stateful for the first time —
  it used to be trivially redeployable/restartable with zero consequence;
  now a wiped data dir loses every account. No backup story exists yet
  (deployment concern, not code — flagged for the user).

WHAT'S DELIBERATELY OUT OF SCOPE (don't build unless asked)
------------------------------------------------------------------
- Mesh P2P between joiners — architecture stays a star.
- TURN/relay fallback when hole punching fails.
- Symmetric-NAT/CGNAT port prediction.
- Full transport encryption for the rendezvous/account UDP channel — still
  plaintext UDP overall; only passwords specifically are protected via
  challenge-response (see "ACCOUNTS + FRIENDS SYSTEM" above). This is a
  known, accepted gap, not an oversight — see "KNOWN GAPS".
- IPv6 (still untested, though the address encoding allows it).
- Extending the STATIC/local-test path (startHost()/startClient()) to
  multiple peers — dev-only loopback path, not the real feature.
- Server browser / public room listing.
- Moderation, bans, nickname content filtering.
- Account recovery for a lost pirate-account friend code — there's no
  password-reset/email flow, and this is a deliberate, accepted trade-off
  (see the plan doc), not a gap to fill silently.
