# ТЗ: дополнительные точки отказа handoff

Срез: 2026-09-27, HEAD `ac530590` и рабочее дерево. Проверены исходники, связи между компонентами и тестовые заглушки. Это статический аудит: новые игровые воспроизведения и нагрузочные тесты в рамках этого аудита не запускались. Номера строк ниже относятся к этому срезу; искать прежде всего по классу и методу.

## Как выполнять задания

Задачи ниже предназначены для последовательного выполнения. Для каждой: сначала воспроизвести проблему тестом, затем изменить минимальный набор исходников, выполнить соответствующие тесты и обновить отчёт `handoff-implementation-status.md`. Не объявлять весь handoff готовым по результатам отдельной задачи.

Исходники общего протокола: `peercraft/src/main/java/net/peercraft/network/handoff/`. Сервер: `rendezvous-server/src/main/java/net/peercraft/rendezvous/`. Игровые адаптеры: `peercraft/src/main/java/net/peercraft/client/` и `peercraft/src/client-{1165,1122,1710}/java/net/peercraft/client/`. У P2PBridge есть реальные Java-8-копии в Forge-проектах — находить их вне build. Не редактировать `build/shared-*`, не перезаписывать изменения других агентов, не включать сборочные файлы в коммит.

P0 — блокирует безопасное включение нового сценария. P1 — обязательное исправление устойчивости/данных. P2 — масштабирование и эксплуатация. «Подтверждено» ниже означает вывод из текущего кода, а не воспроизведение в Minecraft.

## H01 — разделить право запуска и актуальность результата [P0]

**Подтверждено.** `HandoffRegistry.result()` (строка 134) выставляет `ownsCurrentEpoch` только если ключ запроса совпадает с текущим владельцем. После COMMIT это ключ преемника. `HandoffSourceFlow.run()` (126, 135, 140) и `HandoffObserverFlow.run()` (58) требуют этот же флаг для READY. Старый хост и наблюдатель закономерно получают false и отвергают успешную передачу. Наблюдатель также отвергает RECOVERED исходного хоста после ABORT.

**Почему тесты пропустили:** `HandoffSourceFlowTest` и `HandoffObserverFlowTest` безусловно возвращают `ownsCurrentEpoch=true`, не моделируя реальные ключи ролей.

**Сделать:**

1. Сохранить строгую семантику `ownsCurrentEpoch`: только владелец может запускать/устанавливать мир.
2. Добавить отдельный признак актуальности результата попытки, например `isCurrentAttempt`: совпадают session/offer/epoch с текущей записью. Он доступен авторизованным читателям независимо от права запуска.
3. Источник и наблюдатели проверяют актуальность попытки, epoch и READY/RECOVERED; преемник дополнительно проверяет владение. Одного равенства epoch недостаточно: новая попытка после ABORT может иметь тот же epoch и другой offerId.
4. Обновить обе копии authority codec и согласование возможностей/версии. Не менять смысл существующего флага и не выдавать ключ преемника наблюдателям.
5. Добавить контрактный тест через настоящий HandoffRegistry и настоящий codec, с тремя различными ключами; использовать мост test fixture между модулями, а не копию логики registry.

**Приёмка:** после COMMIT/INSTALLED/READY источник получает READY, наблюдатель переподключается, но обоим запрещён `requireCommitted()`. После ABORT/RECOVERED наблюдатель возвращается к источнику. Исторические READY и ABORT после новой попытки отвергаются, включая одинаковый epoch при разных offerId. Чужой ключ получает DENIED.

## H02 — ошибка сохранения COMMIT портит epoch в памяти [P1]

**Подтверждено.** `HandoffOperation.record()` присваивает `journal.epoch = result.epoch` до `journal.advance(COMMITTED)`. При IOException `HandoffJournal.advance()` откатывает только phase. Получается COMMIT_SENT с уже новым epoch. Следующий QUERY возвращает тот же правильный COMMIT, но проверка требует ещё `epoch + 1` и отвергает его.

**Сделать:**

1. Обновлять phase/epoch/digest как единое состояние: подготовить следующую запись, сохранить её, затем публиковать в памяти. Если оставляется mutable-реализация, корректно восстанавливать все изменённые поля при ошибке.
2. Отдельно обработать ошибку после успешного atomic move, но до подтверждения durability: перечитать/повторно синхронизировать журнал и свериться с authority. Ошибка локальной записи не означает ABORT.
3. Ввести небольшой injectable writer/fault hook для тестирования каждой точки отказа, без глобальных флагов в production.

**Приёмка:** ошибка до rename и после rename; повтор QUERY без перезапуска и после перезапуска. В обоих случаях тот же подтверждённый COMMIT принимается, epoch не увеличивается повторно, запуск до устойчивого разрешения запрещён, файлы не удаляются.

## H03 — отмена во время старта может закончиться READY [P1]

**Подтверждено.** `HandoffSuccessorFlow.cancel()` меняет флаг. При `await(startAndRegister(), ..., false)` флаг не проверяется; после завершения future сразу вызывается `operation.ready()`. Проверка перед запуском не закрывает отмену, произошедшую во время запуска.

**Сделать:**

1. Разделить отмену права передачи и локальную отмену запуска. После COMMIT не посылать ABORT для возврата права источнику.
2. На cancel во время запуска закрывать launch guard, запрещать новые open/publish/READY и запрашивать остановку уже начатого сервера.
3. Сериализовать решение READY против cancel через единый терминальный gate. Проверки boolean перед действиями недостаточно для гонки между потоками.
4. Дождаться остановки фактически начатого серверного потока; при таймауте показать отдельную ошибку остановки и продолжать запрещать новые запуски этой попытки. Сохранить принятый мир.

**Приёмка:** управляемый future старта; вызвать cancel, затем завершить его успешной регистрацией. READY не уходит, stop вызывается, исходный хост не восстанавливается. Отдельный тест гонки cancel/registration: один терминальный исход. Повторный cancel идемпотентен.

## H04 — ожидание launcher может принять другой встроенный сервер [P1]

**Подтверждён пробел проверки; игровое воспроизведение требуется.** Modern `SuccessorLauncher.openThenPublish()` (313+) ищет любой `getSingleplayerServer()` с `isRunning()` и ненулевым `mc.player`. Проверки каталога и принадлежности попытке нет. Отложенный vanilla-диалог загрузки может пережить смену экрана; launch guard сам по себе не отменяет его внутренние callbacks.

**Сделать:**

1. Создать контекст запуска с attempt ID, каноническим путём принятого мира и ожидаемым экземпляром сервера. Связать его с реальным событием создания сервера.
2. До публикации на render thread заново проверить guard, экземпляр и путь. Чужой уже открытый сервер не публиковать и не останавливать как сервер этой попытки.
3. В точках продолжения vanilla-подтверждений загрузки проверять контекст; позднее продолжение отменённой попытки не должно создавать сервер. Если создание уже началось — остановить именно этот экземпляр.
4. Реализовать во всех четырёх адаптерах с учётом их API, не полагаться только на проверку наличия игрока.

**Приёмка:** задержать диалог мира A, отменить handoff, открыть мир B, затем разрешить старый callback A. B не публикуется/не останавливается; A не остаётся симулировать. Дополнительно два последовательных handoff с поздним callback первой попытки.

## H05 — UNKNOWN завершает flow без остановки его работников [P1]

**Подтверждено на уровне контракта flow.** В Source/Successor есть `finish(UNKNOWN); return` без `stopAttemptWorkers()`. У `Steps.terminal()` нет обязанности закрывать работников. Если сетевой результат неизвестен, архивирование/приём или поздние callbacks могут продолжиться после экрана ошибки.

**Сделать:**

1. Выделить обязательную идемпотентную процедуру завершения attempt workers/дескрипторов и отложенных действий для каждого терминального пути, включая UNKNOWN и исключение во время остановки сервера.
2. Отделить остановку работников от удаления данных. При UNKNOWN сохранять журнал, архив и staging; не выполнять cleanupConfirmedAbort и не восстанавливать исходный сервер.
3. Если для дальнейшего QUERY сохраняется минимальный authority-канал, оформить его отдельным владельцем ресурсов; он не должен продолжать передачу/запуск.
4. Ошибки остановки ресурсов не скрывать за сообщением об успешной очистке.

**Приёмка:** fake worker продолжает писать и ставит callback после UNKNOWN. После завершения flow новых записей/запусков нет, дескрипторы закрыты, файлы сохранены. Дублированный terminal не вызывает повторную очистку. Проверить обе стороны.

## H06 — цель возврата может быть открыта другим процессом [P1]

**Подтверждён пробел.** `WorldTargetPlan.revalidate()` проверяет fileKey/level.dat, но не владение Minecraft session lock. Затем выполняется сетевой `requireCommitted()`, расширяющий интервал до rename. `WorldInstall.replace/recover()` также не проверяют активное использование целевого мира. Другой процесс может продолжать писать регионы в переименованный каталог; неизменный level.dat этого не исключает.

**Сделать:**

1. Ввести placement lease для канонического целевого пути: межпроцессная блокировка операций PeerCraft плюс проверка/получение Minecraft world lock согласно реальному адаптеру версии.
2. Получать блокировку перед окончательной revalidate и удерживать на протяжении замены/восстановления. Учитывать Windows: открытый lock-файл может мешать rename. Не использовать удаление session.lock как способ «освободить» занятый мир.
3. Для legacy проверить реальную семантику session.lock: один `FileChannel.tryLock()` не защищает от процесса Minecraft, который не участвует в такой блокировке. Если эксклюзивность не доказуема, отказаться от замены и предложить новый каталог до COMMIT.
4. Повторно проверить путь непосредственно перед изменением файлов. После COMMIT при занятой цели сохранить staging и предложить восстановление/размещение в безопасную новую папку; не возвращать право источнику.

**Приёмка:** отдельный процесс удерживает lock; второй handoff выбирает ту же цель; мир открывается между preflight и install. Ни один тест не переименовывает/удаляет занятый мир. Для каждого адаптера задокументировать, что именно обеспечивает эксклюзивность; провести игровой тест, а не только искусственный FileLock-тест.

## H07 — создание backup-маркера происходит после завершения транзакции [P1]

**Подтверждено.** `WorldTargetPlan.install()` сначала вызывает WorldInstall.replace(), который завершает замену и удаляет `.install` журнал; затем пишет `.peercraft-backup` через CREATE_NEW. Ошибка этой записи объявляет install неуспешным при уже установленном новом мире. Если выбранная старая копия уже содержит marker, запись гарантированно падает. Startup recover не создаёт этот marker вообще.

**Сделать:**

1. Перенести создание/проверку backup marker внутрь журналируемого WorldInstall recovery до удаления install-журнала.
2. Сделать операцию идемпотентной: уже существующий корректный marker допустим; некорректный/ссылка — диагностируемая ошибка без удаления копий.
3. Синхронизировать marker и каталог перед завершением транзакции. Одинаковое поведение при обычной установке и startup recovery.
4. Удалить внешнюю запись из WorldTargetPlan. Не лечить это простым проглатыванием IOException.

**Приёмка:** сбой до/после записи marker, повтор recover, старый marker, произвольное имя backup через overload selected(). После восстановления одна установленная новая копия, backup исключён из автопоиска, журнал удалён только после завершения обязательных действий.

## H08 — игроки за одним NAT исчерпывают лимит authority [P1]

**Подтверждено.** `RendezvousServer.handle()` (144) использует общий `roomListRateLimiter` для всего E6; он ограничен 120 запросами/минуту на IP и также обслуживает список комнат/lookup. Observer опрашивает раз в 3 секунды, преемник в ожидании COMMIT — раз в секунду. Шесть наблюдателей уже расходуют весь лимит; преемник, retries и список комнат превышают его. Потерянные ответы порождают до 10 повторов RPC и ухудшают ситуацию.

**Сделать:**

1. Разделить бюджеты room list, неизвестных/неавторизованных запросов и подтверждённых handoff-операций.
2. Сохранить общий ограничитель входного трафика до дорогого I/O. Для валидных операций добавить справедливые ограниченные очереди/квоты по сессии и участнику; не создавать неограниченную карту на каждый присланный UUID.
3. Предусмотреть бюджет COMMIT/ABORT/QUERY, не расходуемый целиком наблюдателями. Учитывать дубликаты и несколько участников за NAT.
4. Согласовать poll/retry backoff с серверным бюджетом; добавить jitter и ограничение суммарного deadline. Если вводится BUSY/retry-after, обновить обе копии codec и обработчики.

**Приёмка:** 10 наблюдателей, источник и преемник с одного IP, одновременный room list, потери/дубликаты. Валидный COMMIT/ABORT имеет конечный подтверждённый результат в пределах deadline. Отдельная флудящая сессия не вытесняет остальные; память/очереди ограничены. Тест с виртуальным временем, без минутных sleep.

## H09 — брошенные PENDING/STAGED навсегда занимают активные слоты [P1]

**Подтверждено.** Registry ограничен 1000 active; maintenance истекает только COMMITTED/ROOM_READY/ABORTED. Если оба приложения исчезли без ABORT, PENDING/STAGED остаются активными после перезапуска. Со временем новые попытки блокируются. Это дефицит доступных слотов, даже при ограниченной RAM.

**Сделать:**

1. Добавить сохраняемый срок действия незавершённой попытки, согласованный с полным допустимым временем подготовки, передачи и проверки. Не применять короткий timeout комнаты к часовому переносу.
2. Если нужны продления, принимать их только с полномочиями попытки и ограничивать абсолютную длительность; обычный QUERY не должен бесконечно продлевать запись.
3. Истечение оформлять устойчивым ABORT через ту же сериализацию, что COMMIT. После подтверждённой записи ABORT освобождать active/activeRooms. Простое удаление записи запрещено.
4. COMMIT и expiry должны иметь единственный исход; committed-сессии не отменять по этому дедлайну. Клиент по локальному таймеру не получает право запуска или очистки.
5. При запуске registry обрабатывать истёкшие записи до проверки лимита admission; учитывать перевод часов назад/вперёд и тестировать выбранную политику.

**Приёмка:** заполнить лимит брошенными попытками, истечь срок, перезапустить сервер — новые операции принимаются; старые QUERY показывают ABORT в пределах retention. Гонка expiry/COMMIT даёт один устойчивый результат. Длительная разрешённая передача не обрывается раньше срока.

## H10 — полная maintenance блокирует единственную очередь authority [P2]

**Подтверждено; величина задержки требует измерения.** `maintenance()` сканирует все `.history` и `.json` под synchronized, работает в том же единственном handoffIo worker, что COMMIT/QUERY. `read()` делает directory fsync для каждой записи. Состояние owner/epoch сохраняется по каждой сессии бессрочно, поэтому число `.json` растёт независимо от лимита RAM. Первый sweep только через сутки после старта; одна повреждённая запись прерывает проход. Конструктор тоже читает все записи, и ошибка одной может помешать запуску rendezvous.

**Сделать:**

1. Выполнять очистку небольшими порциями с ограничением записей/времени за один заход; между порциями обслуживать authority. Не запускать второй несогласованный writer.
2. Сохранить durability COMMIT; не удалять fsync «для ускорения» без обоснованной транзакционной замены. Проверку неизвестного результата после сбоя rename/fsync сохранить.
3. Отдельно индексировать активные записи и минимальное состояние владельцев; исторические данные читать по запросу. Не загружать всю историю в RAM и не забывать владельца ради лимита.
4. Ошибка одного журнала должна блокировать эту сессию и сохранять файл для диагностики, а не молча обнулять epoch. Разработать изоляцию ошибки от остальных комнат.
5. Добавить метрики: глубина очереди, возраст запросов, длительность flush/maintenance, active, объём истории, число повреждённых записей. Секреты в логи не писать.

**Приёмка:** на 100 000 завершённых записей запросы других сессий обслуживаются между порциями; тест доказывает отсутствие монопольного полного прохода. Зафиксировать реальные p95/p99 и размер RAM на стенде, без выдуманного универсального SLA. Повреждённая запись не разрешает запуск своей сессии и не ломает независимые. Перезапуск до первых суток не отменяет retention-политику.

## H11 — подключить реальные компоненты, прежде чем объявлять безопасность [P0, известный незакрытый этап]

Это не новая находка: подтверждён ранее описанный разрыв. `HostHandoffTransfer` вызывает `WorldArchiver.archive(server, tmpDir)` для живого сервера; основной coordinator использует v1 и ранний MIGRATE. Новые Flow/Operation/Transport не обеспечивают безопасность, пока игровой путь их не вызывает. Этот этап выполнять после H01–H09; H10 можно завершать отдельно до эксплуатации под нагрузкой.

**Разбить на отдельные проверяемые изменения:**

1. Реальный session context и авторизованные участники; capabilities rendezvous/всех игроков; отдельный handoff transport. До полной сборки сценария SAFE_HANDOFF оставлять выключенным.
2. Preflight манифеста/места/цели до PREPARE. Закрыть новые входы, в том числе прямой путь к встроенному серверу, а не только список комнаты rendezvous. Подключить реальные адаптеры, завершить nested-моды Forge/NeoForge.
3. Захват пути/UUID → saveAndStop → фактический join серверного потока → archiveClosed → проверенный staging. Ни одного обращения с save-задачей к остановленному серверу.
4. Durable COMMIT → install → конкретный launch → регистрация комнаты → READY. Source/Successor/Observer должны работать с одним реальным протоколом, а не с разнотолкующими флаги заглушками.
5. Startup recovery сетевого журнала: сохранять роль, endpoint authority, session/offer, полномочия, digest, пути, политику backup и необходимые параметры восстановления; версионировать формат. Не выводить разрешение из локального JSON предупреждения или одного `.install` журнала. UNKNOWN сохраняет данные и блокирует автоматический запуск только затронутой операции.
6. Подключить отмену/восстановление источника до COMMIT; после COMMIT — остановку неуспешного преемника без возврата права. Отметку устаревшей копии восстанавливать по подтверждённому COMMIT.

**Приёмка:** один интеграционный стенд с настоящими registry, codec и тремя ролями, потерями/повторами/перестановкой и перезапуском authority. Затем Minecraft: три участника, передача и возврат, modern Fabric/NeoForge, 1.16.5, 1.12.2, 1.7.10. Отдельно доказать применение Mixin и остановку серверного потока. Сборка и unit-тесты не заменяют эти проверки.

## Рекомендуемый порядок и отчёт исполнителя

Порядок: H01 → H02 → H03/H04/H05 → H06/H07 → H08/H09 → H11; H10 завершить до масштабного использования. Косая черта обозначает группу, а не разрешение одновременно менять общие файлы несколькими агентами.

Каждую задачу сдавать отдельно: исходный падающий тест/сценарий, изменённые файлы, точная команда проверки и результат, что проверено в игре, оставшиеся ограничения. Не менять критерии приёмки ради зелёного теста. Не исправлять H01 выдачей всем роли владельца; H06 — удалением lock; H09/H10 — удалением неизвестных попыток/состояния владельца; UNKNOWN — автоматическим откатом или удалением staging.

Существующие исправления полноты world-local архива и UUID не переписывать. Архив должен продолжать сохранять данные расширений; новые исключения допускаются только для конкретных внутренних служебных файлов.
