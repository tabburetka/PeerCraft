# План: самообновление PeerCraft по клику на табличку

## Цель
Сейчас табличка в главном меню только сообщает о новой версии и ведёт на CurseForge.
Нужно, чтобы клик по ней предлагал «Обновить»: мод скачивает подходящий jar, проверяет его
и ставит замену, а та применяется после выхода из игры. Ссылка на страницу остаётся
запасным вариантом.

## Ключевые решения

### 1. Откуда скачивать: CDN CurseForge
- В `releases/<версия>/curseforge-uploads.json` уже лежат имена файлов, их sha256 и
  CurseForge file id для каждой сборки.
- Прямая ссылка на файл строится без API-ключа:
  `https://mediafilez.forgecdn.net/files/<id / 1000>/<id % 1000>/<имя файла>`
  (вторая часть пишется без ведущих нулей).
- Плюсы:
  - игрок получает ровно тот файл, что прошёл модерацию CurseForge;
  - CurseForge App узнаёт новый jar по отпечатку как официальный файл проекта и не считает
    его «чужим».
- Минус: файл появляется на CDN только после ручного одобрения. Поэтому подписанный
  `update.json` публикуется **после** одобрения, и скрипт сам проверяет, что все ссылки
  отвечают 200.

### 2. Безопасность: подпись манифеста
- Без подписи взлом GitHub-аккаунта позволил бы разослать вредоносный jar всем игрокам.
- Подписываем `update.json` целиком. Отдельный файл подписи `update.json.sig` содержит
  base64 подписи над точными байтами файла.
- Алгоритм — **ECDSA P-256 (`SHA256withECDSA`)**, а не Ed25519: Ed25519 нет в Java 8, на
  которой работают 1.7.10, 1.12.2 и 1.16.5. ECDSA там есть «из коробки» (SunEC).
- Открытый ключ зашит в мод. Закрытый хранится только у тебя, вне репозитория
  (например, `~/.config/peercraft/release-key.pem`).
- Внутри подписанного манифеста у каждого файла есть sha512 и размер. Скачанный jar
  проверяется по ним до того, как попадёт в план установки.
- Нет подписи или она неверная → самообновление отключено, остаётся только табличка
  со ссылкой (как сейчас).

### 3. Установка: существующий механизм Mod Sync
- `ModSyncInstaller` (helper) уже умеет: подготовить транзакцию, дождаться выхода из игры,
  заменить jar с бэкапом и откатить при сбое.
- `ModSyncPendingInstaller.arm(...)` запускает helper, пока игра держит блокировку.
- Самообновление — это одна запись `ModSyncInstaller.Entry`:
  - `id = "peercraft"`, новая версия, имя и sha512 нового файла;
  - `oldFileName`, `oldVersion`, `oldSha512` — текущего jar;
  - `source = "self-update"`.
- Helper перед запуском копируется в каталог транзакции (`launch()`), поэтому замена
  собственного jar ему не мешает.

## Формат `update.json` (v2, совместим с уже вышедшими клиентами)
```json
{
  "format": 2,
  "stable": "3.5.0",
  "beta": "3.5.0",
  "url": "https://www.curseforge.com/minecraft/mc-mods/peercraft/files/all",
  "files": {
    "3.5.0": {
      "fabric-1.21.1":  {"file": "peercraft-fabric-1.21.1-3.5.0.jar", "cf": 9500001,
                          "url": "https://mediafilez.forgecdn.net/files/9500/1/peercraft-fabric-1.21.1-3.5.0.jar",
                          "sha512": "…", "size": 977083},
      "forge-1.12.2":   {"…": "…"}
    }
  }
}
```
- Ключ сборки: `<loader>-<minecraft>`, где loader — это `LoaderTag.current()` (fabric,
  neoforge, forge), а minecraft — версия из `InstalledModScanner` (id `minecraft`).
- Нет файла для своей сборки (например, релиз не выпускался для этой версии игры) → только
  табличка со ссылкой.
- Клиенты 3.4.x/3.5.x без самообновления новые поля просто игнорируют.

## Этапы

### Этап 1. Инструмент релиза: `tools/release/make-update-manifest.py`
1. Читает `releases/<версия>/manifest.json` и `curseforge-uploads.json`.
2. Сверяет sha256, считает sha512 и размер локальных jar.
3. Строит ссылки на CDN и проверяет каждую запросом HEAD: 200 и совпадающий размер.
   Не прошло → ошибка «файлы ещё на модерации».
4. Пишет `update.json` (канал `stable` или `beta` по `releaseType`) и подписывает его в
   `update.json.sig`. Используется библиотека `cryptography`, путь к ключу задаётся через
   `--key`.
5. Отдельная команда `keygen` один раз создаёт пару ключей и печатает открытый ключ для
   вставки в мод.

Шаг 6 в «Порядке выпуска» в `VERSIONING.md` заменяется на «запустить скрипт и запушить
`update.json` и `update.json.sig`».

### Этап 2. Общий код (Java 8, `peercraft/src/main/java/net/peercraft/client/update/`)
- **`UpdateManifest`**:
  - разбирает v2: каналы и файлы;
  - `fileFor(version, buildKey)`;
  - проверяет каждую ссылку: только `https://mediafilez.forgecdn.net/` или
    `https://edge.forgecdn.net/`, а имя файла совпадает с последним сегментом URL.
- **`UpdateSignature`**:
  - `verify(bytes, sigBase64)` через `Signature.getInstance("SHA256withECDSA")` и
    зашитый `PUBLIC_KEY` (X.509 DER в base64);
  - тестовый ключ берётся из `-Dpeercraft.updateCheck.publicKey` только при
    переопределённом `updateCheck.url` (для локальной проверки).
- **`UpdateChecker`**:
  - скачивает `update.json` и `.sig`;
  - в `UpdateInfo` добавляется необязательное поле `ManifestFile file` — оно заполняется
    только при верной подписи и найденной сборке;
  - добавляется `canSelfUpdate()`.
- **`SelfUpdateInstaller`**:
  - Предусловия:
    - текущий jar PeerCraft — обычный файл прямо в `getModsDir()`: не dev-окружение,
      не вложенный, не symlink;
    - нет ожидающей транзакции Mod Sync (`ModSyncPendingInstaller.hasPending()`);
    - helper есть в ресурсах.
  - Загрузка:
    - `HttpsURLConnection` с ручными редиректами, только по хостам forgecdn;
    - таймауты 15 с, общий дедлайн 5 минут, лимит размера `size` + 0;
    - прогресс в `AtomicLong`;
    - потоковая проверка sha512; файл пишется в
      `config/peercraft/modsync/downloads/self-update.part`, затем переименовывается.
    - Образец — `ModrinthDownloader` (Java 8) и его проверки CDN.
  - Установка: `ModSyncPendingInstaller.armSelfUpdate(entry, file)`. Это новый метод рядом
    с `arm(...)`: строит одну `Entry` и использует уже существующие `prepare`, `launch` и
    проверку готовности. История записывается в манифест Mod Sync как у обычной операции.
  - Состояния для UI: `IDLE`, `DOWNLOADING(%)`, `READY_RESTART`, `FAILED(причина)`.
- Методы в `ModSyncPendingInstaller` добавляются во все четыре копии: main, client-1165,
  client-1122, client-1710 (сейчас у каждой своя Java 8-копия).

### Этап 3. Интерфейс
- Клик по табличке открывает **экран подтверждения** в стиле `SteampunkDialog`:
  - заголовок «Обновить PeerCraft до 3.5.0?»;
  - строка «Файл с CurseForge, ≈ 0,9 МБ. Установится после выхода из игры»;
  - кнопки [Обновить] [Открыть страницу] [Отмена].
  - Если `canSelfUpdate()` = false, вместо «Обновить» показывается пояснение почему
    (нет сборки, другая операция Mod Sync, нестандартная установка), остаётся «Открыть страницу».
- Во время загрузки — прогресс-бар на том же экране, «Отмена» прерывает загрузку и
  удаляет `.part`.
- Готово:
  - экран «Обновление готово. Перезапустите игру», кнопки [Выйти из игры] и [Позже];
  - табличка в меню меняет текст на «PeerCraft 3.5.0 установится после перезапуска»
    (без «×»);
  - «Выйти из игры» вызывает штатное закрытие клиента.
- Ошибка → сообщение с причиной и кнопка «Открыть страницу».
- Новые экраны по платформам:
  - main — `UpdateConfirmScreen`, с гейтами по образцу `ModSyncProgressScreen`;
  - client-1165, client-1122, client-1710 — копии по образцу их `ModSyncProgressScreen`
    и `PeerCraftDialogScreen`.
- Строки `peercraft.update.*` в `en_us.json` и `ru_ru.json`.

### Этап 4. Тесты
- `UpdateSignatureTest`: верная подпись проходит; изменённый байт, чужой ключ и пустая
  подпись не проходят. Тестовая пара ключей генерируется в самом тесте.
- `UpdateManifestTest`:
  - выбор файла по ключу сборки;
  - отказ при чужом хосте, http, несовпадении имени файла и URL, отсутствии sha512;
  - старый формат v1 → самообновления нет, табличка работает.
- `SelfUpdateInstallerTest`: проверка предусловий (jar вне `mods`, ожидающая
  транзакция) и того, что `Entry` собирается правильно, с `oldSha512` текущего jar.
- Скрипт: `--dry-run` на `releases/3.4.3-beta` строит ссылки, которые совпадают с
  реальными файлами на CurseForge.

### Этап 5. Проверка вручную
1. Сгенерировать тестовую пару ключей. Поднять локальный HTTP с подписанным `update.json`,
   где для `fabric-1.21.1` указан реальный CDN-файл 3.4.3. В инстансе поставить jar
   3.4.2-beta.
2. Запустить с `-Dpeercraft.updateCheck.url=…` и `-Dpeercraft.updateCheck.publicKey=…`.
   Ожидается: табличка → «Обновить» → загрузка → «Перезапустите» → выход → в `mods` лежит
   3.4.3, в бэкапе транзакции 3.4.2, следующий запуск показывает 3.4.3 и табличка пропадает.
3. Негативные случаи:
   - подмена байта в `update.json` → нет кнопки «Обновить»;
   - подмена jar на CDN-зеркале (локально) → ошибка sha512, файлы в `mods` не тронуты;
   - убить игру во время загрузки → `.part` удаляется при следующем старте.
4. Повторить на Forge 1.12.2 (Java 8, ECDSA) и проверить на Windows: замена после выхода,
   когда jar разблокирован.

## Риски и ограничения
- **Модерация CurseForge**: обновление становится доступно только после одобрения файлов.
  Скрипт не даст опубликовать манифест раньше времени.
- **Потеря закрытого ключа** означает, что новые подписи не примет ни один клиент. Нужна
  резервная копия ключа. При смене ключа в мод зашиваются оба ключа на один-два релиза.
- **Лаунчеры** (Prism, Modrinth App) могут показать мод как изменённый вручную. Для
  CurseForge App файл распознаётся как официальный. Работе это не мешает.
- **Минимальная версия**: самообновление начнёт работать только у тех, кто уже вручную
  поставил первую версию с этой функцией.
