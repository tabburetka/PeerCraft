ЧТО ЭТО ЗА ПРОЕКТ
-----------------
PeerCraft — Fabric/NeoForge мод для Minecraft, превращающий "Open to LAN" в P2P-игру
через интернет (UDP hole punching), без dedicated-сервера и без проброса портов у
игроков. Плюс собственная лёгкая система аккаунтов/друзей и публичный браузер игр
(лобби-браузер, как в Among Us — см. RoomRegistry.listPublicRooms()).

Автор — sestrazaitzeva138@gmail.com (репозиторий tabburetka/PeerCraft), хобби-проект,
поддерживается одним человеком. README.md в корне — это документация ДЛЯ ИГРОКОВ и
контрибьюторов, читай его тоже (раздел "Development" внизу).

ТРИ НЕЗАВИСИМЫХ GRADLE-ПРОЕКТА
-------------------------------
1. peercraft/            — сам мод (Fabric + NeoForge, Minecraft 1.21.1–1.21.11 на Java 21
                           и 26.1–26.2 на Java 25 — см. "Необфусцированная эра" ниже)
2. rendezvous-server/     — standalone UDP-сервер знакомств (без зависимости от Minecraft)
3. peercraft-forge-1122/  — бэкпорт мода на Minecraft 1.12.2 Forge (см. "Бэкпорт 1.12.2" ниже).
                           Отдельный проект (НЕ Stonecutter-узел): Gradle 8.8 + RetroFuturaGradle
                           1.4.9 + Java 8, тогда как peercraft/ на Gradle 9. Переиспользует
                           общий код из peercraft/src/ через srcDir.

Они НЕ имеют общего build — открывать/собирать по отдельности (`cd peercraft && ...`,
`cd rendezvous-server && ...`, `cd peercraft-forge-1122 && ...`).

ВАЖНОЕ ОГРАНИЧЕНИЕ ТЕКУЩЕЙ РАБОТЫ (спроси пользователя, если неясно, актуально ли ещё)
---------------------------------------------------------------------------------------
Новые фичи изначально разрабатываются и тестируются ПОД 1.21.1-fabric, остальные версии
адаптируются отдельно — но по факту это почти всегда происходит В ТОЙ ЖЕ рабочей сессии
сразу после (см. mod-sync и host handoff ниже — обе фичи теперь портированы на ВЕСЬ
матрикс, включая все три legacy-бэкпорта). Stonecutter (см. ниже) размножает любой код
без версионных `//? if` на все версии автоматически. Полный `./gradlew buildAll` (весь
матрикс) НЕ гоняй без явной просьбы — обычно долго и грузит машину (параллельные Gradle
worker'ы, CPU/RAM в потолок); для проверки используй `./gradlew :1.21.1-fabric:build` /
`:1.21.1-fabric:test`. (buildAll — это ровно то, что гоняет CI; при портах на новые версии
или на бэкпорты его прогнать один раз уместно и оправданно — он реально ловит версийные
API-разломы, которые точечная сборка одного узла не поймёт, например
`Player.displayClientMessage` пропал на 26.1+.)
ПОЛИТИКА ПО МИНОРНЫМ ВЕРСИЯМ MINECRAFT: редкие минорные версии внутри поддерживаемых веток
(например 1.21.6/1.21.7/1.21.9 и аналогичные "промежуточные" версии) остаются в матриксе
сборки и могут получать общий код через Stonecutter, но НЕ считаются обязательными для ручного
тестирования новых фич. Их достаточно держать компилируемыми; рантайм-проверка делается только
по явно выбранным основным версиям/лоадерам. Такие минорные сборки публиковать только на GitHub
releases/артефактах; на внешние платформы вроде Modrinth/CurseForge их не выкладывать, если
пользователь отдельно не попросит исключение.
ИСКЛЮЧЕНИЯ (гонялись на реальной паре host+joiner, не только компилировались):
  - mod-sync (раздел MOD-SYNC ниже) — на 1.21.1-neoforge; проверять правки нужно и
    `:1.21.1-fabric:build`, и `:1.21.1-neoforge:build`.
  - host handoff (раздел HOST HANDOFF ниже) — ТОЛЬКО на 1.21.1-fabric (сессия
    2026-09-14), затем сразу же портирован на весь матрикс + все три бэкпорта тем же
    Claude, но БЕЗ рантайм-проверки на бэкпортах (только успешная сборка) — см. статус
    портов ниже.
ВАЖНО про физически-дублированные файлы (P2PBridge.java, PeerCraftConfig.java,
PeerCraftClientCommon.java — см. "Протокол-дубликат"-подобное решение #1 и раздел
СТОНКАТТЕР): при добавлении новой фичи, трогающей любой из них, правка автоматически
попадает в src/main (используется 1.21.x/26.x/1.16.5), но НЕ в src/shared-forge1122 /
src/shared-forge1710 — их нужно синхронизировать РУКАМИ. Ровно это один раз забыли
сделать при первой версии host handoff (сессия 2026-09-14, коммит c45a9f85) — итог:
`peercraft-forge-1122`/`peercraft-forge-1710` вообще не собирались (пропущенный exclude
для нового пакета `client/handoff/**`), а P2PBridge на этих двух бэкпортах вообще не имел
API хендофа (`beginHandoff`/`connectedJoiners`/...). Нашлось и было исправлено в сессии
портирования (коммит 9a825b28). Если правишь один из этих трёх файлов — сразу проверяй
`grep` по обеим shared-forge-копиям, не только по src/main.

БЭКПОРТ 1.7.10 (peercraft-forge-1710/)
--------------------------------------
Отдельный sibling-проект, как peercraft-forge-1122/ — тот же тулчейн (RFG 1.4.9 + Gradle 8.8 +
Java 8 toolchain, `org.gradle.java.home=java-21-openjdk`, preferIPv4Stack), только
`minecraft_version=1.7.10`, `mapping_channel=stable` / `mapping_version=12`, Forge
1.7.10-10.13.4.1614 (RFG-дефолт). Переиспользует общий код из ../peercraft/src через srcDir +
strip-then-replace Sync-задачи (`syncSharedMain`/`syncSharedJava8`), ровно как 1122.

Ключевой вывод портирования: GUI 1.7.10 и 1.12.2 — ОБЕ до-1.13 эпоха (immediate-mode GL,
GuiScreen + buttonList, GuiButton по id в actionPerformed). Всю концептуальную конверсию уже
сделал бэкпорт 1.12.2; порт 1122->1710 почти механический.

Раскладка исходников:
  * peercraft-forge-1710/src/main/java/net/peercraft/forge1710/ — entrypoint (пакет FML —
    `cpw.mods.fml.*`, НЕ `net.minecraftforge.fml.*`; последнее с 1.8): PeerCraftForge
    (@Mod + @SidedProxy, + @Mod.EventHandler serverStopping -> P2PBridge.cancelRendezvous(),
    т.к. IntegratedServer не переопределяет stopServer на 1.7.10 и миксин туда не встанет),
    CommonProxy/ClientProxy, ForgePlatform (services), PeerCraftCoreMod (IFMLLoadingPlugin +
    io.github.tox1cozz.mixinbooterlegacy.IEarlyMixinLoader — этот интерфейс отдаёт UniMixins
    0.3.1, метод getMixinConfigs():List<String>; аналог zone.rong.mixinbooter.IEarlyMixinLoader
    из 1122. НЕ com.gtnewhorizons.gtnhmixins.* — там всё repackage'нуто).
  * peercraft-forge-1710/src/main/java/org/slf4j/ — шим Logger/LoggerFactory, копия из 1122.
  * peercraft-forge-1710/src/main/resources/peercraft.forge1710.mixins.json (compat JAVA_8,
    2 миксина), mcmod.info. Имя `peercraft.forge1710.mixins.json`, НЕ `peercraft.mixins.json`
    (тот под `exclude` в build.gradle, фильтры Gradle глобальны по srcDir).
  * ../peercraft/src/shared-forge1710/java/ — 5 твинов (RendezvousClient, P2PBridge,
    PeerCraftClientCommon, PeerCraftConfig, PeerCraftCommon). ПОБАЙТОВО равны
    shared-forge1122 (гейты `//? if <1.17` дают ту же pre-1.13 ветку); только шапки-комменты
    другие. Правишь протокол — правь ВСЕ три копии (src/main, shared-forge1122,
    shared-forge1710) синхронно.
  * ../peercraft/src/main-java8/java/ — переиспользуется как есть (как в 1122).
  * ../peercraft/src/client-1710/java/ — 8 экранов + PeerCraftUi + 4 шима (IdButton,
    ToggleButton [cpw.mods.fml.client.config.GuiCheckBox], CycleTextButton, PasswordField)
    + PeerCraftLang + PeerCraftScreenEvents + 2 миксина.

Механические дельты 1122 -> 1710 (всё уже применено; имена выверены по декомпилю RFG в
build/rfg/minecraft-src/, а НЕ по памяти):
  * `this.fontRenderer` -> `this.fontRendererObj`.
  * убран `throws IOException` у keyTyped/mouseClicked/actionPerformed (появился в 1.8);
    убран `import java.io.IOException` (+ неиспользуемый `import ...resources.I18n` из экранов).
  * нет `GuiScreen#addButton` (с 1.9) -> в каждом экране локальный шим
    `private <T extends GuiButton> T addButton(T)` через `this.buttonList.add`.
  * `new GuiTextField(id, font, ...)` -> `new GuiTextField(font, ...)` (параметр id с 1.8);
    `PasswordField` тоже без id в super(...).
  * `GuiButton.x/.y` -> `.xPosition/.yPosition` (см. PeerCraftMultiplayerScreen.addFavoritesGlyphButtons).
  * `Minecraft.addScheduledTask(Runnable)` (с 1.8) -> `Minecraft.func_152344_a(Runnable)`
    (без читаемого маппинга в stable_12). 8 мест: runOnClientThread в 7 экранах + sendChat
    в OpenToLanMixin.
  * `mc.getSessionService()` -> `mc.func_152347_ac()`; `mc.getSession().getProfile()` ->
    `.func_148256_e()`; НО `Session.getToken()` — читаемое имя, оставлено (PeerCraftAccountScreen).
  * PasswordField: нет `GuiScreen.isKeyComboCtrlV/C/X` (с 1.8) -> `GuiScreen.isCtrlKeyDown()
    && keyCode == Keyboard.KEY_V|C|X`. `getClipboardString`/`setClipboardString` — есть.
  * PeerCraftMultiplayerScreen: `buttonList` — СЫРОЙ `List` (element type = Object).
    `for (GuiButton b : buttonList)` НЕ компилится ("Object cannot be converted to GuiButton")
    -> `for (Object o : buttonList) { GuiButton b = (GuiButton) o; ... }` (см. findVanilla).
    Ручной draw-loop: `((GuiButton) buttonList.get(i)).drawButton(mc, x, y)` — БЕЗ partialTicks
    (4-й аргумент только с 1.10). Id ванильных кнопок GuiMultiplayer (1 select/2 delete/3 add/
    4 direct/7 edit/8 refresh/0 back) — ТЕ ЖЕ, что в 1.12.2 (проверено по
    GuiMultiplayer.createButtons() в декомпиле).
  * PeerCraftScreenEvents: `@SubscribeEvent` -> `cpw.mods.fml.common.eventhandler.SubscribeEvent`
    (сам `net.minecraftforge.client.event.GuiScreenEvent` не переезжал). 1.7.10 GuiScreenEvent —
    ПУБЛИЧНЫЕ ПОЛЯ `event.gui` / `event.button` / `event.buttonList` (геттеры с 1.8.9).
    `InitGuiEvent.Post.buttonList` — РЕАЛЬНЫЙ список экрана (у ActionPerformedEvent — копия),
    добавление в .Post даёт живые кликабельные кнопки. `ActionPerformedEvent.Pre` — @Cancelable.
  * OpenToLanMixin: `IntegratedServer.shareToLAN(WorldSettings.GameType, boolean)` (GameType
    вложен в WorldSettings до 1.8); текст-компоненты `net.minecraft.util.Chat*` /
    `EnumChatFormatting` / `ChatStyle`, `player.addChatMessage`, `Minecraft.thePlayer`;
    инъекции в stopServer нет (см. serverStopping-эвент выше). `server.getFolderName()` вместо
    `getWorldName()`.
  * ServerLoginPacketListenerImplMixin: цель `@Inject(method = "func_152506_a")` (у
    getOfflineProfile НЕТ читаемого маппинга в stable_12); `@Shadow @Final` поле —
    `field_147333_a` (тоже без читаемого имени), у него `.getSocketAddress()` (читаемое)
    вместо `getRemoteAddress()`. Это ГЛАВНЫЙ миксин (стабильный UUID для одинаковых ников —
    пользователь потребовал не допускать коллизий), ради него в проекте вообще есть
    mixin-тулчейн. Refmap после build: shareToLAN->func_71206_a(WorldSettings$GameType,Z),
    func_152506_a->func_152506_a(GameProfile).

Провайдер Mixin: UniMixins (`io.github.legacymoddingmc:unimixins:0.3.1:dev` на GTNH-нексусе;
build.gradle через `modUtils.enableMixins("...:dev", "peercraft.mixins.refmap.json")` +
annotationProcessor'ы asm-debug-all 5.2 / guava / gson — ровно как 1122). Mixin AP
(SpongePowered 0.8.7, внутри UniMixins) при build отрабатывает БЕЗ warning'ов, refmap
пишется. Игроку нужен UniMixins `-all` jar в mods/ (аналог "нужен MixinBooter" для 1.12.2).
Осталось доказать только РАНТАЙМ-применение миксинов (compile + refmap этого не гарантируют).

Локализация: `generateLang` конвертит общий *.json -> *.lang, но ИМЕНА с заглавным регионом
(`en_US.lang` / `ru_RU.lang`) — 1.7.10 код языка в gameSettings.language = `en_US`, не `en_us`
(строчный с 1.11). PeerCraftLang грузит по тому же коду напрямую с classpath (тот же трюк,
что 1122 — resource-pack мода отдаёт icon.png, но не lang/*.lang). PeerCraftLang сделан
`public` (нужен OpenToLanMixin'у для host-side чата).

P2P-СТАТУСЫ/ОШИБКИ — ЛОКАЛИЗОВАНЫ НА ВСЕХ ВЕРСИЯХ (1.7.10 в сессии 2026-08-30, остальные
2026-08-30 позже). Баг: P2PBridge и RendezvousClient исторически шлют user-facing строки
хардкодом по-русски (transport-слой без доступа к i18n), экраны показывали их как есть -> на
англ. клиенте ошибка "неверный код комнаты" по-русски. Фикс: {RendezvousClient,P2PBridge}
(во ВСЕХ трёх копиях: src/main + shared-forge1122 + shared-forge1710) эмитят ТРАНСЛЕЙШН-КЛЮЧИ
`peercraft.p2p.*` (14 ключей в ОБА общих src/main/resources/.../lang/*.json — additive; для
1.12.2/1.7.10 generateLang кладёт их в .lang, PeerCraftLang.tr читает с classpath). Экраны
{PeerCraftJoinScreen,PeerCraftMultiplayerScreen} резолвят строку из listener'а:
src/main + client-1165 через `Component.translatable(...)` (в PeerCraftMultiplayerScreen —
ТОЛЬКО P2P-listener'ы onConnectToFriend/onJoinGame, не AccountClient-колбэки),
client-1122/1710 через `PeerCraftLang.tr()`. OpenToLanMixin.onFailed во всех версиях
резолвит ключ вложенно (`Component.translatable(reason)` / `PeerCraftLang.tr(reason)`).
describeReason во всех трёх копиях (в src/main — ОБЕ ветки Stonecutter-гейта) возвращает ключ.
  * Логи P2PBridge/RendezvousClient (LOGGER.*) — намеренно RU везде, не трогать.
    AccountClient-ошибки (rename/friend/remove/sendFriendRequest в PeerCraftMultiplayerScreen)
    — отдельная подсистема, RU-хардкод, НЕ тронута (осознанно).

BUG «сырой ключ в чате хоста» (screenshot 1.12.2, сессия 2026-08-30). OpenToLanMixin
.onRoomCreated в 1122/1710 строил `TextComponentTranslation(prefixKey)` — но FML-resource-pack
мода в coremod-конфиге не отдаёт lang/*.lang, ванильный i18n echo'ил ключ. Фикс: в 1122/1710
`.onRoomCreated` теперь `new (Text|Chat)ComponentString(PeerCraftLang.tr(prefixKey))` (импорт
`net.minecraft.util.text.TextComponentString` уже был; `TextComponentTranslation`/

(в 1710 уже был). На Fabric-версиях (src/main, 1.16.5) бага нет — lang отдаётся штатно.

`EditBox.setSuggestion` на 1.16.5 рисует подсказку безусловно (в отличие от modern

КЛЮЧЕВЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ (не переизобретай, не удивляйся)
-------------------------------------------------------------------
1. Протокол-дубликат: RendezvousProtocol.java существует В ДВУХ МЕСТАХ (mod и server) с
   ПОБАЙТОВО идентичной логикой кодирования — это осознанное решение (server не зависит
   от Minecraft/Loom, а mod не может тянуть server как Gradle-модуль). Любое изменение
   протокола правь СИНХРОННО в обеих копиях. Есть pinned-byte тесты в RendezvousProtocolTest
   (в обоих проектах), которые ловят регресс формата — после правки протокола обязательно
   прогони тесты в обоих проектах.

2. Обратная совместимость протокола — строго append-only опциональные трейлеры: новое поле
   дописывается в КОНЕЦ существующего сообщения и читается только если
   `buf.remaining() >= N`. Старые encode-перегрузки/тесты не трогать — оставлять их
   побайтово как есть, добавлять НОВЫЕ перегрузки. См. комментарии в самом
   RendezvousProtocol.java — там подробно расписано, что можно/нельзя.

3. Stonecutter (multi-version): один общий src/main/java, версионные различия — через
   preprocessor-комментарии `//? if <VERSION` / `//? if >=VERSION { ... } else { ... }`.
   Код БЕЗ таких комментариев автоматически применяется ко всем версиям — писать
   версии-специфичный код только когда реально меняется Minecraft API.
   ГРАБЛИ: Stonecutter 0.9.7 НЕ поддерживает `//?} else if <VERSION {` — активная ветка
   переносится неправильно (наблюдалось: сломанный `:1.21.1-fabric:compileJava`). Нужен
   3-way выбор — делай вложенные `if/else`, а не `else if`.
   Известные точки излома API в этом дереве версий:
     - `WorldVersion.getName()` → `.name()` (гейт `//? if <1.21.6` в OpenToLanMixin.currentMinecraftVersion())
     - `GameProfile.getName()` → `.name()` — тот же паттерн, см. AccountClient.loginLicensed
     - `ClickEvent`/`HoverEvent` стали sealed-интерфейсами с record-вариантами на 1.21.5
       (см. OpenToLanMixin.copyableCodeMessage)
     - `CycleButton.builder(Function)` потерял overload без initial value на 1.21.11 —
       withInitialValue() убран, значение теперь обязательный аргумент конструктора (см.
       ShareToLanScreenMixin.maxPlayersButton и PeerCraftMultiplayerScreen.rebuildVersionFilterButton)
     - `Screen.keyPressed` сменил (int,int,int) на KeyEvent record на 1.21.9
     - НЕОБФУСЦИРОВАННАЯ ЭРА: с 26.1 Minecraft поставляется без обфускации, FabricMC перестал
       выпускать маппинги. Fabric-цели 26.x собираются ОТДЕЛЬНЫМ buildscript
       build.fabric-unmapped.gradle.kts: плагин net.fabricmc.fabric-loom (НЕ -remap),
       без mappings(), implementation() вместо modImplementation(), Java 25,
       mixin compatibilityLevel JAVA_25 (переписывается в processResources, чтобы не трогать
       общие JSON'ы). Оба loom-плагина объявлены apply false в stonecutter.gradle.kts, выбор
       buildscript'а — параметр fabricBuildscript у mc() в settings.gradle.kts. NeoForge —
       тот же build.neoforge.gradle.kts, но java_version=25 в versions/26.*-neoforge/
       gradle.properties (перекрывает общий 21; options.release/toolchain читают этот проп).
       foojay-resolver подняли 0.8.0 -> 1.0.0 (иначе Gradle 9 падает на IBM_SEMERU и не
       качает JDK 25). Для 26.x ВСЕ гейты //? if <1.21.N уже дают современную ветку
       (major 26 > 1). Новые изломы 1.21.11 -> 26.2 (все загейчены //? if <26.1 / <26.2):
         * 26.1: GuiGraphics -> GuiGraphicsExtractor; Screen#render -> #extractRenderState
           (render-state extraction); drawString/drawCenteredString -> text/centeredText;
           renderBackground рисует сам Screen (как с 1.21.6). Затронуты все PeerCraft*Screen
           + PeerCraftUi (методы загейчены блоками, как keyPressed).
         * 26.1: Player.displayClientMessage(Component,boolean) -> sendSystemMessage(Component)
           (actionbar-вариант — sendOverlayMessage). См. OpenToLanMixin.sendChatMessage.
         * 26.2: Minecraft.setScreen / поле Minecraft.screen переехали на Minecraft.gui
           (gui.setScreen / gui.screen()). Заведены хелперы PeerCraftUi.setScreen(mc,screen)
           и PeerCraftUi.isCurrentScreen(screen) — все ~30 вызовов идут через них;
           TitleScreenMixin гейтит свой единственный вызов inline.
         * 26.2: ShareToLanScreen удалён -> экран "Open to LAN" стал MultiplayerOptionsScreen

MOD-SYNC (автозагрузка модпака хоста при заходе) — 1.21.x fabric/neoforge, сессия 2026-08-31
------------------------------------------------------------------------------------------------
НАЗНАЧЕНИЕ: заходящий стартует с пустой mods/ (только peercraft.jar) — mod-sync качает ВЕСЬ
модпак хоста, потом просит перезапуск. Не "докачать серверные моды", а КЛОНИРОВАТЬ мод-сет.
Разрабатывалось/тестилось на реальной паре host+joiner, host — Sinytra Connector модпак.

ГДЕ ВКЛИНИВАЕТСЯ: единственная точка — P2PBridge.beginClientPunch, в
PunchCoordinator.Callback.onSuccess МЕЖДУ setClientTargetPeer(...) и listener.onConnected().
Прямой UDP-канал уже есть, байт Minecraft ещё не было. Хост-зеркало — beginHostPunch (после
onSuccess пир в authorizedPeers). Демукс: handleIncomingPacket роутит data[0]==0xE2 в
ModSyncCoordinator ДО FramedPacket.decode (joiner — единственный rendezvousListener slot,
host — Map<PeerAddress,ModSyncCoordinator> modSyncHostSessions).

RENDEZVOUS-СЕРВЕР И RendezvousProtocol НЕ ТРОНУТЫ. Хендшейк едет по пробитой P2P-дырке
(magic 0xE2, свой кодек ModSyncProtocol). Нет редеплоя сервера, нет двойных pinned-byte
тестов. НЕ добавляй mod-sync-поля в RendezvousProtocol.

ПЕРЕЧИСЛЕНИЕ МОДОВ = ФАЙЛЫ, НЕ ЗАГРУЗЧИК. ModJarScanner листает *.jar прямо в mods/ и читает
id/версию из fabric.mod.json / META-INF/neoforge.mods.toml (hand-parse regex) ВНУТРИ jar.
Причина: ModList на Sinytra Connector отдаёт для Sodium/KFF/Fabric-модов путь на
распакованный inner-jar (или .connector-кэш), а JIJ-подмодули прячет. Первая реализация
через Services.PLATFORM.getInstalledMods() слала inner-jar'ы (thedarkcolour.kffmod,
fabric-loot-api-v3) отдельными файлами и ломала JarJar на заходящем. НЕ возвращай ModList-based
перечисление. getInstalledMods() остался только для selfVersion().

DIFF ТОЛЬКО ПО id (ModDiff.missing), ВЕРСИЯ ИГНОРИРУЕТСЯ. Мод "недостающий" ⇔ у заходящего нет
jar с таким id. Совпал id — мод НЕ трогается. Сравнение версий пометило бы "недостающим" почти
всё (Fabric↔NeoForge/Connector: "0.6.13" vs "0.6.13+mc1.21.1" vs "mc1.21.1-...-neoforge") и
привело бы к замене рабочих jar. НЕ возвращай version-based diff.

УСТАНОВКА ЧИСТО АДДИТИВНА (ModSyncFilesystem). НИКОГДА не двигает/не удаляет/не перезаписывает
существующий jar. Файл с таким именем уже есть → пропуск. Был механизм "отодвинуть старый jar
в superseded/ + маркер .peercraft-remove" — УДАЛЁН: startup-sweep по маркерам однажды снёс
пользователю весь модпак. sweepOnStartup теперь трогает ТОЛЬКО *.jar.part и serving/.
НЕ добавляй логику, которая трогает чужие jar.

ФИЛЬТР (ModSyncFilter) урезан до минимума: peercraft + minecraft/java + загрузчик
(neoforge/forge/fabricloader). ВСЁ остальное синхрится — Fabric API целиком, kotlinforforge-*-all.jar,
Connector, client-only моды (модель "клонировать весь модпак"). JIJ-подмодулей тут нет, т.к.
перечисляем файлы, а не ModList.

ТРАНСПОРТ — ГИБРИД. На каждый недостающий мод joiner делает Modrinth lookup по SHA-512 jar
(ModrinthClient, 6 параллельно): хеш совпал → HTTPS c cdn.modrinth.com мимо туннеля (ModDownloader);
иначе → стрим байт с хоста по P2P (ModSyncCoordinator T_FILE_*). Connector forgify'ит jar →
SHA-512 не совпадает с Modrinth → на Connector-паке почти всё идёт по P2P (медленно, чанки 6000 Б,
пейсинг). Хеш проверяется ВСЕГДА (и для HTTP, и для P2P). Загрузки последовательные — 160 модов
= десятки минут.

KEEPALIVE + RETRY (важно, было "0 модов за 5 минут"): обе стороны шлют T_PING каждые 3 с всё
время сессии, иначе NAT-дырка протухает за время Modrinth-lookup'ов / открытого confirm-экрана.
requestFile переотправляет T_REQUEST_FILE каждые 1.5 с (до 90 с) — один потерянный UDP-запрос
не должен стопить всё. TRANSFER_TIMEOUT 30 мин.

MANIFEST >~1200 Б стримится как файл под зарезервированным modId "$manifest" (MANIFEST_FLAG_STREAMED),
отдельная ветка в ModSyncCoordinator.ManifestStreamState.

ПОТОК ЭКРАНОВ (ClientModSyncAgent): run() сразу показывает ModSyncPreparingScreen ("Contacting
the host…" / "Checking mods N/M…"). Дальше onManifest → planAndPrompt (параллельный Modrinth) →
ModSyncConfirmScreen (пропуск при modSync.autoAccept) → runDownloads → ModSyncProgressScreen
(полоса на файл + общая + Cancel) → ModSyncRestartRequiredScreen. Экраны — БЕЗ нового миксина,
пушатся из коллбэков, gated render/extractRenderState как в PeerCraftJoinScreen. Полосы —
текстовые (█/░), намеренно без render-primitive API ради версий.

ВОЗВРАТ НА ЭКРАН (был баг "выкинуло в меню + вечный already_connecting"): ClientModSyncAgent
конструируется с previousScreen = САМ экран мультиплеера/по-коду (new ClientModSyncAgent(this,...)),
НЕ lastScreen. finishProceed() делает setScreen(previousScreen) ПЕРЕД outcome.proceedToConnect(),
иначе screen.onConnected() бейлит по stillOnThisScreen() и ConnectScreen.startConnecting не
зовётся, а rendezvousClientBusy остаётся true навсегда. Плюс P2PBridge.armBusyWatchdog():
если через 45 с флаг всё ещё стоит и currentClientSession==null — снимаем принудительно.

MOD-SYNC — НЕ ГЕЙТ. Любой облом (loader_mismatch, ошибка хоста, отмена) → ClientModSyncAgent
делает finishProceed(), НЕ finishFail() — заход продолжается обычным путём (ванилла сама
покажет "missing mods" если что). loader_mismatch хост шлёт ТОЛЬКО когда есть что качать И
загрузчики реально разные (LoaderTag: NeoForge/Forge проверяется РАНЬШЕ Fabric — у Connector
есть шим net.fabricmc.loader.api.FabricLoader).

P2PBridge API: старые перегрузки startClientViaRendezvous(4-арг) / startHostViaRendezvous(7-арг)
делегируют в новые с null (ConnectListener НЕ трогали — он реализован анонимно в 4 местах +
твины). abortModSyncClient() — единственный сброс rendezvousClientBusy для терминала
"моды поставлены / отменено".

ТЕСТИРОВАНИЕ mod-sync: нужен ЖИВОЙ host+joiner (юнит-тесты покрывают ModSyncProtocol pinned-byte,
ModDiff, FileReassembler, ModSyncManifest — network/modsync + client/modsync в src/test). При
любой правке mod-sync ХОСТУ ТОЖЕ нужен свежий джар — перечисление списка и пейсинг чанков
делает хост. rendezvousClientBusy живёт в памяти — залип → перезапуск клиента.

СТАТУС ПОРТОВ mod-sync (обновлено 2026-09-14 — раздел ниже раньше был стухший, ПРОВЕРЬ САМ
если снова не уверен, а не доверяй слепо): портирован ЦЕЛИКОМ на весь модерн-матрикс (26.x

HOST HANDOFF (передача хостинга другому игроку без обрыва сессии) — сессия 2026-09-14
-----------------------------------------------------------------------------------------
НАЗНАЧЕНИЕ: раньше уход хоста убивал всю сессию (топ-пункт известных ограничений в README).
Теперь хост может со страницы паузы выбрать подключённого игрока и "передать" ему хостинг:
выбранный получает копию мира и поднимает свой IntegratedServer под своим аккаунтом, остальные
автоматически переподключаются к новому хосту, старый хост может спокойно выйти.

ПРОТОКОЛ: третье P2P-семейство поверх уже пробитой дырки, magic-байт 0xE3 — HandoffProtocol
(offer/accept/decline/migrate/migrate_ok/abort/ping + T_SUCCESSOR_PREFERENCE 0x08, см. ниже) —
и 0xE4 — WorldTransferProtocol (сами байты архива мира, отдельный от mod-sync 0xE2 транспорт,
свой selective-ACK repair, SHA-512-проверка). RendezvousProtocol/rendezvous-сервер НЕ трогает
хендшейк напрямую — ЕДИНСТВЕННОЕ, что он трогает, это новый query TYPE_LOOKUP_HOST
(account id -> код комнаты), которым каждый НЕ-преемник джойнер находит новую комнату нового
хоста после MIGRATE (нужен свежий джар и на моде, и на rendezvous-server, если хендофф не
работает после апдейта — проверь, что сервер тоже пересобран).

ИЗОЛЯЦИЯ СОХРАНЕНИЙ ПРИ HANDOFF (2026-09-26)
----------------------------------------------
- PlayerDataLoadMixin отключает ТОЛЬКО путь загрузки по имени владельца / Data.Player.
  PlayerDataSaveMixin сохраняет ванильную запись Data.Player, но проверяет UUID локального
  хозяина: гость с тем же именем не может подменить снимок. На 26.x Data.Player уже заменён
  ссылкой singleplayer_uuid; PlayerDataMigrationMixin выставляет фактический UUID профиля
  сервера, чтобы после обычного сохранения мир работал и без PeerCraft.
- LocalPlayerIdentity фиксирует UUID локального хоста до загрузки мира: accountId PeerCraft
  при авторизации, иначе уже записанный UUID миграции или исходный UUID Minecraft. На legacy
  при null UUID используется ванильный OfflinePlayer:<name>. Модерн-login также больше не
  выдаёт профиль хозяина УДАЛЁННОМУ игроку лишь из-за совпадения имени.
- world/PlayerDataMigration + MigrationNbt/Regions/Transaction — общий Java-8-совместимый
  код; мигрирует ДО загрузки регионов/статистики/advancements. Data.Player не удаляется,
  копируется только по доказанному UUID; существующие назначения не перезаписываются.
  stats/advancements копируются по UUID, Owner/OwnerUUID/OwnerUuid/owner в region/ и entities/
  переписываются во всех измерениях. Gzip/zlib/raw/LZ4 и внешние .mcc поддержаны.
- peercraft-player-identities.properties едет с архивом мира; один launcher UUID нельзя
  заново присвоить другому аккаунту. Бэкапы изменённых файлов + journal остаются в
  .peercraft-player-migration/backup-* и исключаются из архива; незавершённый commit
  откатывается перед следующей попыткой. Ошибка чтения/неизвестный UUID прерывает старт,
  не подставляет данные по имени и не запускает мир после частичной миграции.
- У всех трёх новых mixin'ов есть client-1165/1122/1710-копии. Forge getPlayerNBT добавлен
  Forge и НЕ имеет SRG mapping — его Redirect явно remap=false, основной readPlayerDataFromFile
  ремапится обычным способом. Не возвращать stripEmbeddedOwnerPosition в SuccessorLauncher.
- Подробности и ручной сценарий: peercraft/docs/player-data-migration.md; регресс-тесты —
  src/test/java/net/peercraft/world/PlayerDataMigrationTest.java.

---------------------
- peercraft:          cd peercraft && ./gradlew :1.21.1-fabric:test -q

ДЕПЛОЙ (локальная машина разработчика, если попросят)
-------------------------------------------------------
- Мод-джар в PrismLauncher: скопировать собранный jar в
  ~/.local/share/PrismLauncher/instances/peercraft-<mc>-<loader>/minecraft/mods/
  (папка называется `minecraft/`, НЕ `.minecraft/`).
- ИНСТАНСЫ (нормализовано в сессии 2026-09-14, коммит-времени работы над host handoff): у
  КАЖДОЙ пары (mc, loader) РОВНО ТРИ инстанса — peercraft-<mc>-<loader> (хост),
  peercraft-<mc>-<loader>-joiner, peercraft-<mc>-<loader>-joiner2 — чтобы локально гонять
  живой host + 2 джойнеров (нужно, например, чтобы host handoff реально проверить: хост
  передаёт одному joiner'у, второй остаётся проверить автопереподключение через MIGRATE).
  32 пары * 3 = 96 инстансов всего. peercraft-1.12.2-forge-joiner и
  peercraft-1.21.1-neoforge-joiner2 раньше были безымянными PrismLauncher-дублями
  ("peercraft-1.12.2-forge(1)" / "peercraft-1.21.1-neoforge(1)") — переименованы в этой
  сессии, сейвы/моды сохранены (просто rename директории + правка `name=` в instance.cfg).
  У КАЖДОГО из 96 инстансов СВОИ УНИКАЛЬНЫЕ порты в JvmArgs (иначе двух джойнеров на одной
  машине не поднять одновременно — коллизия LocalProxy): `-Dpeercraft.rendezvousHost=127.0.0.1
  -Dpeercraft.hostUdpPort=N -Dpeercraft.clientUdpPort=N+1 -Dpeercraft.proxyPort=M` (хостовый
  инстанс без rendezvousHost — коннектится к боевому серверу). Глобальная последовательная
  схема: hostUdpPort растёт на 2 от инстанса к инстансу (было пройдено до 53192,
  clientUdpPort = hostUdpPort+1), proxyPort растёт на 1 (было пройдено до 54099) — НОВЫЙ
  инстанс получает следующие свободные значения, НЕ переиспользуй уже занятые (проверь
  `grep -h JvmArgs ~/.local/share/PrismLauncher/instances/peercraft-*/instance.cfg` на
  текущий максимум перед тем как добавлять инстанс). peercraft-1.12.2-forge (нужен
  mixinbooter-8.9.jar в mods/) и peercraft-1.7.10-forge (нужен unimixins-all в mods/) — те же
  правила на все 3 их инстанса. Все три «старых» семейства — Java jre-legacy (1.8.0_202)
  через OverrideJavaLocation. Раскатка всех джаров разом: для каждого
  ~/.local/share/PrismLauncher/instances/peercraft-<mc>-<loader>[-joiner[2]]/ скопировать в
  minecraft/mods/ соответствующий свежий джар (forge ->
  peercraft-forge-11xx/build/libs/peercraft-forge-<mc>-<v>.jar, fabric/neoforge ->
  peercraft/versions/<mc>-<loader>/build/libs/peercraft-<loader>-<mc>-<v>.jar) — обычно то же
  ИМЯ файла (mod_version не бампался), так что это просто перезапись на месте; если версия
  всё же сменилась — удалить старый peercraft-*.jar, СОХРАНЯЯ fabric-api-*.jar / mixinbooter /
  unimixins / прочие моды. -joiner/-joiner2 получают ТОТ ЖЕ джар, что и хостовый инстанс пары.
  * 1.21.x-инстансы: Java 21 (instance.cfg → JavaPath=/usr/lib/jvm/java-21-openjdk/...).
  * 26.x-инстансы: Java 25 (instance.cfg → JavaPath=~/.local/share/PrismLauncher/java/
    java-runtime-epsilon/bin/java, OverrideJavaLocation=true).
- Создание инстанса вручную: каталог peercraft-<mc>-<loader>/ с instance.cfg + mmc-pack.json
  (компоненты: org.lwjgl3, net.minecraft, для Fabric ещё net.fabricmc.intermediary +
  net.fabricmc.fabric-loader, для NeoForge — net.neoforged) + minecraft/mods/<jar>.
  Образец — любой существующий peercraft-1.21.11-{fabric,neoforge}/.
- FABRIC-инстансам ОБЯЗАТЕЛЬНО нужен jar Fabric API в minecraft/mods/ рядом с мод-джаром
  (иначе мод не грузится). Готовые jar'ы лежат в кэше Gradle после сборки:
  ~/.gradle/caches/modules-2/files-2.1/net.fabricmc.fabric-api/fabric-api/<version>/*/fabric-api-<version>.jar
  (версия = fabric_api_version из versions/<mc>-fabric/gradle.properties). Для unobf-эры это
  ровно рантайм-jar (ремапа нет).
- NEOFORGE на этой машине: EarlyDisplay (окно раннего лоадскрина) виснет —
  "Cannot hand over rendering to Minecraft! The background loading screen renderer seems stuck."
  Это НЕ баг мода (окружение/GPU-драйвер на Linux). Фикс: minecraft/config/fml.toml →
  `earlyWindowControl = false` в каждом NeoForge-инстансе.
- ВАЖНО про NeoForge-версию в Prism: мета-сервер Prism (meta.prismlauncher.org) отстаёт от
  maven.neoforged.net на ~3 билда. В mmc-pack.json надо ставить версию, которая ЕСТЬ в
  Prism-мете, иначе инстанс не соберётся. Поэтому 26.1.2/26.2 NeoForge-джары в проекте
  запинены на 26.1.2.97 / 26.2.0.67 (не .100/.70) — под то, что Prism реально запускает.
  Джар и версия компонента в mmc-pack должны совпадать (neoforge.mods.toml декларирует
  versionRange "[<neoforge_version>,)").
- Серверный jar (rendezvous-server) НИКОГДА не деплоить и не запускать самостоятельно без
  явной просьбы — по умолчанию только собирать (`./gradlew build`), деплой на реальный сервер
  делает пользователь сам. Если меняется протокол/сервер-логика — обязательно предупреждать
  пользователя, что нужно вручную обновить рабочий сервер, иначе новые поля будут молча
  отбрасываться (readShortString() и подобные хелперы толерантны к недостающим байтам —
  это значит баг "фича работает в коде, но не видна в игре" будет выглядеть как логическая
  ошибка, а на деле — просто старый бинарник сервера).
- MOD-SYNC при правках: ХОСТУ тоже нужен свежий джар (перечисление модов и пейсинг чанков —
  на хосте), иначе поведение непредсказуемо. Rendezvous-сервер mod-sync НЕ трогает. HOST
  HANDOFF при правках — туда же: и хосту, и КАЖДОМУ джойнеру (у обоих P2PBridge должен уметь
  и посылать, и принимать 0xE3/0xE4) нужен свежий джар; rendezvous-сервер трогать нужно
  ТОЛЬКО если менялся сам TYPE_LOOKUP_HOST (см. раздел HOST HANDOFF) — иначе не нужно.
