ПОЛНОЕ ОПИСАНИЕ КОДА PEERCRAFT
================================
Документ объясняет каждый класс и каждый его метод простым языком, с расчётом
на то, что читатель слабо знаком с Java. Везде, где встречается специфичная
для Java (или для библиотеки Fabric/Minecraft) конструкция, стоит пометка вида
[Г7] — это отсылка к ГЛОССАРИЮ в самом конце файла, где эта конструкция
объяснена один раз подробно. Если по ходу чтения встретилась незнакомая
пометка — просто промотай (Ctrl+F в текстовом редакторе) в самый низ файла и
найди этот номер.

ЧТО ВХОДИТ В ДОКУМЕНТ
---------------------
Разобран весь "боевой" код двух проектов:
  1) fabric-example-mod — сам мод для Minecraft (папки src/main и src/client).
  2) rendezvous-server — отдельный сервер знакомств (папка src/main).
Тестовые классы (src/test в обоих проектах) не разбираются построчно — в
конце документа для них дано только краткое назначение файла, т.к. это
проверочный код, а не код, который реально работает у игрока.

ПОРЯДОК ЧТЕНИЯ (рекомендуемый)
-------------------------------
  1. Точки входа (PeerCraftMod, PeerCraftClient, ServerLifecycleHandler)
  2. Конфигурация (PeerCraftConfig, PeerCraftHostOptions)
  3. GUI и mixin'ы (TitleScreenMixin, PeerCraftJoinScreen, ShareToLanScreenMixin, OpenToLanMixin)
  4. Ядро сети — уровень 1, "мост" (FramedPacket, ReorderBuffer, PeerAddress,
     RawPacketListener, P2PSender, P2PReceiver, LocalProxy, P2PBridge)
  5. Ядро сети — уровень 2, "знакомство и пробив NAT" (RendezvousProtocol,
     RendezvousClient, PunchCoordinator)
  6. Отдельный проект rendezvous-server (RendezvousProtocol — копия,
     RendezvousServer, RoomRegistry, Room)
  7. Шаблонные заглушки Fabric (ExampleMixin, ExampleClientMixin) — не несут
     функциональности, но формально тоже классы мода.

Документ дальше идёт именно в этом порядке.

1. ТОЧКИ ВХОДА
====================================================================

--------------------------------------------------------------------
1.1 net.peercraft.PeerCraftMod
Файл: fabric-example-mod/src/main/java/net/peercraft/PeerCraftMod.java
--------------------------------------------------------------------
Роль: главная точка входа мода — код, который Fabric-загрузчик вызывает
первым, ещё до того, как что-либо графическое (окно игры) готово. Класс
реализует интерфейс[Г7] ModInitializer из Fabric API — это контракт вида
"у тебя обязан быть метод onInitialize()".

Поля:
  MOD_ID — строка "modid". Это шаблонное значение из заготовки Fabric,
  оставшееся неизменным (в fabric.mod.json настоящий id мода — "peercraft",
  здесь несовпадение — известный технический долг, не влияет на работу).
  LOGGER — объект для вывода сообщений в консоль/лог-файл [Г28].

Методы:
  onInitialize()
    Вызывается автоматически один раз при старте игры (и клиента, и
    сервера — этот класс общий[Г2] для обеих сторон). Печатает приветственное
    сообщение в лог и вызывает ServerLifecycleHandler.registerEvent() —
    то есть подписывает мод на события жизненного цикла сервера (см. 1.3).
    Аннотация @Override [Г27] говорит, что метод переопределяет метод из
    интерфейса ModInitializer, а не является новым.

  static id(String path)
    Вспомогательный static[Г3]-метод: собирает "адрес ресурса" Minecraft
    (ResourceLocation) вида "modid:path" — используется, когда моду нужно
    сослаться на свою текстуру/звук/рецепт по стандартному для Minecraft
    формату идентификаторов. В текущем коде мультиплеера реально не
    используется — заготовка на будущее.


--------------------------------------------------------------------
1.2 net.peercraft.client.PeerCraftClient
Файл: fabric-example-mod/src/client/java/net/peercraft/client/PeerCraftClient.java
--------------------------------------------------------------------
Роль: точка входа, которая запускается ТОЛЬКО на клиенте (у игрока, а не на
сервере) — реализует ClientModInitializer[Г7]. Именно здесь решается, нужно
ли сразу поднимать сетевые компоненты мода при запуске игры.

Методы:
  onInitializeClient()
    1. Читает PeerCraftConfig.mode() — режим работы мода (auto/client/host/
       disabled, см. раздел 2.1).
    2. Если режим "disabled" или "host" — клиентский прокси не запускается
       (сразу return[Г5], т.е. выход из метода — хосту прокси-туннель для
       себя самого не нужен, он слушает напрямую).
    3. Иначе — запускает P2PBridge.INSTANCE.startProxy(...) (см. 4.7) — это
       локальный TCP-сервер на 127.0.0.1, к которому позже подключится сам
       Minecraft-клиент.
    4. Если включён internetPlay (see 2.1) — ничего больше не делает сразу,
       ждёт, пока игрок сам нажмёт кнопку "PeerCraft: Join" на титульном
       экране (см. 3.1-3.2). Если internetPlay выключен — сразу вызывает
       P2PBridge.INSTANCE.startClient() (старый, "статический" путь по
       фиксированным адресам из конфига, используется только для локальной
       разработки/тестов на одной машине).


--------------------------------------------------------------------
1.3 net.peercraft.event.ServerLifecycleHandler
Файл: fabric-example-mod/src/main/java/net/peercraft/event/ServerLifecycleHandler.java
--------------------------------------------------------------------
Роль: крошечный класс-обёртка вокруг одного события Fabric API. Функционально
не связан с мультиплеерным relay — это отдельная, независимая часть мода
(просто выводит сообщение в лог при старте одиночной игры/сервера).

Методы:
  static registerEvent()
    Подписывается на событие ServerLifecycleEvents.SERVER_STARTED (это
    статическое событие[Г3] из Fabric API — по сути глобальный "список
    подписчиков", и .register(...) добавляет в этот список ещё одного).
    Аргумент — лямбда-выражение[Г13] `server -> { ... }`: короткая функция
    без имени, которая будет вызвана автоматически, когда сервер (в том
    числе внутренний IntegratedServer одиночной игры) закончит запуск.
    Внутри лямбды — всего одна строка: печать в лог "одиночная игра
    запущенна".

2. КОНФИГУРАЦИЯ

--------------------------------------------------------------------
2.1 net.peercraft.config.PeerCraftConfig
Файл: fabric-example-mod/src/main/java/net/peercraft/config/PeerCraftConfig.java
--------------------------------------------------------------------
Роль: единая точка чтения всех настроек мода. Все настройки можно задать
двумя способами (на выбор): флагом при запуске Java (-Dpeercraft.<имя>=...)
или переменной окружения (PEERCRAFT_<ИМЯ>). Если ничего не задано — берётся
значение по умолчанию, зашитое в код.

Публичные static-константы:
  MODE_AUTO / MODE_CLIENT / MODE_HOST / MODE_DISABLED — просто строки-имена
  четырёх допустимых режимов работы мода (используются вместо "магических
  строк" в других классах, чтобы не ошибиться в написании).

Публичные методы (каждый читает ровно одну настройку):
  mode()
    Режим работы: "auto" (по умолчанию), "client", "host" или "disabled".
    Если в конфиге написано что-то другое/с опечаткой — выводится
    предупреждение в лог и возвращается "auto".
  proxyPort()
    Порт локального TCP-прокси (LocalProxy) на джойнере. По умолчанию 25566.
  clientUdpPort() / hostUdpPort()
    UDP-порты, которые слушает мод на джойнере / на хосте соответственно (по
    умолчанию 50002 / 50001). Это ЛОКАЛЬНЫЕ порты на машине игрока — не
    путать с портом сервера знакомств.
  peerHost() / peerPortForClient() / peerPortForHost()
    Настройки СТАТИЧЕСКОГО (не через интернет, без сервера знакомств) пути
    — фиксированный IP и порт пира, нужны только для локального тестирования
    на одной машине или в одной локальной сети напрямую.
  internetPlay()
    true/false — включён ли путь "через интернет" (сервер знакомств + пробив
    NAT) по умолчанию. Это лишь НАЧАЛЬНОЕ значение чекбокса в GUI — игрок
    может переключить его на экране "Открыть для сети" в любой момент (см.
    3.3), тут же значение — просто стартовая точка при запуске игры.
  rendezvousHost() / rendezvousPort()
    Адрес и порт сервера знакомств. По умолчанию — конкретный IP
    (91.146.31.165) и порт 51000.
  roomCode()
    Код комнаты для джойнера (если он предпочитает передать код флагом
    запуска, а не вводить в GUI-поле). По умолчанию — пустая строка.
  maxPlayers()  [добавлено при реализации фичи "несколько игроков в комнате"]
    Максимум игроков в комнате, которую откроет хост. По умолчанию 4,
    допустимый диапазон 1..32 (совпадает с ограничением на сервере
    знакомств, см. 6.3, чтобы значение не "срезалось" молча при передаче на
    сервер).

Приватные методы (внутренняя кухня чтения настроек — используются только
самими методами выше, снаружи класса не видны, см. [Г2] про private):
  stringValue(String key, String defaultValue)
    Базовый метод чтения ОДНОЙ настройки как строки. Порядок проверки:
      1. System.getProperty("peercraft." + key) — это Java system property,
         именно то, что задаётся флагом -D при запуске JVM.
      2. Если пусто — System.getenv("PEERCRAFT_" + toEnvName(key)) —
         переменная окружения ОС.
      3. Если и там пусто — defaultValue.
    .isBlank() [Г34] — стандартный метод строки в Java, проверяет "пустая
    строка или состоит только из пробелов". .trim() убирает пробелы по
    краям.
  intValue(String key, int defaultValue)
    Просто вызывает intValueInRange(key, defaultValue, 0, 65535) — то есть
    "число, допустимое как номер сетевого порта".
  intValueInRange(String key, int defaultValue, int min, int max)
    Общий парсер целого числа с проверкой диапазона: берёт строку через
    stringValue, пытается превратить в int через Integer.parseInt(...)
    внутри try/catch[Г12] (если это не число — NumberFormatException,
    ловится, пишется предупреждение, возвращается значение по умолчанию).
    Если число распарсилось, но вне диапазона [min, max] — тоже
    предупреждение и значение по умолчанию. Этот метод я (при реализации
    лимита игроков) выделил из старого intValue, чтобы переиспользовать
    для maxPlayers() с диапазоном 1..32, а не только для портов 0..65535.
  boolValue(String key, boolean defaultValue)
    Читает строку через stringValue и сравнивает (без учёта регистра) со
    строкой "true".
  toEnvName(String key)
    Превращает имя настройки из "camelCase" (например "maxPlayers") в
    "UPPER_SNAKE_CASE" ("MAX_PLAYERS") — таков принятый стиль имён у
    переменных окружения в целом (не только в этом проекте). Идёт по каждой
    букве строки[Г35]; если буква заглавная — сначала добавляет "_", затем
    саму букву в верхнем регистре.


--------------------------------------------------------------------
2.2 net.peercraft.client.PeerCraftHostOptions
Файл: fabric-example-mod/src/client/java/net/peercraft/client/PeerCraftHostOptions.java
--------------------------------------------------------------------
Роль: крошечный класс-"глобальная переменная" (два публичных static-поля,
без методов вообще) — хранит ТЕКУЩЕЕ (может меняться прямо в GUI) состояние
двух настроек хоста: "играть через интернет" (галочка) и "макс. игроков"
(степпер). В отличие от PeerCraftConfig (который читает значения ОДИН РАЗ из
флагов запуска и больше не меняется), это поле реально меняется во время
игры, когда игрок трогает GUI-виджеты на экране "Открыть для сети".

Поля:
  internetPlayRequested — volatile[Г16] boolean, стартует со значения
  PeerCraftConfig.internetPlay() (то есть с флага запуска), но потом может
  быть переключено чекбоксом на экране.
  maxPlayers — volatile int, аналогично стартует с PeerCraftConfig.maxPlayers().

Почему volatile: значение читается и пишется из разных потоков[Г15]
(GUI-поток Minecraft меняет его по клику, а сетевой код читает его в момент
нажатия "Открыть для сети") — volatile гарантирует, что поток-читатель
увидит самое свежее записанное значение, а не устаревшую закешированную
копию.

Конструктор приватный (private PeerCraftHostOptions() {}) — намеренно,
чтобы никто не создал экземпляр этого класса: он весь состоит из
static-полей, объект тут не нужен в принципе (см. [Г5] и [Г2]).



====================================================================
3. GUI И MIXIN'Ы
====================================================================
Прежде чем читать этот раздел — важно понять, ЧТО ТАКОЕ MIXIN [Г29]. Коротко:
Minecraft — чужая, закрытая игра, мод не может просто взять и отредактировать
её исходный код. Mixin — это библиотека, которая на этапе загрузки игры
"впрыскивает" код мода внутрь чужого метода (например, в начало, в конец или
вместо какой-то строки), не трогая физически файлы игры. Все классы в этом
разделе с именем на "...Mixin" — это ровно такие "вклейки" в код Minecraft.

--------------------------------------------------------------------
3.1 net.peercraft.client.mixin.TitleScreenMixin
Файл: fabric-example-mod/src/client/java/net/peercraft/client/mixin/TitleScreenMixin.java
--------------------------------------------------------------------
Роль: добавляет кнопку "PeerCraft: Join" на титульный экран игры (тот самый
первый экран с "Одиночная игра"/"Множество игроков"/"Выход").
Аннотация @Mixin(TitleScreen.class) [Г29] говорит: "этот класс — вклейка в
класс TitleScreen (титульный экран) самого Minecraft".
Класс abstract[Г8] и extends[Г8] Screen — это техническое требование
механизма Mixin (вклейка "притворяется" подклассом того же класса, в который
встраивается, чтобы иметь доступ к его защищённым полям вроде this.width).

Методы:
  peercraft$addJoinButton(CallbackInfo ci)
    Аннотация @Inject(method = "init", at = @At("TAIL")) [Г29] означает:
    "выполни этот код В КОНЦЕ метода init() оригинального TitleScreen" (то
    есть после того, как ванильный экран уже расставил все свои кнопки).
    Сначала проверяет режим мода (PeerCraftConfig.mode()) — если "disabled"
    или "host", кнопка вообще не добавляется (хосту незачем присоединяться
    к чужой комнате с титульного экрана). Иначе — добавляет кнопку через
    Button.builder(...) [Г31, паттерн Builder] с текстом "PeerCraft: Join";
    при клике (лямбда `b -> this.minecraft.setScreen(new PeerCraftJoinScreen(this))`
    [Г13]) открывается экран ввода кода комнаты (см. 3.2), передавая ему
    ссылку на "себя" (this) как "тот экран, куда вернуться по кнопке Назад".


--------------------------------------------------------------------
3.2 net.peercraft.client.gui.PeerCraftJoinScreen
Файл: fabric-example-mod/src/client/java/net/peercraft/client/gui/PeerCraftJoinScreen.java
--------------------------------------------------------------------
Роль: полноценный самостоятельный экран (не вклейка, а обычный extends[Г8]
Screen класс "с нуля") — "Присоединиться по коду". Именно тут игрок вводит
6-значный код комнаты и жмёт "Подключиться".

Поля:
  lastScreen — экран, куда вернуться по кнопке "Назад".
  roomCodeBox, overrideBox — текстовые поля ввода (EditBox — стандартный
  виджет Minecraft для ввода текста): код комнаты и, опционально, свой
  адрес сервера знакомств.
  connectButton, overrideToggleButton — кнопки.
  overrideVisible — boolean, видно ли сейчас поле "переопределить адрес".
  statusMessage — текст статуса, который рисуется внизу экрана (обновляется
  асинхронно по мере хода подключения).
  listener — приватное final[Г4] поле типа P2PBridge.ConnectListener
    (интерфейс[Г7] с тремя методами: onStatus/onConnected/onFailed).
    Реализовано как анонимный класс[Г32] прямо на месте (new
    P2PBridge.ConnectListener() { ... }) — то есть безымянный класс,
    реализующий интерфейс, созданный один раз только для этого экрана.
    Каждый метод внутри просто перекидывает выполнение на клиентский поток
    игры через runOnClientThread(...), потому что сетевые колбэки[Г13]
    вызываются из ФОНОВОГО потока (рендер и изменение GUI обязаны идти
    только из главного/клиентского потока Minecraft — иначе игра может
    упасть или показать "мигающий"/повреждённый интерфейс).

Методы:
  init() (переопределяет метод Screen — вызывается автоматически при
  открытии экрана)
    Создаёт и расставляет по вертикали все виджеты: поле кода комнаты
    (с подстановкой PeerCraftConfig.roomCode(), если оно задано флагом
    запуска), кнопку "Подключиться" (вызывает onConnect() по клику), кнопку
    "Переопределить адрес сервера" (вызывает toggleOverride()), скрытое по
    умолчанию поле адреса сервера и кнопку "Назад" (возвращает на
    lastScreen).
  toggleOverride()
    Переключает overrideVisible и прячет/показывает overrideBox, меняет
    текст кнопки-переключателя.
  onConnect()
    Обработчик клика "Подключиться". Читает код комнаты, убирает пробелы и
    приводит к верхнему регистру[toUpperCase]. Если поле пустое — просто
    показывает подсказку и выходит. Далее вычисляет адрес сервера
    знакомств: либо из overrideBox (если он открыт и не пуст, парсится
    через parseHostPort), либо берёт из PeerCraftConfig по умолчанию.
    Деактивирует кнопку (чтобы нельзя было нажать повторно, пока идёт
    подключение) и вызывает главный сетевой метод —
    P2PBridge.INSTANCE.startClientViaRendezvous(code, host, port, listener)
    (см. 4.7).
  record HostPort(String host, int port)
    Маленький record[Г10] — просто пара "хост+порт" для удобной передачи
    двух значений одним объектом.
  static parseHostPort(String text, int defaultPort)
    Разбирает строку вида "адрес:порт" (ищет последнее двоеточие через
    lastIndexOf(':')). Если после двоеточия — не число (NumberFormatException
    внутри try/catch), считает, что всё это — просто хост без явного порта
    (например, IPv6-адрес мог содержать двоеточия не как разделитель порта).
  runOnClientThread(Runnable action)
    Обёртка над Minecraft.getInstance().execute(action) — ставит переданный
    кусок кода в очередь на выполнение именно в клиентском/рендер-потоке
    игры (см. пояснение про listener выше).
  stillOnThisScreen()
    Проверка "а игрок ещё на этом экране, или уже ушёл (Назад/Esc) пока шёл
    асинхронный сетевой ответ?" — сравнивает Minecraft.getInstance().screen
    (текущий показанный экран) с this. Нужно, чтобы отложенный колбэк не
    попытался обновить статус на экране, который уже не отображается.
  updateStatus(String message) / handleFailed(String reason)
    Обновляют statusMessage (текст под полями) — если экран ещё активен
    (см. stillOnThisScreen()). handleFailed дополнительно снова включает
    кнопку "Подключиться" (active = true), чтобы можно было попробовать
    ещё раз.
  handleConnected()
    Вызывается, когда пробив NAT и вся цепочка успешно завершились. Берёт
    порт локального прокси через P2PBridge.INSTANCE.getProxyPort() и
    программно, БЕЗ показа стандартного экрана "Прямое подключение",
    запускает подключение ванильного клиента к 127.0.0.1:<этот порт> через
    ConnectScreen.startConnecting(...) — то есть с точки зрения обычного
    сетевого кода Minecraft это выглядит как подключение к самому обычному
    серверу, просто он "живёт" на локальной машине и на самом деле

    важен технически — иначе Minecraft считает попытку подключения
    "миграцией/трансфером" с существующего сервера и отклоняет её.
  render(GuiGraphics graphics, int mouseX, int mouseY, float partialTick)
    Стандартный метод отрисовки экрана (вызывается КАЖДЫЙ КАДР игры) —
    рисует фон, все виджеты (через super.render — вызов родительской
    реализации[Г6]) и две центрированные строки текста: заголовок и текущий
    statusMessage.

  onOpenToLan(GameType gameMode, boolean cheatsAllowed, int port, CallbackInfoReturnable<Boolean> cir)
    @Inject(method = "publishServer", at = @At("RETURN")) — выполняется

    @Inject(method = "stopServer", at = @At("HEAD")) — срабатывает в самом

====================================================================
4. ЯДРО СЕТИ — УРОВЕНЬ 1: "МОСТ" (RELAY)
====================================================================
Общая идея всего этого раздела: настоящий Minecraft общается по TCP
("надёжный" протокол с гарантией доставки и порядка байт). Но мод не может
напрямую пробросить TCP через интернет без открытия портов на роутере —
поэтому он заворачивает TCP-поток в свои собственные UDP-пакеты (менее
надёжные, зато NAT можно "пробить", см. раздел 5) и пересобирает поток
байт на другой стороне. Классы этого раздела реализуют именно это
заворачивание/разворачивание.

--------------------------------------------------------------------
4.1 net.peercraft.network.p2p.FramedPacket
Файл: fabric-example-mod/src/main/java/net/peercraft/network/p2p/FramedPacket.java
--------------------------------------------------------------------
Роль: формат "конверта" для каждого UDP-пакета мода. final[Г4] класс — не
предполагает наследования. Каждый пакет имеет заголовок:
  [версия:1 байт][тип:1 байт][флаги:1 байт][sessionId:8 байт][seq:8 байт][...данные]
(HEADER_SIZE = 1+1+1+8+8 = 19 байт, дальше идут сами данные переменной
длины). sessionId — случайное число, уникальное для одного "логического"
TCP-соединения (пары клиент-хост); seq — порядковый номер куска данных
внутри этой сессии (нужен для восстановления правильного порядка, т.к. UDP
пакеты могут прийти не в том порядке, в котором были отправлены, или вообще
потеряться).

Публичные static-константы:
  VERSION (=2) — если формат заголовка когда-то поменяется, номер версии
  вырастет, и decode() ниже сразу отбросит "старые" или "чужие" пакеты
  вместо того, чтобы попытаться неправильно их разобрать.
  TYPE_DATA (=0) / TYPE_NACK (=1) — тип пакета: обычные данные или
  "запрос повторной отправки" (см. ReorderBuffer, 4.2).
  FLAG_FIN (=0x1) — битовый флаг "это последний пакет в потоке" (сигнал
  конца соединения).
  HEADER_SIZE — размер заголовка в байтах (объяснено выше).

Приватный конструктор FramedPacket(...) — принимает все поля сразу,
используется только внутри самого класса (объекты создаются либо через
decode(), либо неявно не создаются вовсе — только encode-функции возвращают
готовый byte[]).

Методы:
  private static encodeFrame(byte type, long sessionId, long seq, byte flags, byte[] payload)
    Общая внутренняя функция сборки байтов: создаёт ByteBuffer[Г22] нужного
    размера (заголовок + длина данных) и последовательно "кладёт" в него
    все поля через .put()/.putLong() — ByteBuffer сам следит за текущей
    позицией записи. .array() в конце достаёт итоговый массив байт.
  static encode(long sessionId, long seq, byte flags, byte[] payload)
    Публичная обёртка над encodeFrame с типом TYPE_DATA — "закодировать
    обычный кусок данных".
  static encode(long sessionId, long seq, byte[] payload)
    Перегрузка[overload — в Java можно иметь несколько методов с одним
    именем, но разным набором параметров] того же метода без явного flags
    — по умолчанию 0 (флагов нет).
  static encodeNack(long sessionId, long missingSeq)
    Собирает служебный пакет TYPE_NACK — "у тебя есть пропуск, повтори
    seq=missingSeq, пожалуйста". Сам номер missingSeq кладётся как payload
    (8 байт через отдельный ByteBuffer).
  static decode(byte[] data, int length)
    Обратная операция — разбирает сырые байты обратно в объект FramedPacket.
    Если байт меньше, чем HEADER_SIZE, или первый байт (версия) не совпадает
    с VERSION — возвращает null (это "не наш" или битый пакет). Иначе читает
    поля по порядку той же последовательностью, что и encodeFrame их писал,
    и остаток буфера (data.length - HEADER_SIZE байт) копирует как payload.
  type() / isFin() / sessionId() / seq() / payload() / nackSeq()
    "Геттеры" — простые методы чтения приватных полей объекта, которые сам
    Java не генерирует автоматически (в отличие от record, см. [Г10] — этот
    класс написан вручную как обычный class, не record, поэтому геттеры
    здесь пишутся руками). isFin() проверяет бит через побитовое И
    (flags & FLAG_FIN) != 0. nackSeq() имеет смысл только когда type()
    равен TYPE_NACK — читает 8 байт из payload как одно число.

4.2 net.peercraft.network.p2p.ReorderBuffer
Файл: fabric-example-mod/src/main/java/net/peercraft/network/p2p/ReorderBuffer.java
--------------------------------------------------------------------
Роль: пересборка потока байт из отдельных пронумерованных (seq) кусков
обратно в правильном порядке — по ОДНОЙ штуке на каждое направление каждой
сессии (у хоста — свой ReorderBuffer на каждого джойнера для приёма от него;
у джойнера — свой на приём от хоста).

Поля:
  MAX_PENDING (=128) — сколько кусков можно держать в ожидании "дыры" перед
  тем, как считать сессию сломанной (защита от неограниченного роста памяти).
  GAP_TIMEOUT_MILLIS (=3000) — если "дыра" (пропущенный кусок) не
  закрывается 3 секунды подряд — сессия считается сломанной.
  NACK_DEBOUNCE_MILLIS (=200) — не слать повторный NACK чаще, чем раз в
  200мс на одну и ту же дыру (чтобы не заспамить сеть повторными запросами,
  пока предыдущий NACK ещё, возможно, летит по проводу).
  pending — TreeMap<Long, byte[]> [Г19] — коллекция "кусков не по порядку",
  автоматически отсортированная по ключу (номеру seq), что удобно для
  функций типа "дай мне самый маленький из ожидающих".
  expectedSeq — какой seq мы ждём следующим.
  expectedSince / lastNackSentAt — метки времени для таймаутов/дебаунса.

Методы:
  synchronized[Г17] accept(long seq, byte[] payload)
    Главный метод — вызывается на каждый входящий кусок данных. synchronized
    означает, что если два потока одновременно вызовут этот метод на одном
    и том же объекте, второй подождёт, пока первый закончит — иначе
    внутренние счётчики могли бы испортиться при параллельном доступе.
    Логика:
      • seq < expectedSeq — это старьё/дубликат, уже было доставлено раньше
        — возвращает Result.none() (ничего делать не надо).
      • seq > expectedSeq — кусок пришёл "из будущего" (раньше своей
        очереди): кладём в pending (если там ещё нет места — бросаем
        SessionBrokenException, переполнение буфера). Проверяем, не
        истёк ли GAP_TIMEOUT_MILLIS с момента, когда мы впервые начали
        ждать expectedSeq — если истёк, тоже SessionBrokenException
        (сессия окончательно сломана, дальше её тянуть бессмысленно).
        Иначе, если с прошлого NACK прошло больше NACK_DEBOUNCE_MILLIS —
        возвращаем Result.request(expectedSeq) — "попроси у отправителя
        именно этот недостающий кусок ещё раз".
      • seq == expectedSeq — то, чего мы и ждали! Добавляем payload в
        выходной буфер (ByteArrayOutputStream — растущий массив байт[Г35]),
        увеличиваем expectedSeq, и дальше в цикле[while] проверяем: а
        вдруг СЛЕДУЮЩИЙ по номеру кусок уже лежит в pending (пришёл
        заранее, пока мы ждали текущий)? Если да — сразу же его тоже
        забираем и приклеиваем, и так далее, пока цепочка не прервётся.
        В конце сбрасываем таймеры и возвращаем Result.deliver(...) — весь
        собранный к этому моменту непрерывный кусок данных.
  class Result (вложенный static[Г33] класс)
    Простой контейнер результата: либо "нечего делать" (none()), либо "вот
    готовые данные, отдай их дальше по TCP" (deliver(data)), либо "попроси
    повторить этот seq" (request(seq)). Приватный конструктор + три
    именованных static-фабричных метода — это распространённый в Java
    приём вместо public-конструктора с неочевидным набором аргументов.
  class SessionBrokenException extends RuntimeException
    Собственный класс исключения[Г12] — сигнал "с этой сессией всё, дальше
    можно только закрыть соединение". RuntimeException (в отличие от
    checked-исключений вроде IOException) не обязывает вызывающий код
    писать try/catch — но в P2PBridge его всё равно ловят явно, чтобы
    аккуратно закрыть соединение, а не уронить весь поток.

4.3 net.peercraft.network.p2p.PeerAddress
Файл: fabric-example-mod/src/main/java/net/peercraft/network/p2p/PeerAddress.java
--------------------------------------------------------------------
Роль: маленький record[Г10] — пара (IP-адрес, порт), используется как
"адрес одного конкретного пира" — и, что важно, как КЛЮЧ в Map[Г19] внутри
P2PBridge, когда нужно различать разных подключённых джойнеров у хоста.
Я добавил этот класс при реализации функции "несколько игроков в комнате" —
раньше в мосту было только два отдельных поля (targetIp: String, targetPort:
int) на ВЕСЬ мост сразу, что физически не позволяло различать разных
пиров. Record record автоматически даёт методам equals()/hashCode() —
именно поэтому его удобно использовать ключом в Map: две записи PeerAddress
с одинаковым host и port считаются "одинаковым ключом".

Методы:
  ip() — дополнительный метод (не входит в автогенерацию record), просто
  короткая обёртка над host.getHostAddress() — превращает объект InetAddress
  в обычную строку вида "192.168.0.5", т.к. многие методы более старого кода
  (P2PSender.sendData) ожидают IP именно строкой, а не объектом.
(host() и port() — геттеры, сгенерированы автоматически самим record'ом,
отдельно в файле не написаны.)

4.5 net.peercraft.network.p2p.P2PSender
Файл: fabric-example-mod/src/main/java/net/peercraft/network/p2p/P2PSender.java
--------------------------------------------------------------------
Роль: тонкая обёртка над стандартным Java-классом DatagramSocket[Г23]
(объект "UDP-розетка", умеющая слать датаграммы) — просто удобный метод
"отправь эти байты туда-то".

Поле: socket — та самая "розетка". ВАЖНО: сокет создаётся СНАРУЖИ (передаётся
в конструктор), а не внутри этого класса — и это не случайно: P2PSender и
P2PReceiver (4.6) обязаны использовать ОДИН И ТОТ ЖЕ сокет (то есть слать и
принимать с одного и того же локального порта), иначе "пробитие" NAT (см.
раздел 5) окажется бесполезным — роутер запомнил один порт как "открытый"
для конкретного удалённого адреса, а мод слал бы данные с другого.

Методы:
  Конструктор P2PSender(DatagramSocket socket)
    Сохраняет переданный сокет, и если он не null — пытается увеличить его
    буфер отправки (setSendBufferSize) — при ошибке просто логирует, не
    падает (мелкая деталь производительности, не критично для работы).
  sendData(byte[] data, String ip, int port)
    Проверяет, что данные не превышают MAX_UDP_PAYLOAD_SIZE (65507 байт —
    это теоретический максимум одной UDP-датаграммы). Превращает строку ip
    в объект InetAddress через InetAddress.getByName(ip) (может бросить
    UnknownHostException, если строка — не валидный адрес; ловится).
    Собирает DatagramPacket (данные + адрес назначения + порт) и вызывает
    socket.send(packet). Если сокет null или уже закрыт — просто логирует
    ошибку и молча выходит, БЕЗ исключения (это важная деталь — см. ответ
    про "что будет, если порт занят" выше в переписке: сбой отправки не
    останавливает мод и не бросает исключение наружу).

4.6 net.peercraft.network.p2p.P2PReceiver
Файл: fabric-example-mod/src/main/java/net/peercraft/network/p2p/P2PReceiver.java
--------------------------------------------------------------------
Роль: приёмная часть UDP-сокета. В отличие от отправки, приём организован
через ДВА отдельных потока[Г15], чтобы медленная обработка пакета никогда не
мешала вовремя вычитывать новые данные из операционной системы (иначе ОС
начнёт молча терять входящие пакеты, если буфер переполнится).

Поля:
  socket — DatagramSocket, тот самый общий сокет.
  running — volatile boolean, флаг "приёмник ещё активен".
  listenThread / processingThread — два потока (см. ниже).
  processingQueue — BlockingQueue<IncomingDatagram> [Г19] — потокобезопасная
  очередь ограниченного размера (2048), связывающая два потока: поток чтения
  сокета кладёт сюда пакеты, поток обработки их оттуда забирает.
  INSTANCE — публичный static final экземпляр-синглтон (объявлен, но
  реально используется именно экземпляр внутри P2PBridge, а не это поле —
  небольшой исторический остаток кода, не критично).

Методы:
  start(int port)
    Сначала зовёт stop() (на случай, если приёмник уже был запущен раньше —
    чистый перезапуск). Создаёт DatagramSocket(port) — "занимает" этот UDP
    порт на всех сетевых интерфейсах машины (0.0.0.0). Запрашивает у ОС
    больший буфер приёма (4 МБ — линуксовый буфер по умолчанию слишком мал
    для всплесков крупных пакетов при загрузке чанков мира). Запускает два
    daemon-потока[Г15] — listenLoop() и processingLoop(). Если DatagramSocket(port)
    бросает SocketException (порт занят) — ловит, пишет ERROR в лог,
    возвращает false, ничего не запускает (см. подробный разбор этого
    сценария в переписке выше).
  private listenLoop()
    Работает в отдельном потоке, пока running==true: socket.receive(packet)
    — блокирующий вызов, "жди, пока придёт хоть один пакет". Как только
    пришёл — сразу копирует байты в новый массив и кладёт в processingQueue
    (.offer(...) — попытка положить, не блокируясь; если очередь
    переполнена — пакет теряется с предупреждением в лог, но поток чтения
    сокета НИКОГДА не блокируется и не замедляется — специально, чтобы ОС
    не начала терять пакеты на самом сокете).
  private processingLoop()
    Другой поток: в цикле забирает из очереди по одному пакету
    (.take() — блокирующий вызов "жди, пока что-то появится") и передаёт его
    в P2PBridge.INSTANCE.handleIncomingPacket(...) (см. 4.7) — вот тут уже
    происходит вся "тяжёлая" логика разбора пакета, декодирования,
    маршрутизации.
  getBoundPort()
    Возвращает реальный номер порта, на котором сокет сейчас слушает (0,
    если сокет не создан/закрыт).
  getSocket()
    Отдаёт наружу сам объект DatagramSocket — именно это использует
    P2PSender, чтобы слать с ТОГО ЖЕ сокета (см. пояснение в 4.5).
  stop()
    Останавливает всё: выставляет running=false, закрывает сокет (что само
    по себе разбудит блокирующий socket.receive() в listenLoop() с
    исключением, которое тихо игнорируется, т.к. running уже false),
    прерывает processingThread (.interrupt()) и очищает очередь.

4.7 net.peercraft.network.proxy.LocalProxy
Файл: fabric-example-mod/src/main/java/net/peercraft/network/proxy/LocalProxy.java
--------------------------------------------------------------------
Роль: работает ТОЛЬКО на джойнере. Это обычный локальный TCP-сервер на
127.0.0.1 (не виден снаружи машины), к которому подключается настоящий
клиент Minecraft (как будто это самый обычный сервер) — а на самом деле
LocalProxy просто перекладывает байты в UDP-мост (P2PBridge) и обратно.

Поля:
  serverSocket — ServerSocket[Г23] — "слушающая" TCP-розетка, принимающая
  входящие подключения (используется только на этой локальной машине).
  activeClientSocket / clientOut — текущее реальное соединение с локальным
  MC-клиентом и поток для записи ответов в него.
  running / boundPort — статус и фактический порт.
  p2pBridge — final ссылка на мост, которому передаются данные.

Методы:
  Конструктор LocalProxy(P2PBridge p2pBridge) — просто сохраняет ссылку.
  start(int port)
    Если уже запущен — предупреждение и выход. Иначе запускает отдельный
    daemon-поток[Г15], в котором выполняется runProxy(port) (сам start()
    возвращается сразу, не дожидаясь реального бинда порта — асинхронно).
  private runProxy(int port)
    Пытается создать ServerSocket(port, 50, InetAddress.getLoopbackAddress())
    — "слушай именно на 127.0.0.1, максимум 50 ожидающих в очереди
    подключений". Если порт занят — IOException (конкретно BindException),
    ловится, пишется подробный ERROR (см. разбор сценария "порт 25566
    занят" в переписке выше). Если бинд успешен — в цикле[while(running)]
    бесконечно ждёт serverSocket.accept() (блокирующий вызов — "жди
    следующее TCP-подключение"). Как только реальный MC-клиент
    подключился — зовёт p2pBridge.beginClientSession(clientSocket) (просит
    мост завести новый sessionId) и handleClient(clientSocket, sessionId).
    После того как handleClient вернётся (клиент отключился) — цикл
    продолжается, снова ждёт accept() (то есть прокси остаётся живым и
    готовым принять СЛЕДУЮЩЕЕ подключение — важно для сценария "вышел из
    одной комнаты, зашёл в другую", разобранного в переписке выше).
    В finally[Г12] — что бы ни случилось — всё аккуратно закрывается.
  private handleClient(Socket socket, long sessionId)
    Сохраняет socket как "текущий активный клиентский сокет". В цикле
    читает байты, пришедшие от локального MC-клиента (in.read(buffer)),
    и на каждую порцию зовёт p2pBridge.sendProxyDataToP2P(sessionId, data)
    — отправляет их в UDP-мост. Когда чтение возвращает -1 (клиент закрыл
    соединение) или бросает исключение — цикл заканчивается, в finally
    закрывается сокет и вызывается p2pBridge.endClientSession(sessionId) —
    сообщает мосту "эта сессия точно завершена".
  synchronized[Г17] sendToClient(byte[] data)
    Вызывается мостом, когда пришёл ответ от хоста — пишет байты обратно в
    сокет реального локального MC-клиента (если он ещё существует и не
    закрыт). synchronized — на случай, если два потока моста одновременно
    попытаются что-то записать этому же клиенту.
  disconnectClient()
    Принудительно закрывает текущее клиентское соединение (например, если
    мост обнаружил, что сессия сломана — см. ReorderBuffer.SessionBrokenException).
  private closeClientSocket() / closeServerSocket()
    Аккуратное закрытие сокетов с игнорированием возможных исключений при
    закрытии (закрытие уже закрытого сокета — не ошибка, которую стоит
    показывать пользователю).
  isRunning() / getBoundPort() / stop()
    Простые методы состояния и полной остановки прокси (например, при
    выходе из игры или когда хост открывает мир для LAN и глушит свой
    собственный прокси, оставшийся от предыдущей роли джойнера).

4.8 net.peercraft.network.p2p.P2PBridge   ***ГЛАВНЫЙ КЛАСС МОДА***
Файл: fabric-example-mod/src/main/java/net/peercraft/network/p2p/P2PBridge.java
--------------------------------------------------------------------
Роль: центральный "мозг" всей сетевой части. Один-единственный объект на
весь мод (паттерн Singleton[Г3] — INSTANCE, публичное static final поле,
конструктор приватный, чтобы никто больше не создал второй экземпляр).
Умеет работать в ДВУХ ролях одновременно невозможных, но переключаемых:
роль ХОСТА (принимает подключения от нескольких джойнеров, пересылает их
TCP-байты в свой локальный Minecraft-сервер) и роль ДЖОЙНЕРА (общается
ровно с одним хостом).

--- Поля ---
  receiver / sender — текущие P2PReceiver/P2PSender (пересоздаются при
  каждом restartReceiver(...), см. ниже).
  proxy — LocalProxy (используется только ролью джойнера).
  clientTargetPeer — volatile PeerAddress — ТОЛЬКО для роли ДЖОЙНЕРА: адрес
  единственного хоста, с которым сейчас идёт разговор.
  localMinecraftPort — порт локального встроенного MC-сервера (используется
  только ролью хоста — это порт, на который мост сам подключается по TCP
  внутри своей же машины, чтобы дотянуться до игры).
  isHost — обычный (не volatile) boolean, определяющий текущую роль.
  maxPlayers — volatile int — лимит игроков в комнате (используется только
  хостом).
  hostConnectionsBySessionId / hostConnectionsByAddress — две
  ConcurrentHashMap[Г18,Г19] (потокобезопасные словари без блокировок для
  большинства операций) — ТОЛЬКО для роли ХОСТА: каждый подключённый
  джойнер описывается ОДНИМ объектом HostConnection (см. ниже), но найти
  этот объект можно двумя способами — либо по числовому sessionId (это
  "главный", доверенный ключ — ровно тот же принцип, что был всегда в
  протоколе), либо по сетевому адресу пира (для быстрой проверки "сколько
  сейчас реально подключено" и "разрешено ли этому адресу открывать новую
  сессию"). Это ключевое изменение, которое я внёс, реализуя фичу
  "несколько игроков в комнате" — раньше здесь было ровно ОДНО поле
  currentHostConnection на весь мост, то есть второй подключившийся игрок
  физически обрывал первого.
  authorizedPeers — Set<PeerAddress> [Г19] (множество — коллекция без
  повторов, как список "разрешённых адресов") — тоже только для хоста:
  адрес попадает сюда ТОЛЬКО после того, как для него реально успешно
  прошёл пробив NAT (hole punching). Это защитный список: без него
  ЛЮБОЙ, кто просто угадает UDP-порт хоста и пришлёт правильно
  сформированный "начальный" пакет, мог бы открыть себе TCP-сессию к
  локальному Minecraft-серверу хоста, вообще не проходя пробив NAT и не
  зная кода комнаты — я закрыл эту дыру, добавляя поддержку нескольких
  игроков.
  activePunches — Map<PeerAddress, PunchCoordinator> — тоже только хост:
  список СЕЙЧАС идущих попыток пробива NAT, по одной на каждого
  потенциального джойнера — принципиально не единственный слот (как было
  раньше), т.к. иначе второй подошедший игрок отменял бы попытку пробива к
  первому.
  currentClientSession — volatile ClientSession — используется только
  ролью джойнера (джойнер всегда общается ровно с одним хостом, поэтому
  тут одно поле — это правильно и не менялось).
  rendezvousListener — volatile RawPacketListener — используется ТОЛЬКО
  ролью джойнера во время поиска/пробива к хосту (у хоста для этого теперь
  свой отдельный activePunches, см. выше).
  hostRendezvousClient — volatile RendezvousClient — постоянное соединение
  хоста с сервером знакомств, живёт всю сессию хостинга.
  rendezvousClientBusy — AtomicBoolean[Г18] — защита от повторного клика
  "Подключиться" поверх уже идущей попытки (см. подробный разбор в
  переписке — endClientSession сбрасывает этот флаг).

--- Методы ---
  private P2PBridge() (конструктор)
    Приватный[Г2] — не позволяет создать второй экземпляр класса снаружи.
    Создаёт "пустой" receiver и sender (без реального сокета) — реальная
    инициализация происходит позже, в restartReceiver(...).

  startHost(int mcPort)
    СТАРЫЙ статический (без сервера знакомств) путь для роли ХОСТА —
    только для локального тестирования. Читает фиксированные peerHost/
    peerPort из конфига, запускает приёмник на hostUdpPort и сразу
    добавляет этот один статический адрес в authorizedPeers (иначе новый
    admission-контроль заблокировал бы даже этот единственный тестовый
    путь — раньше в этом месте был setTargetPeer(...), сейчас вместо него
    просто "разрешаем" этот адрес).

  startClient()
    Аналогично — старый статический путь для роли ДЖОЙНЕРА. Запускает
    приёмник на clientUdpPort и вызывает setClientTargetPeer(...) с
    фиксированным адресом из конфига.

  interface HostListener { onRoomCreated(...); onFailed(...); }
    Контракт "сообщи мне о ходе создания комнаты" — реализует GUI/чат-код
    (см. OpenToLanMixin, 3.4).

  static final HostListener LOGGING_HOST_LISTENER
    Реализация[Г32] по умолчанию, которая просто пишет в лог, а не в чат —
    используется, если вызывающий явно не передал свой HostListener.

  startHostViaRendezvous(int mcPort)
    Упрощённая перегрузка — вызывает трёхаргументную версию ниже с
    лимитом игроков 1 и логирующим листенером (используется только там,
    где явно не важен реальный лимит — на практике сейчас нигде не
    вызывается из GUI, GUI всегда передаёт настоящий maxPlayers).

  startHostViaRendezvous(int mcPort, int maxPlayers, HostListener listener)
    ГЛАВНАЯ точка запуска реальной интернет-игры со стороны хоста.
    Запоминает роль/порт/лимит, перезапускает приёмник. Определяет IP
    сервера знакомств (resolveRendezvousAddress()) — если не получилось
    (нет интернета/опечатка в адресе) — сразу сообщает об ошибке и выходит.
    Создаёт RendezvousClient (см. 5.2), сохраняет его в hostRendezvousClient
    (setHostRendezvousClient — заменяет предыдущего, если был, с отменой
    старого). Вызывает client.registerRoom(...), передавая:
      • maxPlayers,
      • this::currentPlayerCount — ссылку на метод[Г14] (а не значение) —
        RendezvousClient будет сам, при каждой отправке keepalive, ЗАНОВО
        спрашивать этот метод, сколько игроков подключено ПРЯМО СЕЙЧАС —
        это и есть механизм "освобождения места", когда игрок выходит;
      • колбэк "комната создана" (пишет в лог/зовёт listener.onRoomCreated),
      • анонимный MatchCallback: при успешном матче (onMatched) зовёт
        beginHostPunch(peer, token) (см. ниже), при ошибке — сообщает
        через listener.onFailed(...).

  private currentPlayerCount()
    Просто возвращает hostConnectionsByAddress.size() — количество СЕЙЧАС
    реально живых подключений джойнеров. Именно это число уходит на сервер
    знакомств каждые ~15 секунд (см. RendezvousClient.startKeepaliveLoop,
    5.2) — самое сердце фичи "живой счётчик мест".

  interface ConnectListener { onStatus(...); onConnected(); onFailed(...); }
    Контракт "сообщи мне о ходе подключения" для роли джойнера (реализует
    PeerCraftJoinScreen, см. 3.2).

  static final ConnectListener LOGGING_LISTENER
    Реализация по умолчанию — в лог, а не в GUI.

  startClientViaRendezvous()
    Упрощённая версия без параметров — берёт код комнаты/адрес сервера
    знакомств из PeerCraftConfig (используется, если не нужен интерактивный
    GUI — например, если код комнаты передан флагом запуска сразу).

  startClientViaRendezvous(String code, String rendezvousHost, int rendezvousPort, ConnectListener listener)
    ГЛАВНАЯ точка входа для роли ДЖОЙНЕРА. Если код пустой — сразу ошибка.
    Проверяет rendezvousClientBusy.compareAndSet(false, true) [Г18] —
    атомарная операция "если сейчас false, поставь true и верни true; если
    уже true — просто верни false, ничего не меняя" — это и есть защита от
    повторного клика (см. переписку). Если уже занято — сообщает об ошибке
    и выходит. Иначе оборачивает переданный listener в guardedListener
    (анонимный класс) — версия того же интерфейса, которая при onFailed
    ДОПОЛНИТЕЛЬНО сбрасывает rendezvousClientBusy обратно в false (чтобы
    неудачная попытка не блокировала все последующие). Дальше: если
    LocalProxy ещё не запущен (например, если этот же игрок только что
    сам был хостом и остановил свой прокси) — запускает его. Перезапускает
    приёмник на clientUdpPort. Определяет адрес сервера знакомств. Создаёт
    RendezvousClient, сохраняет в rendezvousListener (единственный слот —
    для джойнера это правильно). Зовёт client.joinRoom(code, ...) — при
    успешном матче зовёт beginClientPunch(...) (см. ниже).

  endClientSession(long sessionId)
    Вызывается LocalProxy, когда реальное TCP-соединение к нему закрылось.
    Если это была именно ТА сессия, что сейчас считается текущей — обнуляет
    currentClientSession. И, вне зависимости от совпадения sessionId, всегда
    сбрасывает rendezvousClientBusy в false — единственное честное место,
    откуда этот флаг может сброситься после УСПЕШНОГО подключения (см.
    подробный разбор сценария "вышел из комнаты A, зашёл в B" выше в
    переписке).

  private resolveRendezvousAddress() / resolveRendezvousAddress(String host, ConnectListener listener)
    Превращают текстовый адрес сервера знакомств в объект InetAddress через
    InetAddress.getByName(host) — при ошибке (UnknownHostException, ловится
    в try/catch) сообщают об ошибке через listener и возвращают null.

  private beginHostPunch(RendezvousProtocol.Address peer, long token)
    Запускает пробив NAT СО СТОРОНЫ ХОСТА для ОДНОГО конкретного джойнера
    (не отменяя пробив к другим). Сначала защитная проверка лимита:
    hostConnectionsByAddress.size() + activePunches.size() >= maxPlayers —
    если комната уже "полна" по факту (сервер знакомств должен был сам
    отклонить лишний JOIN раньше, это подстраховка на случай гонки —
    например, если два джойнера присоединились практически одновременно) —
    просто игнорирует матч и выходит. Иначе создаёт PunchCoordinator (см.
    5.3) с анонимным Callback: при успехе — убирает адрес из activePunches
    и добавляет в authorizedPeers (теперь этому адресу разрешено открыть
    TCP-сессию); при неудаче — просто убирает из activePunches. Кладёт
    новый PunchCoordinator в activePunches (Map.put(...) возвращает
    предыдущее значение по этому ключу, если было — если было, значит для
    ЭТОГО ЖЕ адреса уже шла попытка пробива, её явно отменяет через
    .cancel(), другие адреса не трогает). Запускает punch.start().

  private beginClientPunch(RendezvousProtocol.Address peer, long token, ConnectListener listener)
    То же самое, но для роли ДЖОЙНЕРА — единственная попытка за раз
    (переиспользует единственный слот rendezvousListener через
    setRendezvousListener). При успехе: очищает rendezvousListener,
    вызывает setClientTargetPeer(ip, port) (теперь весь исходящий трафик
    джойнера идёт на этот адрес хоста) и listener.onConnected(). При
    неудаче — тоже чистит слушателя и сообщает об ошибке.

  private setRendezvousListener(RawPacketListener newListener) / clearRendezvousListener()
    Меняют единственный слот джойнерской rendezvous-активности,
    ОБЯЗАТЕЛЬНО вызывая .cancel() у предыдущего значения перед заменой —
    иначе его фоновые потоки (например, keepalive) продолжали бы работать
    вечно без владельца.

  private setHostRendezvousClient(RendezvousClient newClient)
    Аналогично, но для отдельного слота "постоянного" RendezvousClient
    хоста.

  cancelRendezvous()
    Публичный метод — полностью останавливает ВСЮ rendezvous/punch-
    активность хоста: обнуляет hostRendezvousClient и rendezvousListener
    (через уже описанные сеттеры), затем в цикле[for] отменяет и удаляет
    КАЖДУЮ запись из activePunches, и очищает authorizedPeers целиком.
    Вызывается, когда хост закрывает свой мир (OpenToLanMixin.onStopServer)
    — чтобы комната перестала "жить" на сервере знакомств.

  private restartReceiver(int port)
    Останавливает старый receiver (если был), создаёт новый P2PReceiver и
    запускает его на указанном порту, затем пересоздаёт sender на СОКЕТЕ
    ИМЕННО ЭТОГО receiver'а (см. пояснение в 4.5 про общий сокет).

  startProxy(int port)
    Останавливает старый LocalProxy (если был) и запускает новый на
    указанном порту.

  private setClientTargetPeer(String ip, int port)
    Единственное место, где меняется clientTargetPeer — резолвит строку
    ip в InetAddress и сохраняет как PeerAddress. При ошибке резолва —
    логирует, ничего не меняет (адрес останется старым или null).

  beginClientSession(Socket socket)
    Вызывается LocalProxy на каждое новое TCP-подключение реального
    клиента: генерирует случайный[ThreadLocalRandom[Г18]] sessionId,
    создаёт новый ClientSession, сохраняет как текущий, возвращает
    sessionId вызывающему (LocalProxy передаёт его дальше во все
    последующие sendProxyDataToP2P для этого TCP-соединения).

  sendProxyDataToP2P(long sessionId, byte[] data)
    Вызывается LocalProxy на каждый прочитанный от реального клиента кусок
    байт. Проверяет, что переданный sessionId совпадает с текущей сессией
    (иначе — "эта сессия уже неактуальна", предупреждение и выход без
    отправки). Проверяет, что clientTargetPeer вообще задан. Зовёт
    sendChunked(...) (см. ниже) — режет данные на куски и шлёт по UDP.

  private sendEncoded(PeerAddress dest, byte[] framed)
    Самая нижняя точка фактической отправки — если адрес назначения не
    задан (null) или sender не готов — просто логирует и не шлёт. Иначе
    зовёт sender.sendData(framed, dest.ip(), dest.port()).

  private sendFramed(...) / sendFramedAndBuffer(...)
    sendFramed — кодирует один кусок через FramedPacket.encode(...) и
    сразу шлёт. sendFramedAndBuffer — то же самое, но ДОПОЛНИТЕЛЬНО
    сохраняет закодированные байты в retransmitBuffer (Map<seq, байты>,
    под synchronized-блоком[Г17] — доступ к этой карте может идти из
    разных потоков) — чтобы при получении NACK на этот seq можно было
    переслать РОВНО ТЕ ЖЕ байты заново, а не пересобирать их заново.

  private sendChunked(PeerAddress dest, long sessionId, AtomicLong outSeq, byte[] data, Map retransmitBuffer)
    Режет один большой массив байт (пришедший одним TCP-чтением) на куски
    не крупнее MAX_CHUNK_SIZE (=8000 байт — см. комментарий в коде: на
    некоторых машинах роутер/файрвол молча дропает UDP-пакеты больше
    ~16.3KB, 8000 — заведомо безопасный запас). Цикл do-while — минимум
    один кусок шлётся, даже если data пустой (например, пустой финальный
    FIN-пакет). outSeq.getAndIncrement() [Г18] — атомарно "дай текущее
    значение и увеличь на единицу" — гарантирует уникальные, по порядку
    идущие номера seq даже если бы метод дёргали из нескольких потоков
    сразу.

  private sendNack(PeerAddress dest, long sessionId, long missingSeq)
    Кодирует и шлёт служебный NACK-пакет через FramedPacket.encodeNack(...).

  private resendIfBuffered(PeerAddress dest, long sessionId, long seq, Map retransmitBuffer)
    Реакция на входящий NACK: ищет в буфере ретрансляции байты с этим seq
    (под synchronized — та же карта, что защищается в sendFramedAndBuffer).
    Если нашлись — пересылает их (sendEncoded). Если нет (уже "вытеснены"
    из ограниченного по размеру буфера — см. RETRANSMIT_BUFFER_CAPACITY)
    — просто пишет отладочный лог, ничего страшного не происходит (запрос
    просто останется без ответа, отправитель, скорее всего, уже и сам
    прошёл дальше по потоку).

  getProxy() / isProxyRunning() / getProxyPort()
    Простые методы чтения состояния LocalProxy.

  handleIncomingPacket(byte[] data, int length, InetAddress senderAddress, int senderPort)
    Вызывается P2PReceiver на КАЖДЫЙ входящий UDP-пакет (уже после того,
    как он вытащен из очереди приёма). Первым делом смотрит на самый
    первый байт: если это MAGIC-байт (0xE1) сервера знакомств — это НЕ
    игровой трафик, а служебный (REGISTER/JOIN/PEER_FOUND/PUNCH и т.д., см.
    раздел 5). Раздаёт[Г2] его: постоянному hostRendezvousClient (если он
    есть — он сам решит, свой это пакет или нет, по адресу отправителя);
    если сейчас роль хоста (isHost) — ВСЕМ активным попыткам пробива из
    activePunches (каждый PunchCoordinator сам фильтрует "не мой ли это
    случайно чужой пакет" по ожидаемому адресу+токену — раздать всем не
    страшно и не медленно, т.к. игроков мало); если роль джойнера — просто
    единственному rendezvousListener. Если ни один получатель не нашёлся —
    пишет отладочный лог (обычно это безобидный запоздавший пакет).
    Если магический байт НЕ совпал — это обычный игровой пакет: пробует
    FramedPacket.decode(...); если не получилось разобрать — предупреждение
    в лог и выход. Если получилось — в зависимости от роли зовёт
    handleHostIncoming(frame, new PeerAddress(senderAddress, senderPort))
    или handleClientIncoming(frame).

  private synchronized handleHostIncoming(FramedPacket frame, PeerAddress sender)
    Ключевая функция маршрутизации на стороне ХОСТА (переписана почти
    целиком при добавлении поддержки нескольких игроков — раньше тут была
    только одна проверка "совпадает ли sessionId с ЕДИНСТВЕННЫМ текущим
    подключением"). Логика по шагам:
      1. Ищет существующее подключение по frame.sessionId() в
         hostConnectionsBySessionId (это словарь по числовому id — главный,
         "доверенный" способ узнать сессию).
      2. Если это NACK-пакет — если подключение нашлось, зовёт
         resendIfBuffered(...) для него; в любом случае метод на этом
         заканчивается (NACK не несёт игровых данных).
      3. Если подключение по sessionId НАШЛОСЬ — проверяет, не поменялся
         ли реальный адрес отправителя (sender) по сравнению с сохранённым
         в подключении (conn.peerAddress) — если поменялся (например, у
         игрока роутер перевыбрал внешний порт посреди игры — редкий, но
         возможный случай) — переносит запись в hostConnectionsByAddress
         на новый адрес, обновляет поле в самом объекте. Затем передаёт
         пакет на доставку через deliverToHost(conn, frame).
      4. Если подключение НЕ найдено по sessionId — но у пакета seq != 0 —
         значит это не начало нового логического соединения, а середина
         какого-то уже неактуального/чужого потока — просто отбрасывает
         (никогда не "подхватывает" чужой поток на середине, чтобы не
         перепутать данные разных игроков).
      5. Если seq == 0 (это ДЕЙСТВИТЕЛЬНО начало новой сессии) — проверяет
         authorizedPeers.contains(sender) — если этого адреса там НЕТ (он
         не проходил пробив NAT!) — отбрасывает попытку с предупреждением
         в лог. Это и есть тот самый admission-контроль (защита от чужаков,
         см. описание поля authorizedPeers выше).
      6. Если адрес авторизован — проверяет, нет ли УЖЕ подключения от
         ЭТОГО ЖЕ адреса (hostConnectionsByAddress.get(sender)) — если есть
         (это переподключение ОДНОГО И ТОГО ЖЕ игрока, например,
         кратковременный обрыв связи и повторный коннект) — закрывает
         именно ЭТУ старую сессию (closeHostConnection), а НЕ трогает
         подключения остальных игроков (в этом и есть суть исправления
         "второй игрок обрывает первого" — теперь обрыв затрагивает только
         сессию ТОГО ЖЕ адреса, а не глобально всё).
      7. Открывает новое подключение через startNewHostConnection(...) и
         сразу доставляет в него первый пакет.

  private startNewHostConnection(long sessionId, PeerAddress peerAddress)
    Пытается открыть НАСТОЯЩИЙ TCP-сокет к локальному Minecraft-серверу
    (Socket("127.0.0.1", localMinecraftPort)) — это соединение мост держит
    от имени конкретного удалённого джойнера. При успехе создаёт объект
    HostConnection (см. ниже), кладёт его СРАЗУ в ОБЕ карты
    (hostConnectionsBySessionId и hostConnectionsByAddress), запускает
    отдельный daemon-поток listenMcResponses(conn) (он будет читать ответы
    от локального сервера и слать их по UDP этому конкретному игроку), и
    возвращает готовый объект. При ошибке подключения (сервер вдруг не
    отвечает) — логирует и возвращает null.

  private deliverToHost(HostConnection conn, FramedPacket frame)
    Пропускает payload пакета через ReorderBuffer конкретно ЭТОГО
    подключения (conn.inBuf.accept(...)) — если получившийся результат
    содержит готовые к отправке данные — пишет их прямо в TCP-сокет
    локального сервера (conn.mcOut.write(...) + flush()). Если результат
    просит переотправить какой-то seq — шлёт NACK именно этому игроку
    (по conn.peerAddress). Если ReorderBuffer решил, что сессия сломана
    (SessionBrokenException) или произошла обычная ошибка ввода-вывода —
    закрывает именно это подключение (closeHostConnection), не трогая
    остальные.

  private synchronized handleClientIncoming(FramedPacket frame)
    Зеркальная функция для роли ДЖОЙНЕРА (не менялась в рамках фичи
    "несколько игроков", т.к. у джойнера всегда одна сессия). Похожая
    логика: NACK — переотправить из буфера; если sessionId не совпадает с
    текущей ClientSession — отбросить как чужой/устаревший; иначе через
    ReorderBuffer собрать данные и передать их в LocalProxy.sendToClient(...).
    При сломанной сессии — обнулить currentClientSession и попросить
    LocalProxy разорвать соединение с реальным клиентом.

  private listenMcResponses(HostConnection conn)
    Фоновый поток на КАЖДОЕ подключение хоста к одному джойнеру: в цикле
    читает байты из локального Minecraft-сервера (conn.mcIn.read(...)) и
    на каждую порцию шлёт их этому конкретному игроку через sendChunked(
    conn.peerAddress, ...). Когда чтение завершается (-1 или исключение —
    сервер закрыл соединение с этим игроком, например, игрок вышел из
    мира) — в finally шлёт последний пустой пакет с флагом FLAG_FIN и
    закрывает подключение (closeHostConnection).

  private synchronized closeHostConnection(HostConnection conn)
    Помечает соединение неактивным, физически закрывает TCP-сокет к
    локальному серверу, убирает запись из ОБЕИХ карт
    (hostConnectionsBySessionId/hostConnectionsByAddress) — причём именно
    ТАК, что удаление сработает, только если в карте до сих пор лежит
    РОВНО ЭТОТ ЖЕ объект (перегрузка Map.remove(key, value) — "удали, только
    если текущее значение совпадает с ожидаемым") — это защита от гонки:
    устаревший поток от уже давно заменённого подключения не сможет
    случайно стереть более новую запись на том же ключе.

  private static closeQuietly(Socket socket)
    Просто закрывает сокет, если он не null и не закрыт, игнорируя
    возможное исключение при закрытии (закрытие — операция, которая почти
    никогда не должна "мешать" остальной логике своими ошибками).

  getReceiverPort()
    Текущий порт, на котором слушает UDP-приёмник.

  stop()
    Полная остановка моста: закрывает КАЖДОЕ хостовое подключение (цикл по
    снимку hostConnectionsByAddress.values()), обнуляет ClientSession,
    останавливает приёмник и прокси.

  private static newRetransmitBuffer()
    Создаёт специальный LinkedHashMap[Г19] с переопределённым[Г27]
    removeEldestEntry(...) — это стандартный приём Java: LinkedHashMap
    умеет сама удалять САМУЮ СТАРУЮ запись, если переопределить этот метод
    так, чтобы он возвращал true при превышении нужного размера —
    получается простая "кольцевая" структура ограниченного размера
    (RETRANSMIT_BUFFER_CAPACITY = 256 последних отправленных пакетов на
    сессию) без ручного удаления вручную.

  private static final class HostConnection (вложенный класс[Г33])
    Хранит ВСЁ, что нужно про ОДНОГО подключённого джойнера с точки зрения
    хоста: sessionId (final — не меняется никогда), peerAddress (volatile —
    МОЖЕТ поменяться, если у игрока переехал внешний порт NAT посреди
    игры, см. обработку выше), TCP-сокет к локальному серверу + потоки
    чтения/записи, свой персональный ReorderBuffer (inBuf), счётчик
    исходящих seq (outSeq, AtomicLong), свой персональный буфер
    ретрансляции (sentPackets) и флаг active. Раньше (до фичи "несколько
    игроков") такой объект был только ОДИН на весь хост — теперь их может
    быть несколько одновременно, по одному на каждого игрока.

  private static final class ClientSession
    Аналогичный, но более простой контейнер для роли джойнера (у джойнера
    нет привязки к конкретному адресу — он всегда есть только одна
    сессия с одним хостом): sessionId, ReorderBuffer, счётчик исходящих
    seq, буфер ретрансляции.



====================================================================
5. ЯДРО СЕТИ — УРОВЕНЬ 2: ЗНАКОМСТВО И ПРОБИВ NAT
====================================================================
Раздел объясняет, КАК два игрока вообще находят реальный IP-адрес друг
друга через интернет (у обоих обычно "серый" IP за роутером/NAT) и как им
удаётся напрямую обменяться UDP без открытия портов на роутере вручную.
Идея (классический "UDP hole punching"): третья сторона — сервер знакомств
(раздел 6) — видит настоящие "внешние" адреса обоих участников (т.к. они
сами к нему подключаются) и сообщает их друг другу; дальше оба участника
одновременно начинают слать друг другу пакеты напрямую — большинство
домашних роутеров в такой ситуации "открывает" временный проход для этого
конкретного направления трафика, т.к. видит, что их собственная сторона
инициировала исходящий трафик к этому чужому адресу.

--------------------------------------------------------------------
5.1 net.peercraft.network.rendezvous.RendezvousProtocol
Файл: fabric-example-mod/src/main/java/net/peercraft/network/rendezvous/RendezvousProtocol.java
(и БАЙТ-В-БАЙТ идентичная копия в rendezvous-server/.../rendezvous/RendezvousProtocol.java
— см. пояснение в разделе 6 про то, почему две копии, а не одна)
--------------------------------------------------------------------
Роль: описывает "язык", на котором мод и сервер знакомств общаются друг с
другом по UDP — набор функций "закодировать в байты"/"раскодировать из
байт" для каждого типа служебного сообщения. Каждое сообщение начинается с
одного и того же байта-метки MAGIC (0xE1) — по нему P2PBridge.handleIncomingPacket
отличает "это служебное сообщение сервера знакомств", а не обычный игровой
FramedPacket-пакет (у которого первый байт — версия формата, никогда не
равная 0xE1).

Константы:
  MAGIC — метка "это пакет протокола знакомств".
  TYPE_REGISTER / TYPE_ROOM_CREATED / TYPE_JOIN / TYPE_JOIN_FAIL /
  TYPE_PEER_FOUND / TYPE_PUNCH / TYPE_PUNCH_ACK — байт-код типа сообщения.
  REASON_INVALID_CODE / REASON_ALREADY_CLAIMED / REASON_EXPIRED /
  REASON_SERVER_BUSY — коды причин отказа (используются в JOIN_FAIL).
  REASON_ALREADY_CLAIMED теперь (после добавления лимита игроков)
  используется и как "комната уже занята другими игроками", хотя исходно
  задумывался только как "код уже занят кем-то" — переиспользован, чтобы
  не менять протокол лишний раз.

Вложенные record[Г10] — просто типизированные "конверты" для распакованных
данных:
  Address(InetAddress host, int port) — IP+порт.
  RoomCreated(String code, Address hostAddress) — ответ на REGISTER.
  Join(String code) — запрос присоединения.
  Register(int maxPlayers, int currentPlayerCount) — я добавил этот record
  при реализации лимита игроков — раньше REGISTER вообще не нёс данных.
  PeerFound(Address peer, long token) — "вот адрес твоего партнёра и
  секретный код (token) для проверки при пробиве".

Методы:
  static messageType(byte[] data, int length)
    Проверяет длину (минимум 2 байта) и первый байт (== MAGIC) — если
    всё сошлось, возвращает второй байт (тип сообщения) как int; иначе -1
    ("это не наш протокол вообще").
  private static writeAddress(ByteBuffer buf, Address address) / readAddress(ByteBuffer buf)
    Общие вспомогательные функции кодирования/раскодирования адреса:
    [длина IP в байтах:1][сами байты IP][порт:2 байта]. IPv4-адрес — 4
    байта, IPv6 — 16, поэтому длина хранится явно, а не жёстко зашита.
    readAddress оборачивает InetAddress.getByAddress(...) в try/catch —
    хотя формально этот вызов может бросить исключение, тут оно
    физически невозможно (длина всегда ровно та, что мы сами только что
    прочитали), поэтому просто перезаворачивается в необрабатываемое
    IllegalStateException, если вдруг что-то пойдёт совсем не так.
  private static addressSize(Address address) — сколько байт займёт адрес
    при кодировании (для точного расчёта размера буфера заранее).
  encodeRegister(int maxPlayers, int currentPlayerCount) / decodeRegister(...)
    [MAGIC][TYPE_REGISTER][maxPlayers:1 байт][currentPlayerCount:1 байт].
    Я изменил этот метод при добавлении лимита игроков — раньше это было
    буквально new byte[]{MAGIC, TYPE_REGISTER} без параметров вообще
    (2 байта, без полезной нагрузки).
  encodeRoomCreated(...) / decodeRoomCreated(...)
    [MAGIC][TYPE][длина кода:1][сам код][адрес хоста].
  encodeJoin(...) / decodeJoin(...)
    [MAGIC][TYPE][длина кода:1][сам код].
  encodeJoinFail(byte reason) / decodeJoinFailReason(...)
    Простейший — [MAGIC][TYPE][причина:1 байт].
  encodePeerFound(...) / decodePeerFound(...)
    [MAGIC][TYPE][адрес пира][token: 8 байт].
  encodePunch(long token) / encodePunchAck(long token) / private encodeTokenMessage(...)
    Оба — просто [MAGIC][TYPE][token:8 байт], различаются только байтом
    типа — поэтому вынесены в общую приватную функцию.
  decodeToken(byte[] data, int length)
    Читает 8 байт token, начиная с позиции 2 (сразу после MAGIC+TYPE).

5.2 net.peercraft.network.rendezvous.RendezvousClient
Файл: fabric-example-mod/src/main/java/net/peercraft/network/rendezvous/RendezvousClient.java
--------------------------------------------------------------------
Роль: реализует RawPacketListener (4.4) — отвечает за ОБЩЕНИЕ с сервером
знакомств по UDP (не за сам пробив — это отдельный класс PunchCoordinator,
5.3). Один объект используется либо в роли хоста (registerRoom), либо в
роли джойнера (joinRoom) — никогда одновременно.

Поля:
  RETRY_INTERVAL_MILLIS (=500) — как часто повторять REGISTER/JOIN, пока
  нет ответа (UDP не гарантирует доставку — единственный способ быть
  уверенным, что сообщение дошло, это повторять его, пока не пришёл ответ).
  CONNECT_TIMEOUT_MILLIS (=10000) — сколько ждать хоть какого-то ответа
  от сервера знакомств, прежде чем сдаться.
  KEEPALIVE_INTERVAL_MILLIS (=15000) — как часто хост, уже дождавшийся
  кода комнаты, шлёт "напоминание о себе" серверу — иначе NAT-маппинг
  роутера к серверу знакомств закроется от бездействия (обычно
  через 30-60 секунд у бытовых роутеров), и когда партнёр реально придёт
  присоединяться, ответ сервера ("вот твой партнёр") молча потеряется.
  state — enum[Г11] REGISTERING / JOINING / WAITING_FOR_PEER / DONE —
  текущий шаг внутреннего "автомата состояний".
  roomCallback / matchCallback — сохранённые колбэки[Г13], которые вызовет
  этот объект, когда придёт время.
  resultDelivered — AtomicBoolean — гарантия "финальный колбэк (успех или
  неудача) будет вызван РОВНО ОДИН РАЗ", даже если несколько условий
  одновременно "хотят" его вызвать.
  hostMode — true только в роли хоста.
  lastMatchedTokenByPeer — ConcurrentHashMap<Address, Long> — я переделал
  это поле при добавлении лимита игроков: раньше было ОДНО поле
  lastMatchedToken (Long) на весь объект — а значит, при матче с ВТОРЫМ
  джойнером старое значение (токен первого) стиралось, и запоздавший
  повторный PEER_FOUND от сервера про ПЕРВОГО джойнера уже не совпадал бы
  ни с чем и ошибочно считался бы "новым" матчем — то есть был реальный
  баг, который я исправил, сделав дедупликацию по каждому пиру отдельно.
  maxPlayers / currentPlayerCountSupplier — сохранённые при registerRoom(...)
  значение лимита и функциональный интерфейс[Г20] IntSupplier (буквально
  "функция без аргументов, возвращающая int") — вызывается заново на
  каждом keepalive, чтобы получить АКТУАЛЬНОЕ число подключённых игроков.
  lastKnownRoomCode — последний известный код комнаты (для обнаружения,
  что сервер вдруг вернул другой код — например, сам перезапустился и
  забыл старые комнаты).

Методы:
  cancel() [реализация RawPacketListener]
    Просто переключает state в DONE — все фоновые циклы этого объекта
    сами проверяют state на каждой итерации и сами останавливаются, когда
    видят DONE (см. ниже).
  registerRoom(int maxPlayers, IntSupplier currentPlayerCountSupplier, RoomCallback roomCallback, MatchCallback matchCallback)
    Входная точка для роли ХОСТА. Сохраняет все параметры, ставит
    hostMode=true, state=REGISTERING, запускает startRetryLoop(...) с
    лямбдой, которая каждый раз ЗАНОВО кодирует REGISTER свежими
    значениями maxPlayers/currentPlayerCountSupplier.getAsInt() (это и
    даёт "живой" REGISTER, а не один статический пакет).
  joinRoom(String code, MatchCallback matchCallback)
    Входная точка для роли ДЖОЙНЕРА. Тут JOIN-пакет ОДИН И ТОТ ЖЕ на все
    повторные отправки (код комнаты не меняется по ходу ожидания), поэтому
    startRetryLoop получает лямбду, всегда возвращающую один и тот же
    заранее посчитанный payload.
  private startRetryLoop(Supplier<byte[]> payloadSupplier, State activeState)
    Запускает отдельный поток[Г15]: пока state ещё равен activeState (то
    есть мы всё ещё "в процессе" именно этого шага) и не истёк
    CONNECT_TIMEOUT_MILLIS — берёт свежий payload у payloadSupplier.get()
    и шлёт его, затем засыпает[Thread.sleep] на RETRY_INTERVAL_MILLIS.
    Если цикл закончился, а мы всё ещё в том же activeState (то есть
    просто кончилось время, а не потому что мы успешно перешли дальше) —
    считается неудачей (fail(...)).
  onPacket(byte[] data, int length, InetAddress address, int port) [реализация RawPacketListener]
    Точка входа для ВСЕХ входящих пакетов, которые P2PBridge передал этому
    объекту. Сначала проверяет, что пакет реально от ожидаемого сервера
    знакомств (адрес+порт) — если нет, просто отладочный лог и выход
    (мало ли что долетело не по адресу). Дальше по типу сообщения — switch
    [Г24]-выражение (новый стиль switch с "->", а не старый с
    "case: break;") — вызывает соответствующий приватный обработчик.
  private handleRoomCreated(byte[] data, int length)
    Реагирует на ROOM_CREATED. Игнорирует, если мы уже не в
    REGISTERING/WAITING_FOR_PEER (например, случайный запоздавший пакет).
    Если это ПЕРВЫЙ раз — переключает state в WAITING_FOR_PEER и запускает
    startKeepaliveLoop(). Дальше сравнивает пришедший код с
    lastKnownRoomCode — если отличается (или это первый раз) — обновляет
    lastKnownRoomCode и вызывает roomCallback.onRoomCreated(code, changed).
  private startKeepaliveLoop()
    Отдельный поток: пока state == WAITING_FOR_PEER — спит
    KEEPALIVE_INTERVAL_MILLIS, затем (если состояние всё ещё то же) ЗАНОВО
    кодирует REGISTER со свежим currentPlayerCountSupplier.getAsInt() и
    шлёт его. Именно эта строка (пересчёт при КАЖДОМ тике, а не один раз
    до цикла) — реализация "живого счётчика мест", о которой я рассказывал
    в переписке выше.
  private handlePeerFound(byte[] data, int length)
    Реагирует на PEER_FOUND. Игнорирует, если состояние не то (см. код).
    В режиме хоста (hostMode): дедупликация — берёт из
    lastMatchedTokenByPeer предыдущий известный токен для АДРЕСА ЭТОГО
    конкретного пира (map.put(...) удобно возвращает старое значение
    заодно с записью нового — приём "положить и заодно узнать, что было
    раньше"). Если новый токен совпадает со старым — это просто повтор от
    сервера, игнорируем. Иначе — реальный (новый) матч, зовём
    matchCallback.onMatched(...). Состояние специально НЕ переключается в
    DONE — комната хоста может матчиться много раз подряд, для разных
    игроков. В режиме джойнера — наоборот, одноразово: state=DONE, и через
    resultDelivered.compareAndSet(false, true) [Г18] гарантированно
    зовём matchCallback.onMatched(...) только один раз.
  private handleJoinFail(byte[] data, int length)
    Если мы в состоянии JOINING — декодирует причину отказа и зовёт
    fail(...) с человекочитаемым текстом (см. describeReason ниже).
  private fail(String reason)
    Переключает state в DONE, и через resultDelivered гарантирует
    единственный вызов matchCallback.onFailed(reason) (плюс пишет
    предупреждение в лог).
  private static describeReason(byte reason)
    switch[Г24]-выражение — превращает числовой код причины отказа в
    русский текст ("неверный код комнаты", "комната уже занята" — теперь
    этот же текст обслуживает и случай "комната заполнена по лимиту
    игроков", "код комнаты истёк", "сервер знакомств перегружен...").

5.3 net.peercraft.network.rendezvous.PunchCoordinator
Файл: fabric-example-mod/src/main/java/net/peercraft/network/rendezvous/PunchCoordinator.java
--------------------------------------------------------------------
Роль: реализует RawPacketListener — сам процесс "пробива" NAT к ОДНОМУ
конкретному, уже известному (адрес+порт от сервера знакомств) партнёру.
Полностью самостоятельный объект — можно безопасно создавать и запускать
сразу несколько экземпляров параллельно (что и происходит на хосте при
нескольких джойнерах, см. P2PBridge.activePunches, 4.8) — они не делят
между собой никакого изменяемого состояния, кроме общего (и уже
потокобезопасного) P2PSender.

Поля:
  RETRY_INTERVAL_MILLIS (=300) — как часто слать PUNCH.
  TIMEOUT_MILLIS (=10000) — сколько пытаться, прежде чем сдаться.
  peer / token — кому и с каким секретным кодом пробиваемся.
  callback — куда сообщить результат.
  done — AtomicBoolean — "уже завершено (успехом, неудачей или отменой)?" —
  предотвращает двойной вызов колбэка, если, например, и таймаут, и
  успешный ответ подоспели почти одновременно.

Методы:
  start()
    Запускает отдельный поток с runPunchLoop().
  cancel() [реализация RawPacketListener]
    Просто ставит done=true — без вызова callback (тихая остановка).
  private runPunchLoop()
    Пока !done и не истёк TIMEOUT_MILLIS — шлёт пакет PUNCH{token} партнёру
    и засыпает на RETRY_INTERVAL_MILLIS. Если цикл закончился ПО ТАЙМАУТУ
    (done.compareAndSet(false, true) — атомарно "если ещё не done, сделай
    done и скажи мне, что это удалось именно тебе") — вызывает
    callback.onFailure(...).
  onPacket(byte[] data, int length, InetAddress address, int port) [реализация RawPacketListener]
    Проверяет тип сообщения — интересны только PUNCH и PUNCH_ACK, иначе
    выходит. Проверяет, что пакет ПРИШЁЛ ИМЕННО с того адреса+порта,
    которые нам назвал сервер знакомств — если нет, это диагностически
    интересный случай (возможно, у одной из сторон "симметричный" NAT,
    который меняет исходящий порт для разных направлений) — пишется
    предупреждение, пакет игнорируется. Проверяет совпадение token —
    несовпадение обычно означает "это запоздавший пакет от предыдущей
    попытки пробива к тому же партнёру". Если пришёл именно PUNCH (не
    ACK) — сразу же отвечает PUNCH_ACK тем же способом (чтобы партнёр,
    возможно, всё ещё ждущий именно ACK, тоже смог остановиться). Наконец,
    через done.compareAndSet(false, true) гарантированно ровно один раз
    вызывает callback.onSuccess(ip, port).

6. ОТДЕЛЬНЫЙ ПРОЕКТ: RENDEZVOUS-SERVER (СЕРВЕР ЗНАКОМСТВ)
====================================================================
Это отдельная маленькая программа (свой собственный Java-проект, без
зависимости от Minecraft/Fabric вообще — просто "голая" Java), которая
запускается на отдельной, всегда включённой машине (не у игроков) и не
участвует в самой передаче игровых данных — только сводит два (а теперь и
больше) IP-адреса вместе и передаёт им токены для пробива, как описано в
разделе 5.

--------------------------------------------------------------------
6.1 net.peercraft.rendezvous.RendezvousProtocol
Файл: rendezvous-server/src/main/java/net/peercraft/rendezvous/RendezvousProtocol.java
--------------------------------------------------------------------
БАЙТ-В-БАЙТ идентичная копия класса из раздела 5.1 (см. описание там —
повторять не буду). Почему копия, а не общий код: два проекта (мод и
сервер) собираются полностью независимо (у мода — сложная система сборки
Fabric Loom, у сервера — обычная Java), специально без общего
under-модуля, чтобы их сборки никогда не мешали друг другу. Расплата за
это — необходимость руками поддерживать оба файла синхронными. Чтобы
рассинхронизация не проходила незамеченной, в обоих проектах есть
тест fixedEncodingMatchesModCopy/fixedEncodingMatchesServerCopy,
проверяющий КОНКРЕТНЫЕ байты результата кодирования — если кто-то поправит
только одну копию, эти тесты начнут падать.


--------------------------------------------------------------------
6.2 net.peercraft.rendezvous.RendezvousServer
Файл: rendezvous-server/src/main/java/net/peercraft/rendezvous/RendezvousServer.java
--------------------------------------------------------------------
Роль: главный класс сервера — однопоточный цикл приёма UDP-пакетов plus
один фоновый поток для периодической очистки истёкших комнат.
final[Г4] класс.

Поля:
  DEFAULT_PORT (=51000) — порт по умолчанию.
  MAX_DATAGRAM_SIZE (=512) — намеренно маленький буфер приёма: все реальные
  сообщения этого протокола короче 32 байт, так что ничего крупнее и не
  нужно принимать — заодно это защита от UDP reflection/amplification атак
  (нельзя прислать что-то настолько большое, чтобы сервер вернул
  значительно больший ответ).
  SWEEP_INTERVAL_SECONDS (=30) — как часто чистить истёкшие комнаты.
  registry — RoomRegistry (см. 6.3) — вся внутренняя "база" комнат.
  socket — текущий DatagramSocket сервера.

Методы:
  static main(String[] args)
    Точка входа программы (обычный Java main[Г5] — именно его вызывает
    команда "java -jar rendezvous-server.jar [порт]"). Порт можно передать
    первым аргументом командной строки, иначе берётся DEFAULT_PORT.
    Создаёт RendezvousServer и вызывает run().
  Конструктор RendezvousServer(int port) — просто сохраняет порт.
  getBoundPort()
    Возвращает реальный порт, на котором слушает сокет (0, если ещё не
    запущен) — используется в тестах, которые специально просят системный
    "любой свободный порт" (0) и потом узнают, какой реально достался.
  run() (может бросить IOException — не ловится внутри, а "пробрасывается"
  наружу[Г12], что нормально для main-подобного метода верхнего уровня)
    try-with-resources[Г12] (конструкция try (DatagramSocket socket = ...) {...}
    — гарантирует, что socket.close() будет вызван автоматически, даже
    если внутри блока случится исключение — не нужно вручную писать
    finally). Создаёт сокет на нужном порту, запоминает его. Запускает
    отдельный поток-"уборщик" через ScheduledExecutorService[Г18]
    (стандартный Java-инструмент "выполняй эту функцию регулярно по
    расписанию") — каждые SWEEP_INTERVAL_SECONDS вызывает
    registry.sweepExpired(). Дальше — бесконечный цикл[while(true)]: ждёт
    очередной пакет (socket.receive(...) — блокирующий вызов), копирует
    его данные в новый массив и передаёт в handle(...). Любая ошибка внутри
    одной итерации (try/catch вокруг всего тела цикла) не останавливает
    сервер целиком — просто логируется, и цикл продолжается со следующего
    пакета (сервер не должен падать из-за одного кривого/вредоносного
    пакета).
  private handle(DatagramSocket socket, byte[] data, InetAddress fromAddr, int fromPort)
    Определяет тип пакета через RendezvousProtocol.messageType(...) — если
    это не наш протокол (-1) — просто выходит без всякой реакции. Дальше
    switch[Г24] по типу: REGISTER → handleRegister(...), JOIN →
    handleJoin(...), всё остальное (PUNCH/PUNCH_ACK и т.д.) — специально
    игнорируется (default-ветка с комментарием, что эти сообщения летят
    напрямую между игроками, сервер их никогда не видит и не должен).
  private handleRegister(DatagramSocket socket, byte[] data, RendezvousProtocol.Address from)
    Раскодирует новый payload через RendezvousProtocol.decodeRegister(...)
    (это я добавил при реализации лимита игроков — раньше метод вообще не
    принимал data, т.к. у REGISTER не было полезной нагрузки). Зовёт
    registry.register(from, maxPlayers, currentPlayerCount). Если получилось
    (Registered) — шлёт в ответ ROOM_CREATED с кодом комнаты; в лог пишет,
    новая это комната или просто повторный keepalive (see reused-флаг).
    Если отклонено (RegisterRejected) — шлёт JOIN_FAIL с причиной отказа
    (переиспользуется тот же тип ответа, у REGISTER нет отдельного
    "сообщения об отказе").
  private handleJoin(DatagramSocket socket, byte[] data, RendezvousProtocol.Address from)
    Раскодирует код комнаты из запроса, зовёт registry.join(code, from).
    Если Matched — шлёт PEER_FOUND ОБЕИМ сторонам сразу: хосту сообщает
    адрес джойнера, джойнеру — адрес хоста, с ОДНИМ общим token на эту
    пару (сервер не хранит состояние "кому уже отправлено" — просто шлёт
    оба сообщения сразу после успешного матча). Если JoinRejected — шлёт
    JOIN_FAIL только тому, кто попросил присоединиться (с текущей фичей
    лимита игроков сюда же попадает и код "комната заполнена" —
    REASON_ALREADY_CLAIMED). Дополнительно: если причина именно
    INVALID_CODE — выводит в лог ПОЛНЫЙ список всех известных сейчас комнат
    (registry.describeAllRooms()) — диагностическая мера, оставшаяся с
    момента реального расследования одного странного бага "код стал
    недействителен раньше времени" (описано в истории проекта).
  private static send(DatagramSocket socket, byte[] data, RendezvousProtocol.Address to)
    Простая обёртка — собрать DatagramPacket и отправить.
  private static describe(RendezvousProtocol.Address address)
    Форматирует адрес как строку "IP:порт" для логов.
  private static log(String message) / logErr(String message)
    Печатают строку в консоль (System.out / System.err) с меткой времени в
    формате ЧЧ:мм:сс.ммм впереди — простейшее логирование без внешних
    библиотек (в отличие от мода, тут нет SLF4J — сервер совсем
    минималистичный, без лишних зависимостей).

6.3 net.peercraft.rendezvous.RoomRegistry
Файл: rendezvous-server/src/main/java/net/peercraft/rendezvous/RoomRegistry.java
--------------------------------------------------------------------
Роль: вся "база данных" комнат сервера — целиком в оперативной памяти, без
сохранения на диск (комнаты — временные "рукопожатия", не аккаунты, при
перезапуске сервера все комнаты просто исчезают). final class, PACKAGE-
PRIVATE (нет модификатора public перед class — то есть класс виден только
внутри своего пакета net.peercraft.rendezvous, см. [Г2]) — снаружи пакета
никто не должен трогать эту "базу" напрямую.

Поля:
  CODE_ALPHABET — набор букв/цифр для генерации кода комнаты, специально
  БЕЗ похожих друг на друга символов (нет 0/O, 1/I/L и т.д. — чтобы человек,
  диктующий код другу голосом или переписывающий с экрана, не путал буквы).
  CODE_LENGTH (=6) — длина кода.
  ROOM_TTL_MILLIS (=10 минут) — комната "живёт", пока хост её регулярно
  подтверждает (REGISTER/keepalive) в пределах этого окна — то есть код
  комнаты остаётся рабочим сколько угодно долго, пока хост не закрыл мир.
  REMATCH_DEBOUNCE_MILLIS (=3 секунды) — окно, в течение которого повторный
  JOIN от ТОГО ЖЕ адреса считается просто повтором той же попытки
  подключения (а не новой), и получает тот же самый токен, а не новый.
  MAX_ROOMS (=1000) — общий предел количества комнат на сервере сразу
  (защита от переполнения памяти).
  REGISTER_RATE_LIMIT (=5) / REGISTER_RATE_WINDOW_MILLIS (=60 секунд) —
  ограничение "не больше 5 REGISTER с одного IP за минуту" — защита от
  спама/DoS с одного адреса.
  MIN_MAX_PLAYERS (=1) / MAX_MAX_PLAYERS (=32) — я добавил эти константы
  при реализации лимита игроков: сервер сам, независимо от мода, обрезает
  (clamp) присланное хостом значение maxPlayers в этот диапазон — так
  сервер не доверяет клиенту вслепую (мод мог быть с ошибкой/подделан).
  roomsByCode — ConcurrentHashMap<String, Room> — сама "база" комнат по коду.
  registerTimestampsByIp — карта "IP → очередь недавних времён REGISTER" —
  для расчёта rate limit.
  clock — LongSupplier[Г20] ("функция без аргументов, возвращающая long") —
  ИСТОЧНИК текущего времени. В обычной жизни это System::currentTimeMillis
  (ссылка на метод[Г14] — "просто спроси у системы реальное время"), но в
  тестах это подменяется на управляемый вручную счётчик — приём, который
  позволяет тестировать "что будет через 10 минут", НЕ ожидая эти 10 минут
  по-настоящему (см. второй конструктор ниже).

Методы:
  Конструктор RoomRegistry() — использует настоящее системное время.
  Конструктор RoomRegistry(LongSupplier clock) — package-private (виден
  только внутри пакета — это "потайной лаз", специально сделанный только
  для тестов, не для обычного использования).
  interface RegisterResult {} — пустой интерфейс-"маркер", просто чтобы
  можно было объявить, что результат либо Registered, либо RegisterRejected
  (оба ниже реализуют этот интерфейс).
  record Registered(String code, boolean reused) — успешная регистрация;
  reused=true означает "это была не новая комната, а просто повтор/
  keepalive уже существующей".
  record RegisterRejected(byte reason) — отказ (превышен rate limit или
  общий предел комнат).
  interface JoinResult {} — тот же приём для результата join(...).
  record Matched(Address hostAddress, Address joinerAddress, long token) —
  успешный матч.
  record JoinRejected(byte reason) — отказ (неверный код/комната
  заполнена/истекла).
  register(Address hostAddress, int maxPlayers, int currentPlayerCount)
    Сначала проверяет — есть ли УЖЕ комната от этого же hostAddress (цикл
    по всем существующим комнатам roomsByCode.values() — если у хоста уже
    есть комната, просто обновляет её lastSeenAt/maxPlayers/
    currentPlayerCount и возвращает СТАРЫЙ код с reused=true — именно так
    keepalive не плодит новые комнаты, а обновляет одну и ту же). Клампит
    maxPlayers в допустимый диапазон через приватный clamp(...). Если
    комнаты ещё нет — проверяет rate limit (allowRegister) и общий предел
    MAX_ROOMS; если всё в порядке — генерирует уникальный код
    (generateUniqueCode()), создаёт новый объект Room (см. 6.4), сохраняет
    maxPlayers/currentPlayerCount в него, кладёт в roomsByCode и
    возвращает Registered(code, reused=false).
  join(String code, Address joinerAddress)
    Ищет комнату по коду — если нет, JoinRejected(INVALID_CODE). Дальше
    ВЕСЬ код обёрнут в synchronized(room) [Г17] — блокировка именно на
    ЭТОМ КОНКРЕТНОМ объекте комнаты (а не на всём registry сразу) — так
    операции с разными комнатами могут идти параллельно без взаимных
    задержек, а с одной и той же комнатой — строго по очереди, что важно,
    т.к. несколько джойнеров могут пытаться присоединиться к одной
    комнате практически одновременно. Проверяет TTL — если комната не
    обновлялась дольше ROOM_TTL_MILLIS, удаляет её и возвращает
    JoinRejected(EXPIRED). Обновляет lastSeenAt. Смотрит, есть ли уже
    запись про ЭТОГО джойнера (room.joiners.get(joinerAddress) — это я
    переделал при добавлении фичи "несколько игроков": раньше в комнате
    было только ОДНО поле joinerAddress на всю комнату, второй РЕАЛЬНЫЙ
    джойнер просто затирал первого). Если запись есть И с последнего
    матча прошло не больше REMATCH_DEBOUNCE_MILLIS — это просто повтор той
    же попытки подключения, возвращает тот же token (без создания новой
    записи). Иначе — это либо совсем новый адрес, либо старый, но давно
    неактивный (переподключение) — если это ИМЕННО НОВЫЙ адрес (slot ==
    null) И текущее число игроков (self-reported хостом) уже достигло
    лимита — отказывает с REASON_ALREADY_CLAIMED ("комната заполнена").
    Иначе генерирует новый token, сохраняет/обновляет JoinerSlot для этого
    адреса в room.joiners и возвращает Matched(...).
  private static clamp(int value, int min, int max)
    Простое ограничение числа диапазоном — Math.max(min, Math.min(max, value))
    (сначала "не больше max", потом "не меньше min").
  sweepExpired()
    Периодическая уборка (вызывается по расписанию из RendezvousServer,
    НЕ на пути обработки обычных запросов) — удаляет из roomsByCode все
    комнаты, которые не обновлялись дольше ROOM_TTL_MILLIS (через
    removeIf(...) с лямбдой-условием[Г13]).
  roomCount() — просто текущее количество комнат (для диагностики/тестов).
  describeAllRooms()
    Формирует список текстовых строк "код (host=..., состояние, последний
    раз видели N мс назад)" по каждой комнате — используется сервером
    только для диагностического лога при странном отказе INVALID_CODE (см.
    RendezvousServer.handleJoin выше). Я обновил текст состояния при
    добавлении лимита игроков — теперь пишет "joined by X/Y (self-reported:
    Z)" вместо старого "claimed"/"unclaimed".
  private allowRegister(InetAddress ip)
    Реализация rate limit: достаёт (или создаёт) очередь[Г36] недавних
    времён REGISTER для этого IP, выбрасывает из неё все записи старше
    REGISTER_RATE_WINDOW_MILLIS (пока не осталось только "свежее"), и если
    в очереди всё ещё REGISTER_RATE_LIMIT или больше записей — отказывает;
    иначе добавляет текущее время и разрешает. Обёрнуто в
    synchronized(timestamps) — очередь используется из разных потоков
    (сервер однопоточный по приёму, но на будущее/на всякий случай защита
    не помешает — реально в текущем коде гонки нет, т.к. handle() вызывается
    последовательно, но это дешёвая подстраховка).
  private generateUniqueCode()
    Крутит randomCode(), пока не получится код, которого ещё нет в
    roomsByCode (do-while[Г12] цикл — "делай хотя бы один раз, потом
    проверяй условие").
  private static randomCode()
    Собирает случайную строку длины CODE_LENGTH из CODE_ALPHABET через
    ThreadLocalRandom (потокобезопасный генератор случайных чисел,
    оптимизированный для использования из многих потоков одновременно, в
    отличие от обычного java.util.Random) и StringBuilder[Г35] (эффективный
    способ собирать строку по кусочку, не создавая кучу промежуточных
    строк-копий, как это было бы при обычном "строка + строка").

6.4 net.peercraft.rendezvous.Room (rendezvous-server)
Файл: rendezvous-server/src/main/java/net/peercraft/rendezvous/Room.java
--------------------------------------------------------------------
Роль: "карточка" одной комнаты — просто данные, почти без логики (вся
логика — в RoomRegistry выше, который единственный трогает эти поля,
причём только под синхронизацией на самом объекте Room). final,
package-private (снова "виден только внутри своего пакета" — см. [Г2]).

Поля:
  code / hostAddress / createdAt — final, не меняются после создания
  (сам код комнаты, адрес хоста, время создания).
  lastSeenAt — когда последний раз обновлялась (REGISTER или JOIN).
  maxPlayers / currentPlayerCount — я добавил оба этих поля при реализации
  лимита игроков — раньше их не существовало вообще, лимита не было в
  принципе.
  joiners — Map<Address, JoinerSlot> — я заменил этим полем старые
  ЕДИНСТВЕННЫЕ joinerAddress/token/claimed/lastMatchedAt — теперь у КАЖДОГО
  джойнера своя отдельная запись, а не одна на всю комнату.

Конструктор Room(String code, Address hostAddress, long createdAt)
  Просто сохраняет три значения и выставляет lastSeenAt = createdAt.

Вложенный static class JoinerSlot
  Совсем маленький контейнер на одного джойнера: его адрес (final), его
  текущий token и время последнего матча (оба — обычные, не final, т.к.
  RoomRegistry.join(...) их обновляет при повторном/новом матче того же
  адреса).

7. О ТЕСТОВЫХ КЛАССАХ (кратко, не по методам)
====================================================================
Тесты не выполняются во время игры — это отдельный набор проверок, который
разработчик (или CI) запускает командой `./gradlew test`, чтобы убедиться,
что код по-прежнему работает правильно после любых изменений.

fabric-example-mod/src/test/java/net/peercraft/network/p2p/:
  FramedPacketTest — проверяет, что encode(...)+decode(...) для FramedPacket
  дают обратно те же данные (round-trip), и что decode(...) правильно
  отбрасывает битые/чужие пакеты.
  ReorderBufferTest — проверяет пересборку "не по порядку" пришедших
  кусков, запросы NACK, таймауты и переполнение буфера.

fabric-example-mod/src/test/java/net/peercraft/network/rendezvous/:
  RendezvousProtocolTest — round-trip кодирования/раскодирования каждого
  типа сообщения плюс тест с "зашитыми" байтами (fixedEncodingMatchesServerCopy)
  для защиты от рассинхронизации с копией на сервере.
  RendezvousClientTest — регрессионный тест на старый баг с бесконечными
  повторами REGISTER, плюс (добавлен мной) тест, что матчи для двух РАЗНЫХ
  джойнеров не мешают друг другу (не "затирают" дедупликацию один другого).
  RendezvousEndToEndTest — самый "тяжёлый" тест: реально поднимает
  rendezvous-server как отдельный процесс (subprocess) и гоняет через него
  настоящие RendezvousClient/PunchCoordinator по локальной петле (loopback)
  — включая (добавленный мной) тест с ДВУМЯ джойнерами, пробивающимися к
  одному хосту ОДНОВРЕМЕННО.

rendezvous-server/src/test/java/net/peercraft/rendezvous/:
  RendezvousProtocolTest — та же идея, что и в моде (вторая копия того же
  протокола).
  RoomRegistryTest — юнит-тесты всей логики комнат: уникальность кодов,
  идемпотентность REGISTER, TTL, дебаунс повторных JOIN, и (добавленные
  мной) тесты лимита игроков — отказ при переполненной комнате, разрешённый
  повторный вход уже известного джойнера даже при "заполненной" комнате,
  освобождение места после того, как хост сообщил уменьшённый
  currentPlayerCount.
  RendezvousServerIntegrationTest — поднимает настоящий RendezvousServer
  внутри той же JVM (без отдельного процесса) и гоняет через него сырые
  DatagramSocket, эмулируя реального хоста/джойнера — включая (добавленные
  мной) тесты с двумя одновременными джойнерами и с отказом третьему при
  превышении лимита.

ГЛОССАРИЙ: ОСНОВЫ JAVA (и немного Fabric/Minecraft-специфики)
====================================================================
Каждый пункт — то, на что в тексте выше стоит пометка вида [ГN].

[Г1] package / import
  package в самом верху файла — это "папка" (пространство имён), к которой
  относится класс — нужно, чтобы разные библиотеки могли иметь классы с
  одинаковым коротким именем без конфликта (просто у них будет разный полный
  путь, например net.peercraft.network.p2p.PeerAddress). import — способ
  "подключить" в файл класс из другого package, чтобы можно было писать
  его короткое имя, а не полный путь каждый раз.

[Г2] Модификаторы доступа: public / private / protected / (ничего)
  public — виден и используется откуда угодно.
  private — виден только внутри самого этого класса.
  protected — виден внутри класса, его наследников, и внутри пакета.
  Если модификатор вообще не написан — это называется "package-private":
  виден только классам из того же package (папки).

[Г3] static
  Означает "принадлежит самому классу, а не отдельному созданному объекту".
  Например, static-метод можно вызвать как ClassName.method(...), без
  создания объекта класса через new. static-поле — одно на весь класс, а
  не своя копия у каждого объекта.

[Г4] final
  Для переменной/поля — значение можно присвоить только один раз (дальше
  уже нельзя переприсвоить). Для метода — его нельзя переопределить в
  классе-наследнике. Для класса — у него вообще не может быть наследников.

[Г5] Конструктор класса
  Специальный "метод" с именем, совпадающим с именем класса, без
  указанного типа возвращаемого значения — вызывается автоматически при
  создании объекта через ключевое слово new. "void" в обычных методах
  означает "метод ничего не возвращает" (в отличие от, например, int
  method() — такой обязан вернуть число через return).

[Г6] this / super
  this — ссылка "на самого себя" (на текущий объект) внутри метода.
  super — ссылка на реализацию из родительского класса (например,
  super.render(...) вызывает оригинальный, "родительский" вариант метода
  render, прежде чем/вместо того, чтобы делать что-то своё).

[Г7] interface (интерфейс) и implements
  Интерфейс — это просто список "обещанных" методов (без реализации,
  только сигнатуры — как договор "у любого класса, реализующего этот
  интерфейс, обязательно будут эти методы"). implements — ключевое слово,
  которым класс заявляет "я выполняю обещания вот этого интерфейса" и
  дальше обязан написать РЕАЛЬНЫЙ код для каждого его метода.

[Г8] abstract class и extends (наследование)
  extends — класс "наследуется" от другого класса, автоматически получая
  все его поля и методы, и может добавлять/переопределять что-то своё.
  abstract class — класс, который нельзя создать напрямую через new (в нём
  могут быть методы вообще без тела — обязанность их реализовать
  перекладывается на наследников). В коде мода abstract часто встречается
  из-за технических требований Mixin-библиотеки (см. [Г29]), а не потому,
  что это "настоящее" абстрактное понятие.

[Г9] Generics — <T>, <K, V>
  Способ написать код, который работает с ЛЮБЫМ типом данных, но при этом
  остаётся типобезопасным. Например, Map<String, Integer> — это "словарь,
  где ключи — строки, а значения — целые числа"; сама буква в треугольных
  скобках (T, K, V — просто традиционные короткие имена: T = Type, K = Key,
  V = Value) — "заглушка", которая при реальном использовании заменяется
  на конкретный тип.

[Г10] record
  Специальный, очень компактный вид класса (появился в современных версиях
  Java), предназначенный для "просто хранения нескольких значений вместе".
  При объявлении record PeerAddress(InetAddress host, int port) {} Java
  сама, автоматически, генерирует: конструктор, геттеры host()/port(),
  методы equals()/hashCode() (для сравнения двух объектов "по значению", а
  не "по ссылке на один и тот же объект в памяти") и toString() — всё, что
  иначе пришлось бы писать руками в обычном классе.

[Г11] enum — перечисление
  Специальный тип, который может принимать только одно из ЗАРАНЕЕ
  перечисленных значений — например, private enum State { REGISTERING,
  JOINING, WAITING_FOR_PEER, DONE } — переменная этого типа не может быть
  ничем, кроме одного из этих четырёх слов, что делает опечатки/
  недопустимые значения невозможными на уровне компиляции.

[Г12] try / catch / finally, исключения
  Механизм обработки ошибок. Код внутри try выполняется как обычно; если
  внутри что-то "бросает" исключение (throw) — выполнение блока try сразу
  прерывается, и управление переходит в соответствующий catch (если тип
  исключения совпадает с тем, что указан после catch). Блок finally
  выполняется ВСЕГДА — и если всё прошло гладко, и если было исключение
  (даже если оно не было поймано) — обычно используется для "гарантированной
  уборки" (закрыть файл/сокет и т.п.). "Checked"-исключения (например,
  IOException) Java заставляет либо ловить, либо явно объявлять в сигнатуре
  метода (throws IOException); "unchecked" (RuntimeException и его
  наследники) — можно игнорировать, компилятор не заставит.
  try-with-resources — особая форма: try (ResourceType x = ...) {...} —
  гарантирует автоматический вызов x.close() в конце, без ручного finally.
  do { ... } while (условие) — цикл, который выполнится хотя бы один раз,
  ПЕРЕД первой проверкой условия (в отличие от обычного while, который
  сначала проверяет условие).

[Г13] Лямбда-выражение
  Короткая "функция без имени", которую можно передать как значение —
  например (a, b) -> a + b — "функция, принимающая a и b, возвращающая их
  сумму". Синтаксис x -> { ... } или просто x -> выражение. Используется
  везде, где нужен "код, который выполнится позже" — колбэки, обработчики
  кликов кнопок, условия для .removeIf(...) и т.д. Требует, чтобы тип
  переменной был "функциональным интерфейсом" — интерфейсом ровно с одним
  методом (тогда Java понимает, какую именно "дырку" заполняет лямбда).

[Г14] Ссылка на метод (Class::method / object::method)
  Ещё более короткая форма лямбды, когда лямбда просто целиком состоит из
  вызова уже существующего метода — например System::currentTimeMillis
  вместо () -> System.currentTimeMillis(), или this::currentPlayerCount
  вместо () -> this.currentPlayerCount().

[Г15] Thread и daemon-поток
  Thread — отдельная "нить" выполнения кода, работающая параллельно с
  остальной программой (в этом моде почти весь сетевой код работает в
  отдельных потоках, чтобы не "морозить" игру во время ожидания сети).
  .setDaemon(true) помечает поток как "демон" — такой поток не мешает JVM
  корректно завершиться (обычные, не-daemon потоки не дают процессу
  закрыться, пока сами не закончатся — daemon-потоки просто обрываются при
  выходе, что и нужно для фоновых сетевых циклов мода).

[Г16] volatile
  Модификатор поля, гарантирующий, что при чтении этого поля из ЛЮБОГО
  потока будет видно самое последнее записанное значение (без volatile
  один поток теоретически мог бы долго "не замечать" изменение,
  сделанное другим потоком, из-за внутреннего кеширования процессора/JIT-
  компилятора). Не даёт полной потокобезопасности сама по себе (например,
  не защищает составные операции вида "прочитать-изменить-записать"), но
  гарантирует "видимость" одиночных чтений/записей.

[Г17] synchronized
  Блокировка: если метод или блок кода помечен synchronized (на каком-то
  объекте), то в любой момент времени этот код может выполнять только ОДИН
  поток — остальные, если попытаются войти одновременно, будут ждать
  своей очереди. Нужно, когда несколько потоков могут одновременно менять
  одни и те же данные, и без такой очереди могли бы их испортить.

[Г18] "Атомарные" классы и java.util.concurrent
  AtomicBoolean/AtomicLong — обёртки над обычным boolean/long, которые
  умеют выполнять операции вроде "прочитать и сразу изменить" КАК ОДНО
  неделимое (атомарное) действие, без отдельной synchronized-блокировки —
  например .compareAndSet(ожидаемое, новое) — "если сейчас там ожидаемое
  значение, замени на новое и скажи, что получилось; если нет — не меняй
  и скажи, что не получилось" — именно так реализована защита от двойного
  клика в этом моде. .getAndIncrement() — "верни текущее значение, потом
  прибавь единицу", тоже атомарно. ConcurrentHashMap — словарь (см. [Г19]),
  безопасный для одновременного использования из многих потоков без
  внешней synchronized-блокировки. ThreadLocalRandom — генератор случайных
  чисел, оптимизированный для многопоточного использования (в отличие от
  обычного Random, у которого при интенсивном параллельном использовании
  из многих потоков падает производительность). ScheduledExecutorService —
  готовый инструмент "выполняй эту функцию каждые N секунд" без ручного
  написания потока со sleep в цикле.

[Г19] Коллекции: Map / List / Set
  Map<K, V> — словарь "ключ → значение" (в этом проекте используются
  HashMap — обычный несортированный, ConcurrentHashMap — потокобезопасный,
  LinkedHashMap — запоминает порядок добавления записей (и умеет, если
  переопределить removeEldestEntry, сама выбрасывать самые старые записи
  при превышении размера — так сделан "кольцевой" буфер ретрансляции в
  P2PBridge), TreeMap — держит записи отсортированными по ключу).
  List<T> — упорядоченный список с повторами (в проекте — обычно
  результат Stream'ов, см. [Г21]). Set<T> — набор БЕЗ повторов (в проекте
  — Set<PeerAddress> authorizedPeers, ConcurrentHashMap.newKeySet() —
  быстрый способ получить потокобезопасное множество на основе
  ConcurrentHashMap). Deque<T> (ArrayDeque) — очередь, из которой удобно
  забирать/добавлять элементы С ОБОИХ концов — используется для истории
  времён REGISTER (RoomRegistry.allowRegister) как "скользящее окно".

[Г20] Функциональные интерфейсы из java.util.function
  Готовые (стандартные, поставляются вместе с Java) интерфейсы ровно с
  одним методом — специально для передачи "кода как значения" (см. [Г13]).
  Supplier<T> — "дай мне значение типа T, без аргументов" (метод .get()).
  IntSupplier — то же самое, но для примитивного int, без лишней "коробки"
  Integer (метод .getAsInt()) — используется для currentPlayerCountSupplier
  (P2PBridge/RendezvousClient) и для clock (RoomRegistry, там —
  LongSupplier, аналогично для long). Function<A, B> — "дай мне A, я
  верну B" (метод .apply(a)).

[Г21] Stream API
  Способ описать обработку последовательности значений цепочкой вызовов
  вместо ручных циклов. IntStream.rangeClosed(1, 8) — "поток целых чисел
  от 1 до 8 включительно". .boxed() — превращает поток примитивных int в
  поток объектов Integer (коллекции Java не умеют напрямую хранить
  примитивы, только объекты). .collect(Collectors.toList()) — "собери всё
  это в обычный список".

[Г22] ByteBuffer (java.nio)
  Класс для ручной сборки/разбора последовательности байт с чётким
  контролем формата (в отличие от, скажем, простого объединения массивов) —
  умеет писать/читать числа разных размеров (.put() — один байт, .putLong()
  — 8 байт как одно число, и т.д.), сам следит за текущей позицией
  чтения/записи внутри буфера. Используется в FramedPacket и
  RendezvousProtocol для ручной сборки "конвертов" сетевых сообщений.

[Г23] Сетевые классы Java (java.net)
  Socket — один конец обычного TCP-соединения (надёжная, потоковая
  передача данных, как телефонный звонок — сначала "дозвониться", потом
  говорить по очереди). ServerSocket — "слушающая" сторона TCP, которая
  ждёт входящих Socket-подключений (.accept() — блокирующий вызов, "жди
  следующего, кто позвонит"). DatagramSocket — "розетка" для UDP
  (ненадёжная, без гарантии порядка/доставки, но без предварительного
  "дозвона" — как открытка по почте: отправил и не факт, что дойдёт, но и
  не нужно заранее договариваться). DatagramPacket — один конкретный UDP-
  "пакет"/"открытка" — данные + адрес назначения (или, при приёме, адрес
  отправителя). InetAddress — представление IP-адреса в Java (умеет
  резолвить текстовые адреса/доменные имена через .getByName(...) и
  превращать обратно в текст через .getHostAddress()).

[Г24] switch-выражение (стиль с "->")
  Современная форма switch в Java: switch (значение) { case ВАРИАНТ ->
  результат_или_код; ... } — короче и безопаснее старого стиля с
  case: ... break; (не надо помнить про break, иначе исполнение "проваливается"
  в следующий case — частая старая ошибка).

[Г25] Тернарный оператор ?:
  Короткая форма "если-иначе" прямо внутри выражения: условие ? значение_если_true
  : значение_если_false — например `parsed ? "да" : "нет"`.

[Г26] instanceof с автоматическим приведением типа
  Проверка "является ли объект экземпляром именно этого класса" —
  современный синтаксис вида `if (result instanceof Matched matched) {...}`
  сразу же, если проверка прошла успешно, создаёт внутри блока новую
  переменную matched уже нужного, более конкретного типа — не нужно
  отдельной строкой писать явное приведение типа (Matched) result.

[Г27] Аннотации
  Пометки вида @Слово перед классом/методом/полем — сами по себе не код, а
  "метаданные", которые читает либо компилятор, либо сторонние библиотеки/
  фреймворки. @Override — говорит компилятору "я точно переопределяю метод
  родителя/интерфейса, если это не так — покажи ошибку" (защита от опечаток
  в имени метода). Остальные важные для этого проекта аннотации —
  Fabric-специфичные, см. [Г29].

[Г28] Logger (SLF4J)
  Стандартная в Java-мире библиотека логирования — вместо
  System.out.println(...) используются LOGGER.info(...)/.warn(...)/.error(...)/
  .debug(...) — плюсы: можно централизованно включать/выключать уровни
  подробности, автоматически пишется и в файл, и в консоль, сообщения
  можно снабжать "плейсхолдерами" ({} в строке подставляется по порядку
  переданными следом аргументами, без ручной конкатенации строк).

[Г29] Fabric Mixin (@Mixin, @Inject, @At)
  Это НЕ часть самой Java — отдельная библиотека, специфичная именно для
  модификации Minecraft (и похожих закрытых Java-игр). @Mixin(TargetClass.class)
  над классом означает "код этого класса при запуске игры будет
  подмешан прямо в байт-код TargetClass" (это происходит один раз, во
  время загрузки игры, а не во время редактирования исходников самой
  игры). @Inject(method = "имяМетода", at = @At("HEAD"/"TAIL"/"RETURN"/...))
  над методом означает "вставь тело этого метода в указанное место
  ("HEAD" — самое начало, "TAIL" — самый конец, "RETURN" — прямо перед
  КАЖДЫМ выходом из метода) внутри оригинального метода имяМетода
  целевого класса". CallbackInfo / CallbackInfoReturnable<T> — служебные
  параметры, через которые вклеенный код может, например, узнать итоговое
  возвращаемое значение оригинального метода (cir.getReturnValue()) —
  доступны только внутри @Inject-методов, это не обычные Java-параметры.

[Г30] Component (Minecraft)
  Класс из самого Minecraft, представляющий кусок текста для отображения в
  игре (чат, интерфейс, названия предметов) — с поддержкой цвета/форматирования.
  Component.literal("текст") — "просто голый текст без переводов на другие
  языки" (в противовес Component.translatable(...), который ищет перевод
  по ключу в языковых файлах игры).

[Г31] Паттерн "Builder"
  Распространённый в Java стиль создания сложных объектов пошагово:
  Checkbox.builder(...).pos(...).selected(...).onValueChange(...).build() —
  каждый метод настраивает одну характеристику и возвращает "себя же" для
  следующего вызова цепочкой (это и называется method chaining —
  "цепочка вызовов методов"), а .build() в конце наконец создаёт готовый
  объект. Используется в основном в Minecraft/Fabric API для создания
  GUI-виджетов (кнопок, чекбоксов, степперов).

[Г32] Анонимный класс
  Способ создать ОДИН объект, реализующий интерфейс (или наследующий
  класс), прямо на месте использования, без объявления отдельного
  именованного класса где-то ещё в файле — синтаксис `new ИмяИнтерфейса() {
  // тут реализация всех методов интерфейса
  }`. Отличается от лямбды[Г13] тем, что может реализовывать интерфейс с
  НЕСКОЛЬКИМИ методами (лямбда — только с одним) — например
  P2PBridge.HostListener или ConnectListener с их 2-3 методами реализованы
  именно так.

[Г33] Вложенный статический класс
  Класс, объявленный ВНУТРИ другого класса, с модификатором static —
  например `private static final class HostConnection {...}` внутри
  P2PBridge. static здесь означает "этот вложенный класс не привязан к
  конкретному экземпляру внешнего класса" (в отличие от вложенных
  НЕ-static классов, которые в Java всегда неявно хранят ссылку на
  "родительский" объект). Используется просто для группировки — чтобы
  небольшой вспомогательный класс-контейнер данных (вроде HostConnection
  или ReorderBuffer.Result) не "болтался" отдельным файлом, если он нужен
  только внутри одного конкретного класса.

[Г34] null и проверки на null
  null — специальное значение "ссылка в никуда", означает "тут пока/уже
  нет объекта". Обращение к полю/методу null-объекта (например
  socket.send(...), если socket == null) приводит к аварийному падению
  (NullPointerException) — поэтому в коде мода перед использованием
  часто явно проверяется `if (x != null) { ... }`. .isBlank() — метод
  строки (не про null, а про "пустоту"): true, если строка либо совсем
  пустая, либо состоит только из пробельных символов.

[Г35] Массивы byte[] и операции с ними
  byte[] — массив байт (простейших чисел от -128 до 127) — то, из чего
  физически состоят все данные, передаваемые по сети. Arrays.copyOfRange(a, from, to)
  — вырезает кусок массива в новый массив. System.arraycopy(...) —
  быстрое копирование части одного массива в другой (используется вместо
  ручного цикла по производительности). StringBuilder — изменяемый
  "конструктор строк": в Java обычная String неизменяема (любая
  "модификация" на самом деле создаёт новую строку целиком), а
  StringBuilder позволяет эффективно дописывать текст кусками (.append(...))
  и получить итоговую строку только в конце (.toString()).

[Г36] Deque (ArrayDeque)
  "Двусторонняя очередь" — коллекция, из которой удобно добавлять/забирать
  элементы и с начала, и с конца (.peekFirst() — посмотреть первый элемент
  не удаляя, .pollFirst() — забрать и удалить первый, .addLast() —
  добавить в конец). В этом проекте используется, чтобы хранить "окно
  недавних времён" (RoomRegistry.allowRegister) — старые записи
  выбрасываются с начала, новые добавляются в конец, что естественно
  реализует "скользящее окно по времени".
